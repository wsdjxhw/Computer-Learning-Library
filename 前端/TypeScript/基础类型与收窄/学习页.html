1 · 原始类型、数组与元组

类型系统的字母表。TS 的原始类型关键字比 Java 少一半——因为 JS 只有一种数字、没有 char。先把地基打准，后面的收窄才不会踩空。

本节目标：能区分数组与元组，解释 number、null、undefined 的关键边界，并选出正确的类型标注。

1.1 三大件：string / number / boolean

number 一个类型管所有数。Java 里 byte/short/int/long/float/double 六兄弟各管一段，TS 里全是 number——这不是偷懒，是历史：JS 1995 年设计时（Brendan Eich 著名的 10 天）选了 IEEE 754 双精度浮点一统天下，整数小数在内存里是同一种东西；TS 是 JS 的类型层，只能继承这个事实。代价是整数小数不分家：


    
算钱的铁律：先乘到整数分运算，展示时再 toFixed(2)；浮点比较永远用误差范围而不是 ===。超过安全整数范围的大数（订单号、雪花 ID）用 bigint 或干脆 string——见本节深挖。

    
string 不可变，和 Java 的 String 完全一样：trim()、replace() 都返回新串，原串不动。TS 没有 char：单字符就是长度为 1 的 string（Java 里 'a' 是 char、"a" 是 String，TS 里只有 'a'）。

    
boolean 只有两个值。注意划清界限：truthy/falsy 是「在条件位置当真当假」的强制转换规则，跟 boolean 类型无关——0 不是 boolean，但它是 falsy。这个区别在第 3 节真值收窄里会反复出现。


    
1.2 两个空：null 与 undefined

    
JS 地基里讲过运行时分工，TS 把它们当成两个不同的类型，并且 strict 模式下不再是谁都能塞的默认值（strictNullChecks，包含在 --strict 里）：

    

    

      
undefinednull

      
语义「从来没有」：未赋值 / 没传参 / 没有这个属性「现在没有」：明确置空，人为表示无数据

      
谁产生语言自动（漏赋值就是它）只有你手写才会出现

      
TS 态度strict 下都不可赋给其他类型；可空必须显式写进联合（string | null）

    

    
「可空要显式写进联合」这一条，就是后面所有收窄故事的起点——类型系统先把可能性说全，代码里再一层层证明排除。


    
1.3 数组与元组

    

    
要点：数组两种写法完全等价，元素同型、长度不进类型（对照 Java：数组定长，String[3] 就是 3 个）；元组定长 + 每位定类型 + 顺序敏感，适合「固定搭配的一组值」（坐标对、键值对、CSV 的一行）；带标签元组把含义写进类型，读代码不用背下标。


    
深挖 · 为什么没有 int？安全整数边界 2^53
      

        
IEEE 754 双精度用 52 位尾数 + 1 位隐含位存整数，所以能精确表示的整数上限是 2^53 − 1 = Number.MAX_SAFE_INTEGER = 9007199254740991。再往上相邻整数会「粘住」（本机 node 实测）：

        
9007199254740992 === 9007199254740993   // true —— 两个都舍入到 2^53，判重失真

        
后果：大整数 ID 一旦当 number 处理，去重/比较会悄悄出错。工程惯例：后端把大数序列化成字符串，前端用 string 接；真要运算用 bigint（字面量带 n：9007199254740993n，typeof 是 'bigint'，与 number 不能直接混算）。

      

    

    

    
本节记住：number 同时表示整数和小数；可空必须显式写进联合；数组不固定长度，元组固定每个位置的类型。

  


  
  

    
2 · 字面量类型与联合类型

    
TS 表达力的第一个来源：类型可以不只是「类名」，还可以是「具体的值」和「值的组合」。这一节两个概念，撑起后面所有的建模。

    
本节目标：能解释「值域是并集、可访问成员是交集」，并判断 const 与 let 的字面量推导差异。


    
2.1 字面量类型：把值本身当类型

    
'asc'、0、true 这种具体的值也能当类型——此时合法取值只有这一个。单个字面量类型没什么用，威力在它参与联合之后：约束一组合法取值，比 Java enum 更轻（回想初识 TypeScript：enum 是唯一有运行时产物的例外，字面量联合编译后零残留），拼错立刻编译期现形，IDE 还能自动补全。


    
2.2 联合类型：值域的「或」

    
A | B 读作「A 或 B」，值域是两者的并集。业务里最常见三种：string | null（可能没有）、'asc' | 'desc'（枚举取值）、Fish | Bird（形状分岔，第 4 节主角）。联合可以嵌套并自动摊平：(A | B) | C 就是 A | B | C。


    
2.3 联合上只能访问共有成员

    

    
规则为什么这么定：编译器必须保证「这行代码在任何一种可能下都成立」。toString() 两种类型都有，放行；trim() 只有 string 有，万一进来的是 number 就崩了——所以 TS2339 拦下。想让编译器知道「现在只剩一种可能」，就是下一节的主角：收窄。


    

    
深挖 · 字面量拓宽（widening）：let 和 const 推导为什么不一样？
      

        
const dir = 'asc' 推导为 'asc'（const 不会再改，类型可以精确到值）；let dir2 = 'asc' 推导为 string——let 可能被重新赋值，TS 故意把字面量「拓宽」成通用类型，否则 dir2 = 'desc' 就报错了。

        
想要 let 也锁死取值：显式标注 let dir3: 'asc' | 'desc' = 'asc'。这就是「枚举式取值要手写联合」的底层原因。另一个方向（把已有值锁成字面量）是 as const 断言，在知识点 ⑤「类型推导与断言」细讲。

      

    

    
本节记住：联合描述的是所有可能值，因此未收窄前只能使用所有成员都具备的共有成员。

  


  
  

    
3 · 收窄六式

    
联合类型只是「声明了所有可能」；收窄（narrowing）是编译器沿着控制流，逐行证明「走到这一行，值只可能是哪几种」。前五式是现成的判断手段，第六式是主动建模。Java 里你手写 instanceof + 强转的活，TS 沿代码路径自动推。

    
本节目标：看到联合成员的形态，能选出合适的收窄方式，并逐行说出判断前后的类型。


    

    
① typeof 收窄——原始类型分岔

    

    
typeof 的坑：返回值只有 8 种字符串（'string' 'number' 'boolean' 'undefined' 'object' 'function' 'symbol' 'bigint'），其中 typeof null === 'object' 是 JS 1995 年的实现 bug，为兼容 30 年没改——排除 null 永远用 === null（第三式），别信 typeof。


    
② 真值收窄——if(x) 排除空

    

    
边界（面试高频）：JS 的 falsy 值共 8 个：false、0、-0、0n、''、null、undefined、NaN。if(x) 在类型层只排除 null/undefined（TS 没有「非空字符串」这种类型），在运行时却滤掉全部 8 个。greet('') 会走进 !name 分支返回「匿名」——类型层完全看不出来。两层永远分开想；想精确排除空串，用 s === ''。


    
③ 相等性收窄——一刀切走某个值

    

    
深挖 · == null 是宽松相等里唯一被推荐的特例
      

        
JS 地基里说过 == 会隐式转换、永远别用——但 x == null 是官方背书的例外：它同时匹配 null 和 undefined（且不匹配 falsy 的 0、''）。TS 也认：它会把 x == null 之后 x 的类型同时收掉 null 和 undefined。所以老代码里见到 if (x == null) return; 不是坏味道，是惯用法；新代码统一 === 也完全没问题。

      

    


    
④ in 收窄——按「有没有某属性」分岔

    

    
'swim' in pet 问的是对象里有没有 swim 这个键。适合形状不同的对象联合（一个会游一个会飞）；Java 没有对应物（instanceof 只认类，不认形状）——这是结构类型系统的独有分法。


    
⑤ instanceof 收窄——按原型链分岔

    

    
沿原型链找构造函数，语义同 Java instanceof，适合「类实例 vs 原始值」的混合（Date、RegExp、Error、Map 等）。

    
两个坑：① 跨 iframe/window 的对象原型不同（两个页面的 Array 互不认识），Web Worker / 第三方 iframe 场景会失手；② 'x' instanceof String 永远 false——原始值不是对象，包了 new String('x') 才是。判原始值用 typeof，判对象用 instanceof，别混。


    
⑥ 判别联合——业务建模首选

    
前五式都是「数据长什么样就怎么分」；第六式反过来——主动把数据设计成好分岔的形状。它值得单独一节，见下。


    

      
互动 · 收窄追踪器

      
这是控制流教学模拟，不是在浏览器里运行 tsc。先选一个输入并预测输出，再用「下一步」逐行核对类型怎样变窄。

      

      

      

      

      

    

    


    
深挖 · 控制流分析：收窄的三个伙伴
      

        
收窄不只发生在 if 里——①赋值收窄：let x: string | number = f(); x = 'hi'; 赋值那行起 x 就是 string；②提前返回：if (x === null) return 0; 之后 null 被永久排除（return 截断了后续控制流）；③别名跟随：const s = x; 之后对 x 的收窄，s 也跟着享受。TS 编译器对每条语句做的是控制流类型分析——你写的每一行都在缩小「此刻可能的世界」。

      

    


    
    
本节记住：收窄不是强制转换，而是控制流证明；选择手段时先看成员形态，同时分清类型层收窄与运行时过滤。

  


  
  

    
4 · 判别联合：业务建模的第一选择

    
把一组互斥的形状建成联合，每个成员带一个字面量类型的标签字段。switch 标签 → 自动收窄到对应成员。这是 TS 里最接近「Java enum + 多态」的表达力，也是类型安全收益最大的一招。

    
本节目标：能把可选属性堆叠改造成判别联合，并解释为什么非法状态会因此变得无法表达。


    
4.1 先看烂版本长什么样

    

    
三宗罪：①不合法状态可表达——kind: 'circle' 却没有 r 完全合法；②每个属性都是 number | undefined，用起来步步惊心；③新增形状时编译器一言不发，错误漏到运行时（NaN 静默传播，报表里一列 NaN 才发现）。


    
4.2 正确版本

    

    
逐行看门道：kind 在每个成员里是不同的字面量类型（'circle' vs 'square'）——这正是 switch 能精确分流的依据，这样的字段叫判别字段（discriminant）。注意判别字段标普通 string 不行（无法区分成员），必须是字面量类型。case 内部 s 自动收窄为 Circle / Square，s.r、s.w 放心用，没有任何 ?. 和 ?? 0。

    
Java 对照：这就是 Java 17 的 sealed interface + record + 模式匹配 switch 干的事——permits 白名单 = 联合成员，pattern case = 自动收窄。两个语言殊途同归（TS 从 2012 年起就能这么写）。

    
实战模式：API 响应建模 type Result<T> = { status: 'ok'; data: T } | { status: 'err'; message: string }——比抛异常更适合前端：错误是数据而不是控制流，渲染层 switch 一下就分流，还能配合下一节的 never 穷尽检查防漏。


    
互动 · 判别联合路由图

    
点击不同的 kind 值，看 switch 把它路由到哪个分支、收窄成什么类型——squiggle 是故意「没写分支」的新成员。

    

      

      

      

    

    
本节记住：判别字段让每个业务形态拥有明确标签；联合负责限制合法状态，switch 负责按标签安全分流。

  


  
  

    
5 · unknown 与 never：两个极端类型

    
unknown = 任意值但不许直接用（逼你证明）；never = 不可能是任何值（收窄的尽头）。一个是外部数据的正确入口，一个是重构安全的守护神。

    
本节目标：能为外部数据写出完整的 unknown 收窄链，并用 never 让漏写的分支在编译期暴露。


    
5.1 unknown：诚实的 any

    
any 是「检查器闭嘴」，而且传染（初识 TypeScript 的 3307 案例：any 的数据一路放行，运行时算出错的值）。unknown 是「我知道我不知道」：什么值都能装进去，但想用它，必须先收窄证明类型。赋值方向一表看清：

    

      
操作anyunknown

      
任何值 → 赋给它✓✓

      
它 → 赋给具体类型 / 直接使用✓（静默放行，错的也过）✗ 编译期拦下，必须先收窄

      
传染性用它的表达式跟着变 any不传染，收窄后就是具体类型

    

    

    
收窄链逐层看：① typeof data === 'object' 排除原始值；② data !== null 必不可少——typeof null === 'object' 的历史 bug（第 3 节埋的雷在这炸）；③ 'port' in data 证明键存在，但 in 之后取出的属性仍是 unknown，要单独再收窄一次。


    
    
陷阱：JSON.parse() 的返回类型是 any 不是 unknown——直接 const data = JSON.parse(s) 拿到的是 any（传染入口）。要 const data: unknown = JSON.parse(s) 显式改标，防线才真正立起来。


    
5.2 never：空集，收窄的尽头

    
never 表示「不可能是任何值」，三种出场：①穷尽检查（本节主角）；②永不返回的函数（直接 throw 或 while (true)）；③收窄到互相矛盾（string & number）。推导穷尽检查只要三步：

    
    
      
  1. switch 覆盖了联合的全部成员 → default 分支不可达 → 那里 s 的类型是 never；
    2. 
      
  2. const _exhaustive: never = s; 把 never 赋给 never，安然无恙（这行成了「我承诺全覆盖」的声明）；
    3. 
      
  3. 某天联合新增成员 Squiggle 而你忘了写 case → Squiggle 流到 default → s 变成 Squiggle → 塞不进 never → TS2322 当场报错，精确到行和列。
    4. 
    

    

    
一句话：改类型定义（加一个成员），编译器替你找出全项目所有「该改而没改」的 switch——把「新增形状」从提心吊胆变成例行公事，这是判别联合 + never 的组合拳，也是重构安全感的来源。

    

    
本节记住：unknown 要求先证明再使用；never 用来表达不可能，把漏处理的联合成员留在 default 时就会变成可检查的编译错误。

  


  
  

    
6 · 常见误区

    

      
误区真相纠正

      
联合类型能直接用两边的方法只能用共有成员，其余要收窄typeof / 判别联合，见第 3/4 节

      
if (x) 收窄 = 排除 null 就够了运行时还滤掉 ''、0、NaN 等全部 8 个 falsy区分「类型层排除」和「运行时排除」；要精确用 ===

      
typeof x === 'object' 就当对象用null 的 typeof 也是 'object'再补 && x !== null（第 5 节收窄链第②层）

      
外部数据标个接口类型就安全了标注是「担保」不是「验证」入口用 unknown，收窄/校验后再进业务

      
JSON.parse 之后类型是 unknown返回 any，正在传染显式 : unknown 改标再收窄

      
枚举用 number（1/2/3）当 kind数字判别照样工作，但可读性差、日志里对不上kind 用字符串字面量：'circle' | 'square'

      
switch 写完 default: break 就完了错过穷尽检查的保护default 里放 const _check: never = s

9 · 闭卷回忆、迁移与配套文件

    
先不看前文作答，再展开核对。能滚到页尾不等于学会，能独立回忆和迁移才是本页的完成标准。

    

      
1. 为什么联合类型未收窄前只能调用共有成员？
因为编译器必须保证代码对联合中的每一种可能都成立。独有成员需要先通过控制流判断证明当前值的类型，见第 2、3 节。

      
2. if (x) 的类型层效果和运行时效果有什么不同？
对普通 string、number 等宽类型，类型层不会得到「非空字符串」或「非零数字」；运行时却会过滤全部 falsy 值。需要精确排除某个值时使用相等性判断。

      
3. 外部 JSON 数据为什么应该标成 unknown，而不是接口或 any？
接口标注只是开发者担保，any 会关闭检查并传染；unknown 承认入口数据尚未验证，迫使代码逐层收窄，见第 5 节。

      
4. 判别联合与 never 怎样在重构时配合？
新增联合成员却漏写 case 时，新成员会进入 default，使 default 中的值不再是 never，赋给 never 的穷尽检查随即报 TS2322。
