### 1.

```text
true    // == 隐式转换：'5' 转数字 5
false   // === 类型不同直接不等
true    // 特例：null 与 undefined 仅彼此宽松相等
false   // null 不做任何转换，只与 undefined 相等
false   // NaN 与任何值（包括自己）都不等
```

### 2.

- `undefined`：**系统口径**——"从未赋值/不存在"（声明未赋值、函数无 return、属性不存在）；
- `null`：**程序员口径**——"主动置空"，显式写 `x = null`；
- `typeof null === 'object'`：1995 年 JS 首版实现中类型标签位的历史 bug，值恰好与对象标签相同；为保持向后兼容（大量老代码依赖这个行为）至今不能修。

### 3.

输出顺序：`开始 → 结束 → Promise → 定时器`。

理由：同步代码（开始、结束）先执行到底；栈空后先**清空微任务队列**（Promise）；然后才取**一个宏任务**（setTimeout 的回调，0ms 也只保证"至少"，且永远排在微任务之后）。

### 4.

原因：`const show = user.greet` 把方法从对象上**拆下来**，`setTimeout(show, 1000)` 相当于裸调用 `show()`——this 由"怎么调用"决定，裸调用的 this 是 undefined，访问 `this.name` 报错。

修复（任两种）：
- 闭包包一层：`setTimeout(() => user.greet(), 1000);`（箭头函数不绑 this，用外层的 user）
- 永久绑定：`setTimeout(user.greet.bind(user), 1000);`
- 临时指定：`setTimeout(() => show.call(user), 1000);`（call 是单次，这里等价）

### 5.

- `arr.push(4)` **合法**：const 锁的是"变量到数组的绑定"（不能重新赋值），不锁数组内容——类比 Java 的 `final List` 仍可 add；
- `arr = [5]` **报错** `TypeError: Assignment to constant variable`：重新赋值改变了绑定本身。

### 6.

输出：`A F B D C E`（本机 Node 18.20.4 实测）。

推演：`work()` 同步执行到 `await` → 输出 A；await 的 Promise 已解决，**"恢复 work（B 及之后）"此刻就入微任务队列**；回到脚本，`.then(D)` 注册 → D 入队（晚于恢复 work）；输出 F。此刻队列：[恢复work, D]。清队列：恢复 work → 输出 B，work 完成 → C 的回调排**队尾** → [D, C回调]；执行 D → E 排队尾 → [C回调, E]；执行 C → 执行 E。两条规律都在里面：谁先入队谁先执行（B 在 D 前）；完成时新任务排队尾（C 在 E 前）。对照互动演示「事件循环调度器」场景三——示例 04 实测输出里"3"排在"then1"之前、"4"排在"then2"之前，是同一条规律。

### 7.

bug 在 `backup.db.host = 'prod-server'`：`{ ...config }` 是**浅拷贝**，只复制第一层；嵌套的 `db` 对象在两边仍是同一个引用，改"备份"的嵌套字段直接改到了原始对象。

修复：`const backup = structuredClone(config);`（深拷贝，所有层级彻底分离）。

### 8.

```js
const total = orders
  .filter((o) => o.paid)
  .map((o) => o.amount)
  .reduce((acc, n) => acc + n, 0);
console.log(total);   // 320
```

对照 Java Stream：`filter` ↔ `filter`、`map` ↔ `map`、`reduce(初值, 累加器)` ↔ `reduce(0, Integer::sum)`。差别：JS 数组方法每步**立即**求值。

### 9.

结论：JS 只有一个线程执行代码，但"等待型任务"（网络、定时器、文件 IO）交给运行时（浏览器/Node 的 libuv）处理；完成后回调进入任务队列，JS 线程空了才取出来执行。同一时刻只有一段 JS 在跑，没有并发竞争，所以也不需要锁。

为什么：等待 IO 不消耗 CPU，无需为"等"专门开线程；浏览器环境里多线程操作 DOM 会带来加锁复杂度，单线程是设计取舍。

常见追问：计算密集型怎么办（Web Worker / Node 的 worker_threads / 子进程，真并行但不共享 DOM 和主状态）；同步死循环会怎样（调用栈永远不空，事件循环停转——所有定时器、请求回调、页面渲染全部卡死，相当于 Java 里把唯一的线程 sleep 死）。
