# 哈希表

## 学习目标

- 理解哈希函数"把键变成数组下标"的核心思想，以及 O(1) 查找的来源。
- 掌握链地址法处理哈希冲突的机制，能手写一个简易哈希表。
- 理解负载因子、自动扩容（rehash）的作用与代价。
- 明白为什么哈希表的键必须可哈希（不可变）。

**前置知识**：[数组](../数组/)（哈希表的底层就是数组 + 哈希函数）、[链表](../链表/)（冲突链就是单链表）。
**适用范围**：所有语言通用；示例语言为 Python。

---

## 一、哈希表解决什么问题

[数组](../数组/)按下标访问是 O(1)，但按"值"查找是 O(n)。哈希表的做法是：**用一个哈希函数把键（如 `"alice"`）换算成数组下标，把键值对存进对应的格子（桶）**。查找时再做一次同样的换算，一步跳到目标桶——把"按键查找"也做到接近 O(1)。它是 `dict`、`HashMap`、`map`、`unordered_map` 背后的同一思想，也是工程中出场率最高的数据结构之一。

## 二、核心原理

### 2.1 哈希函数：键 → 桶下标

流程分两步：

```text
键 "apple" ──hash()──> 一个大整数 ──% 桶数──> 桶下标
```

- 好的哈希函数要求：**同一个键每次算出同一个结果**（否则存进去就找不回来），且不同键尽量散开。
- 示例手写表采用多项式哈希 `h = h*31 + 字符编码`：比"字符编码求和"散得更均匀（求和会让 `abc` 和 `cba` 撞车）。

### 2.2 哈希冲突与链地址法

桶数有限、键无穷多，两个键落进同一个桶不可避免（鸽巢原理），这就是**哈希冲突**。**链地址法**：每个桶不是一格，而是一条 (键, 值) 对组成的列表（本质是[链表](../链表/)），冲突的元素在桶内排队：

```text
桶0: (空)
桶1: [('cherry', 2)]
桶2: [('apple', 3)]
桶3: (空)
桶4: [('elderberry', 1), ('fig', 9)]   ← 两个键哈希后同落桶 4：冲突，挂成链
桶5: [('banana', 5)]
```

查找 = 先 O(1) 定位桶，再在桶内逐个比对键。桶内链越短越接近 O(1)；若所有键挤进同一个桶，就退化成 O(n)——所以控制"散得开"是关键。

另一种主流方案是**开放寻址法**（冲突后按规则探测下一个空位），Python 的 `dict` 用的就是它的变体。

### 2.3 负载因子与自动扩容

**负载因子 = 元素个数 / 桶数**，衡量拥挤程度。超过阈值（示例取 0.75，也是 Java `HashMap` 的默认值）就**把桶数翻倍，并把所有元素重新哈希到新桶（rehash）**：

- 好处：桶多了，链变短，后续查找更接近 O(1)。示例第 3 段里 a~h 扩容到 16 个桶后，8 个键恰好一桶一个。
- 代价：扩容那一刻要搬迁全部元素，是一次 O(n) 的集中开销——与动态数组扩容同理，均摊后单次插入仍是 O(1)。

### 2.4 键必须可哈希

哈希表的正确性依赖"键的哈希值终身不变"。列表这样的可变对象放进桶后再修改内容，哈希值就变了，永远找不回原来存的位置。所以 Python 直接规定**可变类型不可哈希**（`hash([1,2])` 抛 `TypeError`），字符串、数字、元组等不可变类型才能做键。需要"列表状"的键时，先转成元组。

### 2.5 复杂度速查

| 操作 | 平均 | 最坏（全部冲突挤一桶） |
| --- | --- | --- |
| put / get / remove | O(1) | O(n) |
| 扩容触发的那次 put | O(n)（均摊 O(1)） | — |

示例文件：`示例代码.py`（与下述段落编号一一对应）

**第 1 段：哈希函数**。用内置 `hash()` 观察：两次 `hash("apple")` 结果相同（同键同哈希），`% 4` 折算下标。注释说明每次运行程序字符串哈希值可能不同（Python 默认加盐防哈希碰撞攻击），因此第 2 段的手写表改用自己稳定的多项式哈希，保证输出可复现。

**第 2 段：SimpleHashTable**。`_index` 定位桶；`put` 先在桶内找同键则更新（一键一值），否则追加；`get`/`remove` 在桶内逐键比对，找不到抛 `KeyError`（与 `dict` 行为一致）。`debug_view()` 打印全部桶，可以看到 `elderberry` 和 `fig` 的冲突链。

**第 3 段：自动扩容**。容量 4 逐个插入 a~h，在 `'d'`（负载因子 1.0 > 0.75）和 `'g'`（0.875 > 0.75）两处触发翻倍 + rehash，扩容后 8 个键均匀落进 16 个桶。

**第 4 段：可哈希性**。`hash([1, 2])` 抛 `TypeError`；元组可以；用元组做键查 dict 的实例。

**第 5 段：dict 对照**。插入、更新、`pop`、`in`、`get(默认值)`——日常用的就是哈希表的标准形态。

## 四、常见误区与边界条件

| 误区 / 边界 | 说明 |
| --- | --- |
| 以为哈希表是严格 O(1) | 平均 O(1)，最坏 O(n)；工程上靠好哈希函数 + 及时扩容把最坏情况压到几乎不出现 |
| 用可变对象做键 | 直接 `TypeError`；元组嵌套列表（如 `(1, [2])`）同样不可哈希 |
| 以为哈希值是"内容指纹"跨机器稳定 | Python 的 `hash()` 对字符串加盐，跨进程/机器不一定相同；持久化去重应使用 md5/sha 等摘要算法 |
| 忘了同键是"更新"不是"新增" | `put` 已存在的键会覆盖旧值，`dict[k]=v` 同理 |
| 迭代时修改表 | 扩容/删除改变内部结构，迭代中插入或删除可能漏项或抛 `RuntimeError` |

**排查思路**："存进去查不到"先检查键类型是否可哈希、前后是否同一个值（`1 == 1.0 == True` 在 Python 里哈希相同，混用 int/bool/str 键容易踩坑）；性能异常时怀疑负载因子过高未扩容或哈希函数分布不均。

## 五、实际应用与取舍

- **适合**：按键存取、判重（集合）、计数统计、缓存（LRU 的定位层）、数据库索引的内存形态之一。
- **不适合**：范围查询/有序遍历（需要有序结构，如[二叉搜索树](../二叉搜索树/)）、极小数据量（直接线性查找更省）、需要稳定内存布局的场景。
- 语言对照：Python `dict`/`set`、Java `HashMap`/`ConcurrentHashMap`、Go `map`、C++ `unordered_map`、Redis 的字典底层。

## 六、可继续学习的方向

- 开放寻址法与 Python `dict` 的紧凑布局演进。
- [二叉搜索树](../二叉搜索树/)：用有序性换取范围查询能力，与哈希表互补。
- 一致性哈希（分布式缓存分片）。
- 布隆过滤器：用极小内存判断"可能存在/一定不存在"。
