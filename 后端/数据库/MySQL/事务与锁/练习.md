## 进阶题

<summary>参考答案（先自己做完再看）</summary>

### 1.

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 会 | 会 | 会 |
| READ COMMITTED | 防住 | 会 | 会 |
| **REPEATABLE-READ（默认）** | 防住 | 防住 | 基本防住 |
| SERIALIZABLE | 防住 | 防住 | 防住（读也加锁） |

那句话：**RC 每条查询都生成新的 ReadView，RR 只在事务内第一次快照读时生成、之后复用同一个**——其余机制完全相同。

### 2.

当前读 = 读最新已提交版本并加锁：`UPDATE`、`DELETE`、`INSERT`、`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`（旧写法 LOCK IN SHARE MODE）。

B4 仍是 1000 的原因：普通 SELECT 走 **MVCC 快照**，而快照在 B1 第一次普通读时就定了。B3 的当前读只读最新版、加行锁，**并不会替换事务的 ReadView**——"FOR UPDATE 之后快照就新了"是高频误区（对照演示4 的 B3=1500、B4=1000）。

### 3.

- ① **阻塞，超时后报 1205**：RR 下等值未命中的当前读会锁住目标"本来该在"的间隙 (5,10)——间隙锁唯一的使命就是拦 INSERT，id=7 正好要插进这个位置；
- ② **畅通**：间隙锁锁的是 (5,10)，(1,5) 没被锁，id=3 随便插。

关键认知：**锁可以加在"不存在的行"上**——锁的是位置不是行。这也是"RR 用间隙锁防当前读幻读"的机制。可以在互动演示的「锁范围判定器」里选"等值未命中"复现这个判定。

### 4.

- **1205 锁等待超时**：我要的锁被别人拿着，等了 `innodb_lock_wait_timeout`（默认 50 秒）还没等到——对方可能还活着，只是慢（典型：长事务）。第一步：查长事务 `SELECT * FROM information_schema.INNODB_TRX;`，九成是"开了事务没提交"的连接；
- **1213 死锁**：互相等待成环，InnoDB 死锁检测**立即**发现并主动回滚代价小的一方。第一步：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 段（两个事务各持哪把锁、两条 SQL 一目了然），应用层对 1213 做有限重试。

### 5.

```sql
UPDATE account SET balance = balance - 500
WHERE id = 1 AND balance >= 500;
```

余额不足时 WHERE 不满足，**影响行数为 0**——调用方检查 affected rows：0 即失败（余额不足），1 即成功。一条语句完成"读-判-写"，天然原子（当前读 + 行锁），不需要先 SELECT 再 UPDATE 的两步（两步会被并发打穿）。

### 6.

```sql
-- 会话A                          -- 会话B
BEGIN;                            BEGIN;
UPDATE account SET balance=balance+1 WHERE id=1;
                                  UPDATE account SET balance=balance+1 WHERE id=2;
UPDATE account SET balance=balance+1 WHERE id=2;  -- 阻塞：等B
                                  UPDATE account SET balance=balance+1 WHERE id=1;  -- 阻塞：等A → 环！
```

发现方式：InnoDB 的**死锁检测**（`innodb_deadlock_detect=ON`，默认）在每次加锁受阻时检查等待图是否成环——环一闭合立刻回滚代价小（undo 量少）的一方，不等超时（对照演示6：B 立即收到 1213，A 照常提交）。

应用层：捕获 1213（死锁是暂时性错误），**小睡随机几十毫秒后重试**整个事务（重试上限 2~3 次）；预防靠统一加锁顺序（如都按主键升序访问）。

### 7.

- 最新版 `trx_id=100`：落在 `[min_trx_id, next_trx_id)` 且在 `m_ids=[100]` 里 → 生成快照时还活跃、**不可见**（它也不是 creator=105）；
- 沿 `roll_pointer` 找上一版 `trx_id=90`：`90 < min_trx_id=100` → 生成快照前已提交 → **可见**；
- 所以 B 读到 `trx_id=90` 那个版本的值。这正是演示3/演示4 里"别人提交了我还读旧值"的内部过程。

### 8.

根因：**锁要持有到事务结束（严格 2PL）**。HTTP 风控调用（比如耗时 500ms）发生在 BEGIN 和 COMMIT 之间，期间 UPDATE 拿到的行锁一直不放；高峰期其他请求排队等锁，超过 `innodb_lock_wait_timeout` 就 1205。

改法（至少两条）：
1. **把外部调用挪出事务**：先查数据 → 退出事务去调风控 → 再开短事务做更新；
2. **缩短事务**：事务里只留数据库操作，去掉 sleep/RPC/发消息等一切慢操作；
3. 配套：调小 `innodb_lock_wait_timeout` 让失败快速暴露 + 应用重试；监控 `INNODB_TRX` 里的长事务，排查句式：

```sql
SELECT trx_id, trx_started,
       TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) AS 持续秒, trx_rows_locked
FROM information_schema.INNODB_TRX ORDER BY 持续秒 DESC;
```

### 9.

```sql
BEGIN;
UPDATE account SET balance = balance - 300 WHERE id = 1;      -- 扣款成功
SAVEPOINT after_pay;
UPDATE stock SET n = n - 1 WHERE sku = 'X' AND n > 0;         -- 影响行数可能为 0
-- 应用层判断：影响行数 = 0 → 库存不足，只回滚这一步：
ROLLBACK TO after_pay;    -- 撤销库存操作，扣款保留，事务继续
COMMIT;                   -- 提交扣款
```

`ROLLBACK TO sp1` **不会结束事务**——它只撤销存档点之后的语句，事务照常进行，仍然要最终 COMMIT / ROLLBACK（对照演示9：ROLLBACK TO sp1 后还能继续读，最后 ROLLBACK 撤销了包括扣款在内的一切）。
