# 事务与锁：ACID、隔离级别、MVCC、行锁/间隙锁/死锁

> 学习目标：搞懂"事务保证什么"（ACID 各自靠什么实现）、"并发到底会出什么错"（脏读/不可重复读/幻读）、"InnoDB 怎么又快又稳地解决它们"（MVCC + 锁），并亲眼看到 1205 锁等待、1213 死锁、间隙锁拦截 INSERT 的现场。

## 一、解决什么问题

转账场景，两个并发会话同时操作 Alice/Bob 的账户（初始各 1000）：

1. **A 扣了 Alice 的钱还没提交，B 就读到了中间值**——A 一回滚，B 拿着 1500 去做后续计算，全错（**脏读**）；
2. **B 一个事务里两次读同一行，值变了**——第一次读 1000 做校验，第二次读已经 1500，校验了个寂寞（**不可重复读**）；
3. **B 两次统计行数，凭空多了一行**——按"共 2 人"做的业务判断，下一刻变 3 人（**幻读**）；
4. **两个事务互相攥着对方要的行**——谁也不撒手，永远等下去（**死锁**）；
5. **最粗暴的解法**：干脆全表一把锁、一次只让一个事务动——安全是安全了，并发能力归零。

本篇的主线：**隔离级别决定"错到什么程度可以容忍"，MVCC 负责"读不阻塞写"，锁负责"写不冲突"**——三者合起来，就是既安全又高并发的 InnoDB。

## 二、核心原理

### 2.1 ACID：四个保证，四种实现

| 保证 | 含义 | InnoDB 靠什么 |
| --- | --- | --- |
| **A**tomicity 原子性 | 事务内的操作要么全成、要么全不算 | **undo log**（回滚日志）：每改一行记一份"反向操作"，ROLLBACK 时倒着放回去 |
| **C**onsistency 一致性 | 数据从一个合法状态到另一个合法状态 | A+I+D 打底，再加约束（主键/唯一/外键/CHECK）与应用层校验——C 是**目的**，其他三个是手段 |
| **I**solation 隔离性 | 并发事务互不干扰 | **锁 + MVCC**（本篇主角） |
| **D**urability 持久性 | 提交了就掉电也不丢 | **redo log**（重做日志，WAL 先写日志再改数据页）+ 双一配置（`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`） |

记忆锚点：**回滚靠 undo，崩溃恢复靠 redo，并发靠锁和 MVCC**。（undo/redo 的日志细节属于"日志与恢复"话题，本篇只在需要时提及。）

### 2.2 四个隔离级别：一张矩阵 + 一个选择

并发问题按严重程度排：脏读 > 不可重复读 > 幻读。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED 读未提交 | **会** | 会 | 会 | 啥也不防，直接读最新数据 |
| READ COMMITTED 读已提交（RC） | 防住 | **会** | 会 | 每次查询建新 ReadView（快照） |
| **REPEATABLE READ 可重复读（RR，默认）** | 防住 | 防住 | **基本防住**（见 2.5） | 事务开始后的第一次查询建 ReadView，之后复用 |
| SERIALIZABLE 串行化 | 防住 | 防住 | 防住 | 普通读也自动加锁，读写互斥，性能差 |

切换方式：`SET SESSION transaction_isolation = 'REPEATABLE-READ';`（还有 GLOBAL 级别）。默认 RR；互联网公司不少改用 RC（没有间隙锁、锁冲突少，幻读靠业务规避）。

### 2.3 MVCC：多版本并发控制——读为什么不加锁

InnoDB 的行上不只存"当前值"：每次修改都把**旧版本**留在 **undo log 版本链**里（` trx_id`改它的事务号，`roll_pointer` 指向上一版）。查询时，拿一份 **ReadView**（快照）沿版本链挑"我该看见的那一版"：

ReadView 核心是四个数：`m_ids`（生成快照时还活跃的事务号列表）、`min_trx_id`（活跃里最小）、`next_trx_id`（下一个将分配的号）、`creator_trx_id`（自己的号）。判断某版本可见性的规则：

1. 版本的 `trx_id == creator_trx_id` → 自己改的，可见；
2. `trx_id < min_trx_id` → 生成快照前已提交，可见；
3. `trx_id >= next_trx_id` → 生成快照**之后**才开始的事务，不可见；
4. `min_trx_id <= trx_id < next_trx_id` → 看 `trx_id` 在不在 `m_ids` 里：在（当时还活跃）→ 不可见；不在（当时已提交）→ 可见。

不可见就顺着 `roll_pointer` 找上一版再判，直到找到可见版本或链尾。

**RC 与 RR 的全部区别就在这里**：RC **每条查询**生成新 ReadView（所以能看见别人新提交的——不可重复读）；RR **只在第一次查询时生成**，整个事务复用（所以看见的永远是开事务时的世界——可重复读）。

### 2.4 快照读 vs 当前读：同一张表两种"读"

| 类型 | 语句 | 读什么 | 加锁吗 |
| --- | --- | --- | --- |
| **快照读** | 普通 `SELECT` | MVCC 版本链里的可见版本 | 不加锁（读不阻塞写、写不阻塞读） |
| **当前读** | `UPDATE` / `DELETE` / `INSERT` | **最新已提交版本**（必须，否则改错基础） | 加行锁 |
| **当前读** | `SELECT ... FOR UPDATE` | 最新已提交版本 | 排他行锁 |
| **当前读** | `SELECT ... LOCK IN SHARE MODE`（8.0.5+ 可写 `FOR SHARE`） | 最新已提交版本 | 共享行锁 |

演示4 的 B3 就是铁证：同一个事务里，普通读拿到 1000（快照），`FOR UPDATE` 拿到 1500（最新）——**"我改的这条"永远是最新版，"我看的这条"可能是旧版**。

### 2.5 锁家族：记录锁、间隙锁、Next-Key Lock

行锁加在**索引记录**上（这是关键伏笔，见第四节误区）：

| 锁 | 锁什么 | 什么时候出现 |
| --- | --- | --- |
| **记录锁 Record Lock** | 一条索引记录本身 | RC/RR 的等值命中 |
| **间隙锁 Gap Lock** | 两条记录**之间**的开区间（不含记录） | 仅 RR；`FOR UPDATE` 等当前读的范围内 |
| **Next-Key Lock** | 记录锁 + 前面的间隙（左开右闭） | RR 范围当前读的默认形态 |
| 意向锁（IS/IX） | 表级"声明"：表里有行被锁了 | 行锁的自动伴生，让"锁表"不用逐行检查 |

**RR 怎么"基本防住"幻读**：快照读靠 MVCC（第二次读还是旧快照，新行天然不可见）；当前读靠间隙锁——把范围内所有间隙锁住，别人根本插不进来（演示7：RR 下 `BETWEEN 2 AND 9 FOR UPDATE` 之后 INSERT id=7 直接 1205）。所以"RR 完全防住幻读"不对——先快照读再当前读的混用场景仍可能"看见"幻影行；RC 则完全放行（演示8 终态 1/5/7/10）。

### 2.6 死锁与锁等待：1205 和 1213

- **锁等待（1205）**：我要的行被别人锁着。等 `innodb_lock_wait_timeout`（默认 50 秒，演示5 里 SET 成 3 秒）后超时报 `ERROR 1205 Lock wait timeout`——**等得起，超时只是我自己失败**；
- **死锁（1213）**：A 攥着行1 等行2，B 攥着行2 等行1，互相等到天荒地老。InnoDB **死锁检测**（`innodb_deadlock_detect` 默认开）立即发现环，挑一个"回滚代价小"（undo 量少）的事务牺牲掉：它收到 `ERROR 1213 Deadlock found when trying to get lock`，另一个照常成功（演示6：B 被牺牲，A 提交成功）。

## 三、示例逐段讲解

配套 [示例代码/](示例代码/)：`00_建库与数据.sql` 建 `learn_tx` 库（account 两行：Alice/Bob 各 1000；t_gap 稀疏主键 1/5/10）。演示 1~8 都是成对的会话 A/B 脚本，靠 `SELECT SLEEP()` 把两条时间线对齐，`运行演示.ps1` 同时启动两个 mysql 连接真实并发执行。

### 演示1：脏读（RU）——读到别人还没提交的值

时间线：A（RU）改 Alice +500 未提交 → B 读到 **1500** → A ROLLBACK → B 再读 **1000**。B 第一次拿到的 1500 从未真实存在过——这就是 RU 被称为"裸奔"的原因。

### 演示2：不可重复读（RC）——一个事务里两次读不一样

B 开事务读 balance=**1000**、COUNT=**2** → A 提交修改（Alice +500）并插入新行 Carol → B 同一事务内再读：**1500**、**3**。RC 防住了脏读（B 看到的都是 A **已提交**的），但"同一事务内视角漂移"仍会发生。

### 演示3：可重复读（RR）——同样时间线，结果纹丝不动

RR 下重复演示2 的时间线：B 两次读都是 **1000**、**2**；COMMIT 之后新事务、新快照，才看到新数据（实测 COUNT=**3**）。RC 与 RR 的差别只有一处：ReadView 建一次还是每查询建一次（2.3）。

### 演示4：MVCC 快照读 vs 当前读（本篇最关键的实验）

RR 下，B 先普通读建立快照（B1=**1000**）→ A 提交 +500 → B 继续：

| 步骤 | 语句 | 结果 | 解释 |
| --- | --- | --- | --- |
| B2 | 普通 SELECT | **1000** | 快照读：ReadView 没换，A 的修改不可见 |
| B3 | SELECT ... FOR UPDATE | **1500** | 当前读：读最新版本并加行锁 |
| B4 | 之后再普通 SELECT | **1000** | 快照**并没有**被 B3 换掉——"当前读改快照"是高频误解 |
| B5 | COMMIT 后普通 SELECT | **1500** | 新事务新快照，看见已提交的最新值 |

一行四读、三种答案，MVCC 的全部要点都在这张表里。

### 演示5：行锁与锁等待——1205 现场

A 锁住 id=1 不提交 → B 先更新 id=2：**秒过**（锁的是不同行）→ B 更新 id=1：卡 3 秒后 `ERROR 1205 Lock wait timeout`。行锁粒度到单行，互不相干各行其是。

### 演示6：死锁——1213 现场

A：锁 id=1，睡 3 秒，再要 id=2；B：锁 id=2，睡 3 秒，再要 id=1。双方在各自第 2 步互相等待——InnoDB 立刻检测到环：**B 收到 `ERROR 1213`**（被选为牺牲品），**A 毫发无损继续执行并 COMMIT 成功**。

### 演示7/8：间隙锁——RR 拦 INSERT，RC 放行

t_gap 现有主键 1、5、10。A 执行 `SELECT * FROM t_gap WHERE id BETWEEN 2 AND 9 FOR UPDATE` 锁住间隙（2,5）(5,10) → B INSERT id=7：

- RR（演示7）：INSERT 被间隙锁挡住 → 3 秒后 `ERROR 1205`；
- RC（演示8）：没有间隙锁，INSERT **成功**，终态 1/5/7/10。

同一个操作，隔离级别不同、命运不同——"RC 并发性能好"的代价就在这。

### 演示9：SAVEPOINT——事务里的"存档点"

单会话：1000 → 扣 300 → 存档 sp1 → 再扣 700（余额 0）→ `ROLLBACK TO sp1` 回到 **700**（只撤销存档之后的部分）→ `ROLLBACK` 回到 **1000**。事务不是只有"全成全败"，可以局部回滚（注意：ROLLBACK TO 后事务继续，还需最终 COMMIT/ROLLBACK）。

## 四、常见误区

| 误区 | 实际 | 本例现场 |
| --- | --- | --- |
| "RR 完全防住幻读" | 快照读+当前读混用时仍可能看到幻影行；"基本防住" | 2.5、演示4 B4 |
| "FOR UPDATE 之后普通读也是新值" | 快照在第一次普通读就定了，当前读**不换快照** | 演示4 B4=1000 |
| "BEGIN 就建立了快照" | RR 的快照在**第一次快照读**时建立（`START TRANSACTION WITH CONSISTENT SNAPSHOT` 才是立即） | 演示3/4 的时间线设计 |
| "行锁锁的是'行'" | 行锁加在**索引记录**上；WHERE 列没索引 → 沿聚簇索引全扫，把**所有**记录都锁上 | 演示5 的伏笔；索引篇延伸 |
| "1205 和 1213 是一回事" | 1205 等锁超时（对方还活着）；1213 死锁（InnoDB 主动牺牲我） | 演示5 vs 演示6 |
| "死锁是 Bug，会被回滚所有事务" | 只回滚**牺牲的那一个**，另一方正常成功 | 演示6 A 存活 |
| "COMMIT 就是写盘" | COMMIT 保证 redo 落盘（持久性）；数据页可以晚点刷 | 2.1 |
| "SERIALIZABLE 最安全，用它" | 普通读也加锁，并发吞吐骤降；默认 RR 足矣 | 2.2 |

**排查思路（遇到锁问题）**：① 看错误码：1213 死锁 → `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段，看两个事务各持哪把锁；1205 等待 → 找长事务（`information_schema.INNODB_TRX`），九成是"开了事务没提交"的连接；② 事务要短，别在事务里 sleep/调外部接口；③ 多行更新按统一顺序（如按主键升序）访问，环就成不了。

## 五、八股追问

**Q1：ACID 分别怎么实现的？**
结论：A 靠 undo log（反向操作回滚），D 靠 redo log + WAL（先写日志后改页，提交即落盘），I 靠锁 + MVCC，C 是前三者 + 约束共同达成的目的。
为什么：undo/redo 是"性能与安全的账本"——直接随机写数据页太慢且不安全，先顺序写日志，崩溃后按日志重放（redo）或撤销（undo）。
常见追问：*redo 和 undo 的区别？*——redo 记"做了什么"用于重放恢复；undo 记"怎么撤销"用于回滚与 MVCC 版本链。*双一是什么？*——`innodb_flush_log_at_trx_commit=1`（每次提交刷 redo）与 `sync_binlog=1`（每次提交刷 binlog），保证掉电不丢已提交事务。

**Q2：四个隔离级别分别解决什么问题？默认哪个？**
结论：RU 什么都不防；RC 防脏读；RR（默认）再防不可重复读、基本防幻读；SERIALIZABLE 全防但读加锁。
为什么：隔离越强，并发能力越弱——级别是"正确性 vs 并发吞吐"的旋钮。RR 是 MySQL 的折中。
常见追问：*怎么切换？*——`SET [GLOBAL|SESSION] transaction_isolation='READ-COMMITTED'`。*为什么很多大厂用 RC？*——没有间隙锁、锁范围小、死锁少；不可重复读/幻读交给业务（如乐观锁、唯一约束）兜底。

**Q3：讲讲 MVCC 的实现？ReadView 的判断规则？**
结论：行上有多版本（undo 版本链 + trx_id + roll_pointer），读时拿 ReadView 按四条规则挑可见版本；RC 每查询一个 ReadView，RR 一个事务一个。
为什么：并发读不该被写阻塞——读旧版本即可满足一致性，读写两不误。
常见追问：*不可见怎么办？*——沿 roll_pointer 找上一版继续判，直到可见或链尾。*RR 下改了某行再读，看到的是？*——自己改的（trx_id==creator）可见，读到自己修改后的值。*MVCC 能防幻读吗？*——快照读能（新行 trx_id 更大，不可见）；当前读防幻读靠间隙锁。

**Q4：什么是当前读和快照读？**
结论：普通 SELECT 是快照读（读 MVCC 可见版本，不加锁）；UPDATE/DELETE/INSERT、`FOR UPDATE`、`FOR SHARE` 是当前读（读最新已提交版本并加锁）。
为什么：修改必须基于最新值，否则会用旧基础算出新错值（丢失更新）。
常见追问：*RR 下 FOR UPDATE 读到的是？*——最新已提交值（演示4 B3=1500）。*怎么显式锁一行又不修改？*——`SELECT ... FOR UPDATE`（排他）/`FOR SHARE`（共享）。

**Q5：RR 是怎么防幻读的？**
结论：两条腿——快照读靠 MVCC（新插入行对旧 ReadView 不可见）；当前读靠 Next-Key Lock（记录+间隙）把范围封死，别人插不进来。
为什么："幻读"是**第二次读多出/少了行**；快照不变则看不见新行，间隙封死则新行进不来。
常见追问：*完全防住吗？*——不能 100%：事务先快照读、后当前读时，当前读可能"看见"别的事务新插的行（如 FOR UPDATE 查到快照里没有的行）；严格防幻读用 SERIALIZABLE 或加锁读+业务约束。*RC 为什么不防？*——没有间隙锁（演示7 vs 8），且 ReadView 每次重建。

**Q6：间隙锁和 Next-Key Lock 是什么？什么时候用？**
结论：间隙锁锁"两条索引记录之间的开区间"，只在 RR 存在；Next-Key = 记录锁+前间隙，是 RR 范围当前读的默认加锁单位（左开右闭区间）。
为什么：只锁已有记录拦不住"往空隙里插新行"，要防幻读必须连"还不存在的行"的位置一起锁。
常见追问：*等值命中唯一索引时也是 Next-Key 吗？*——退化成纯记录锁（唯一性已保证没有幻影）。*间隙锁之间冲突吗？*——不冲突（两个事务可以同时持有同一间隙的 Gap Lock，它只拦 INSERT）。*代价？*——锁范围变大、死锁概率升高，这是 RR 并发弱于 RC 的根源。

**Q7：什么是死锁？怎么排查和避免？**
结论：两个事务互相持有对方需要的锁形成环。InnoDB 默认开启死锁检测，回滚代价小的一方（ERROR 1213），另一方成功；也可等 `innodb_lock_wait_timeout` 超时。
为什么能主动发现：加锁时检测等待图（who-waits-for-whom）是否成环。
常见追问：*怎么查现场？*——`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段（两个事务、两条 SQL、各自持有/等待的锁）。*怎么预防？*——多行操作按固定顺序（如主键升序）、事务尽量短、索引建好避免锁放大、必要时拆小事务/用重试。*死锁能彻底消灭吗？*——只能降低概率；应用层对 1213 做重试是常规配套。

**Q8：什么是两阶段锁协议（2PL）？**
结论：事务分"扩展阶段"（只加锁）和"收缩阶段"（只放锁），锁在 COMMIT/ROLLBACK 时才统一释放；InnoDB 遵循严格 2PL。
为什么重要：它解释了"**锁要持有到事务结束**"——所以事务越长，持锁越久，并发越差；也解释了演示6：A 第一步的锁直到 COMMIT 才放，环才成立。
常见追问：*那 MVCC 和 2PL 矛盾吗？*——不矛盾：2PL 管"写写冲突"（锁），MVCC 额外解决了"读写冲突"（读旧版本），InnoDB = 2PL 写 + MVCC 读。*怎么利用 2PL 提高并发？*——把最热的行（如账户）的更新放到事务**最后**再做，持锁时间最短。

## 六、实际应用

- **转账模板**：`BEGIN; 扣款 UPDATE ... WHERE id=? AND balance>=?; 看影响行数; 入账 UPDATE ...; COMMIT/ROLLBACK`——靠"影响行数为 0 即失败"保证扣款不会扣成负数（练习.md 会让你写完整版）；
- **扣库存/抢名额**：`UPDATE stock SET n=n-1 WHERE id=? AND n>0` 一条当前读语句搞定原子判断，不需要"先 SELECT 再 UPDATE"两步（两步会被并发打穿）；
- **锁等待调参**：线上 `innodb_lock_wait_timeout` 常调小（如 5 秒）快速失败 + 应用重试，避免请求堆积；
- **死锁运维**：应用捕获 1213 做有限重试；巡检 `SHOW ENGINE INNODB STATUS`；批量任务按主键序处理；
- **长事务是万恶之源**：事务里调外部 HTTP/发消息 = 持锁等待外部系统；框架的 `@Transactional` 别包住大方法。查长事务：`SELECT * FROM information_schema.INNODB_TRX WHERE TIME_TO_SEC(TIMEDIFF(NOW(),trx_started))>10;`

## 七、延伸方向

- **redo/undo/binlog 三日志**与两阶段提交（内部 XA）——"日志与恢复"主题；
- **分布式事务**：2PC/TCC/SAGA/本地消息表（服务拆分后的转账怎么保一致）；
- **SERIALIZABLE 与间隙锁的极端场景**、`innodb_lock_wait_timeout`/`innodb_deadlock_detect` 调优；
- **MDL 元数据锁**（DDL 与 DML 的冲突，"改表把整站查堵死"事故的主角）；
- 乐观锁（版本号/CAS 思想）vs 悲观锁（FOR UPDATE）的选型——Spring/Redis 篇会重逢。
