## 一、解决什么问题

真实业务里的查询几乎从不只是"把一张表捞出来"：

- **数据分家存**：员工信息在 `emp`，部门名在 `dept`，想一起看就要 **JOIN**；
- **条件是"算出来的"**：找"高于本部门平均工资"的人，平均值得先查出来——**子查询**；
- **要的是报表不是明细**：每个部门几个人、平均多少——**GROUP BY**；要的是排名、累计、环比——**窗口函数**；
- **查询本身太长**：一层套一层的子查询没法读——**CTE（WITH）**；两个结果要拼在一起——**UNION**。

而这三类错误几乎每个写 SQL 的人都犯过：`mgr = NULL` 永远查不出东西；`LEFT JOIN` 后在 `WHERE` 里过滤右表，左连接悄悄退化成内连接；`NOT IN` 遇上含 NULL 的子查询返回空集还不报错。本文把这三颗雷和排雷方法一次讲清。

## 二、核心原理

### 2.1 一切的根基：SQL 的逻辑执行顺序

写 SQL 的顺序和执行顺序不一样。优化器实际怎么算不作数，**语义**上按这个顺序理解：

```
FROM / JOIN（含 ON） → WHERE → GROUP BY → HAVING → SELECT（含窗口函数）→ DISTINCT → ORDER BY → LIMIT
```

后面所有的"为什么"都从这里推：

| 疑问 | 答案（都来自执行顺序） |
| --- | --- |
| LEFT JOIN 的条件写 ON 还是 WHERE？ | ON 在连接时生效（决定怎么配对），WHERE 在连接后生效（过滤最终行） |
| WHERE 里为什么不能用聚合函数？ | WHERE 跑在 GROUP BY 之前，那时还没有"组" |
| WHERE 里为什么不能用 SELECT 起的别名？ | SELECT 在 WHERE 之后才执行（ORDER BY 可以用，因为更靠后） |
| 窗口函数为什么不能写在 WHERE 里？ | 窗口函数在 SELECT 阶段才算，WHERE 时还不存在（要套一层子查询） |

### 2.2 JOIN：按条件配对，类型决定"配不上怎么办"

JOIN 的本质：对两表的行做**组合**，保留满足连接条件的组合。

| 类型 | 语义 | 配不上的行 |
| --- | --- | --- |
| `INNER JOIN`（`JOIN`） | 只要两边都匹配的行 | 丢弃 |
| `LEFT JOIN` | 左表全保留，右边配不上补 NULL | 左表行保留 + NULL |
| `RIGHT JOIN` | 右表全保留，左边配不上补 NULL | 右表行保留 + NULL（等价于换位左连接） |
| 自连接 | 一张表当两张表用（如 emp.mgr → emp.empno） | 同 INNER/LEFT |
| 非等值连接 | 条件不必是 `=`，如 `BETWEEN` | 同 INNER |

**ON vs WHERE（左连接专属陷阱）**：`ON e.deptno = d.deptno AND e.sal > 2000` 是"按这两个条件**配对**"，配不上的左表行照样输出（右侧补 NULL）；而把 `e.sal > 2000` 挪到 WHERE，是连接完再过滤——补出来的 NULL 行过不了 `NULL > 2000`（结果是 UNKNOWN，不是 TRUE），整行被扔掉，**左连接名存实亡**。

### 2.3 子查询：查询里套查询

| 种类 | 形态 | 用法 |
| --- | --- | --- |
| 标量子查询 | 返回 1 行 1 列 | 当一个值用：`sal - (SELECT AVG(sal) FROM emp)` |
| 列子查询 | 返回 1 列 N 行 | 配 `IN` / `NOT IN` / `ANY` / `ALL` |
| 表子查询（派生表） | 返回一张临时表 | 当 FROM 的表用，必须起别名 |
| 相关子查询 | 子查询里引用外层列 | 外层每行都执行一次子查询，如"高于本部门平均" |

**IN 与 EXISTS 怎么选**：语义相同时看谁当"外表/内表"更划算——外表大、子查询结果小用 IN；外表小、内表大用 EXISTS。现代 MySQL 8 的优化器多数场景会把两者改写成同一种半连接计划，**写哪个都对，但 NOT IN 和 NOT EXISTS 语义有实质差异**：

```text
x NOT IN (a, b, NULL)
  =  x<>a AND x<>b AND x<>NULL      -- 最后一项是 UNKNOWN
  →  整个表达式永远凑不出 TRUE → 空集，且不报错！
```

所以**子查询列可能含 NULL 时，NOT IN 禁用，改写 NOT EXISTS**。

### 2.4 GROUP BY：分组即折叠

`GROUP BY deptno` 把同部门的行**折叠成一行**，SELECT 里只能出现：分组列（deptno）或聚合函数（COUNT/AVG/MAX/MIN/SUM）。

- **WHERE vs HAVING**：WHERE 过滤"行"（分组前），HAVING 过滤"组"（分组后，可用聚合结果）；
- **ONLY_FULL_GROUP_BY**（MySQL 5.7.5+ 默认开）：`SELECT deptno, ename ... GROUP BY deptno` 直接报 ERROR 1055——每组 5 个人的 ename 显示谁？老版本"随机挑一个"的结果没有意义，新版本把这种含糊拒之门外。想要"每组工资最高的人"，用窗口函数或相关子查询。

### 2.5 窗口函数：分组但不折叠（MySQL 8.0+）

```sql
函数(...) OVER (PARTITION BY 分区列 ORDER BY 排序列 [帧])
```

- **PARTITION BY** = "分教室"：每个区各自从 1 开始算；不写就是全区；
- **ORDER BY** 决定区内顺序，排名/累计都依赖它；
- **帧（frame）** 决定"当前行和哪些行参与计算"。`ORDER BY` 后默认 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`——**排序值相同的行算作"同位"一起算**（示例 5.3 里同一天入职的两人累计值相同，就是它）。

| 需求 | 函数 | 并列时 |
| --- | --- | --- |
| 硬排 1、2、3…（取 Top-1 不并列） | `ROW_NUMBER()` | 也分先后 |
| 体育式名次（1、2、2、4） | `RANK()` | 同名次，占号 |
| 紧凑名次（1、2、2、3） | `DENSE_RANK()` | 同名次，不占号 |
| 累计求和/移动平均 | `SUM/AVG + OVER(ORDER BY ...)` | RANGE 帧一起算 |
| 和上一行比（环比） | `LAG(col)` / `LEAD(col)` | — |

### 2.6 CTE 与 UNION

- **CTE（`WITH x AS (...)`）**：给中间结果起名字，可以引用多次；等于"先算一张临时表"，让长查询平铺直叙；
- **`UNION`**：两个结果按列拼起来，**去重**（有排序开销）；**`UNION ALL`**：不去重直接拼，确定无重复时优先用它。

### 2.7 NULL：三值逻辑

NULL 与任何值的比较结果不是 TRUE/FALSE，而是第三个值 **UNKNOWN**：

| 表达式 | 结果 |
| --- | --- |
| `NULL = NULL` | UNKNOWN（两个"没有值"不相等） |
| `0 = NULL` | UNKNOWN（不是 FALSE！所以 NOT (0=NULL) 也查不出） |
| `NULL IS NULL` | TRUE —— 判断 NULL 只能用 IS NULL / IS NOT NULL |
| `NULL <=> NULL` | TRUE（`<=>` 是 NULL 安全等号） |

UNKNOWN 参与逻辑运算：`TRUE AND UNKNOWN = UNKNOWN`、`FALSE AND UNKNOWN = FALSE`、`UNKNOWN OR TRUE = TRUE`。WHERE 只放行 TRUE，UNKNOWN 一律拦下。聚合函数与 NULL：`COUNT(列)` 跳过 NULL，`AVG/SUM/MAX/MIN` 忽略 NULL，`COUNT(*)` 数所有行。

## 三、示例逐段讲解

配套 [示例代码.sql](示例代码.sql)，共 8 节（0~7），本节挑关键点对照真实输出讲。

### 第 0 节：数据集（经典 scott 库）

14 名员工、4 个部门。三个"故意"：**40 号部门没有员工**（演 LEFT JOIN）、**KING 的 mgr 是 NULL**（演三值逻辑和 NOT IN 陷阱）、**两对同薪（3000/3000、1250/1250）与一对同日入职**（演排名并列与 RANGE 帧）。这套数据小到能心算，大到每个坑都有现场。

### 第 1 节：四种 JOIN（示例 1.1~1.5）

- 1.1 内连接 14 行——**40 号部门消失**（两边都没有对方）；1.2 左连接 15 行，多出的 `OPERATIONS | NULL` 行把"部门没人"显式暴露；
- 1.4 自连接输出 13 行（KING 无 mgr 被内连接丢掉），这正是后面 NOT EXISTS 要找的"没有下属的人"的反面——有 mgr 的人全在；
- 1.5 非等值连接：`sal BETWEEN losal AND hisal`，一行对上一个区间，14 人都拿到工资级别。

### 第 2 节：ON vs WHERE（示例 2.1、2.2）

同一条件 `e.sal > 2000`：

```
2.1 写在 ON  →  7 行：6 个高薪员工 + 部门40的 NULL 行
2.2 写在 WHERE → 6 行：NULL 行被 UNKNOWN 过滤，OPERATIONS 消失
```

一多一少正好一行——就是那条 `NULL > 2000 = UNKNOWN` 的行。**结论：对右表的过滤条件想保留"没有匹配"的行就写 ON；想剔除就写 WHERE（此时与内连接等价）。**

### 第 3 节：子查询（示例 3.1~3.5）

- 3.1 标量子查询当常量：全公司平均 2073.21 与每个人并列展示；
- 3.2 相关子查询"高于本部门平均"：6 人上榜，注意部门平均各不相同（2916.67 / 2175.00 / 1566.67）——子查询带着外层的 deptno 每行重算；
- 3.3 `IN` 找各部门最高薪：SCOTT 和 FORD 并列 3000 双双入榜——IN 天然允许并列；
- 3.4 **NOT IN 返回空集**（子查询 mgr 列含 NULL）；3.5 NOT EXISTS 正确返回 8 名"光杆"员工。注意 KING 不在其中——他有 3 个下属，空集的那个"直觉答案"本来就该是这 8 人。

### 第 4 节：GROUP BY（示例 4.1~4.4）

- 4.1 五聚合并列，10 号部门 3 人平均 2916.67；
- 4.2 `WHERE job <> 'CLERK'` 先删员工再分组、`HAVING AVG(sal) > 2000` 再筛组：10、20 部门留下，30（平均被 CLERK 拉低到 1433.33）出局；
- 4.3 `SELECT deptno, ename ... GROUP BY deptno` → **ERROR 1055**（原文见第八节），这是本文唯一一条"故意报错"的语句；
- 4.4 相关子查询版"每组最高"：与 3.3 相同的 4 行，为第 5 节的窗口函数版做铺垫。

### 第 5 节：窗口函数（示例 5.1~5.4）

- 5.1 三兄弟并排：SCOTT/FORD 同为 3000——`ROW_NUMBER` 给 2、3（用 empno 决胜，否则并列行顺序未定义），`RANK` 给 2、2、下一个 4，`DENSE_RANK` 给 2、2、下一个 3；
- 5.2 `PARTITION BY deptno` 三个部门各自 1~n；外层套 `WHERE rn = 1` 取每组第一名（3 行）——"Top-N per group"的标准解法；
- 5.3 累计求和：同日入职的 JAMES/FORD 累计值同为 23625.00（RANGE 帧把"同位"行一起算），这就是默认帧和 `ROWS` 帧的差异；
- 5.4 `LAG` 取上一行工资做差值；第一行没有"上一行"，得 NULL。窗口内 ORDER BY 只有 hiredate 时，同日两人的先后**未定义**（本次运行 FORD 的上一人是 JAMES）——要确定性就补第二列。

### 第 6 节：CTE 与 UNION（示例 6.1、6.2）

- 6.1 `WITH dept_avg AS (...)` 先算部门平均再 JOIN 回 emp，与 3.2 的相关子查询结果一致（6 行），但可读性高下立判；
- 6.2 `UNION` 得 4 种岗位（重复的 CLERK/MANAGER 被去掉），`UNION ALL` 得 8 行原样拼接——10 号部门 3 人 + 20 号部门 5 人。

### 第 7 节：NULL 与 COUNT（示例 7.1、7.2）

`NULL = NULL` → NULL、`NULL <=> NULL` → 1；`mgr = NULL` 空集、`mgr IS NULL` 抓出 KING；`COUNT(*)` = 14、`COUNT(mgr)` = 13、`COUNT(DISTINCT job)` = 5——同一张表三种数法，口径全在 NULL。

## 四、常见误区

| 误区 | 实际行为 | 本例现场 |
| --- | --- | --- |
| "LEFT JOIN 条件随便放 ON 或 WHERE" | 放 WHERE 过滤右表 → 左连接退化成内连接 | 2.1 有 7 行，2.2 只剩 6 行 |
| "NOT IN 和 NOT EXISTS 等价" | 子查询含 NULL 时 NOT IN 永远空集 | 3.4 Empty set vs 3.5 八行 |
| `WHERE mgr = NULL` | UNKNOWN，永远空集，也不报错 | 7.1 |
| "GROUP BY 里顺便 SELECT 个名字" | ONLY_FULL_GROUP_BY 下 ERROR 1055 | 4.3 |
| "窗口函数写在 WHERE 里" | 语法直接报错（SELECT 阶段才计算）；要先在 SELECT 里算好再套一层过滤 | 5.2 的两层写法 |
| "UNION ALL 就是快的 UNION" | 语义不同：不去重。需要去重时用 UNION | 6.2 |
| "COUNT(列) 和 COUNT(*) 一样" | COUNT(列) 跳过 NULL | 7.2：14 vs 13 |
| "别名哪儿都能用" | WHERE 看不到 SELECT 的别名（执行顺序） | 2.1 推论 |

**排查思路**：结果莫名是空集 → 先把子查询单独跑一遍，看返回里有没有 NULL；怀疑"过滤把不该删的删了" → 想一遍 2.1 的逻辑执行顺序，标出每个条件作用在哪一步；报 1055 → 检查 SELECT 列是否都是分组列或聚合。

## 五、八股追问

**Q1：INNER JOIN / LEFT JOIN / RIGHT JOIN 的区别？怎么选？**
结论：INNER 只留两边都匹配的行；LEFT 保左表全量、右表补 NULL；RIGHT 对称。选型看业务语义——"部门表连员工表，想看到没有员工的部门"必须 LEFT；等值关系的正常取数用 INNER。
为什么：JOIN 是"配对+筛选"，类型只决定"配不上的行去留"。
常见追问：*LEFT JOIN 左表一定会全出现吗？*——不一定，WHERE 里对左表列过滤照样删（对右表列过滤则是 2.2 的退化陷阱）。*A LEFT JOIN B 再 LEFT JOIN C，顺序有讲究吗？*——有，C 的 ON 若引用 B 的列，B 为 NULL 的行配 C 也多为 NULL，层级关系要想清楚。

**Q2：LEFT JOIN 的过滤条件写 ON 还是 WHERE？**
结论：右表的条件写 ON = "影响配对"，写 WHERE = "过滤最终结果"，后者会把左连接退化成内连接。
为什么：执行顺序 ON 在连接时、WHERE 在连接后；NULL 行过不了 WHERE 的比较（UNKNOWN）。
常见追问：*那左表的条件写哪？*——语义等价（左表行在连接前连接后都在），习惯写 WHERE，条件归拢一处。*怎么"既要过滤右表又要保留左表全部"？*——条件写 ON（2.1）。

**Q3：WHERE 和 HAVING 的区别？**
结论：WHERE 过滤行、分组前生效、不能用聚合；HAVING 过滤组、分组后生效、能用聚合。
为什么：逻辑执行顺序 WHERE → GROUP BY → HAVING。
常见追问：*HAVING 里能不能写普通列条件？*——语法上部分可以（分组列），但普通行级条件应写 WHERE，先过滤再分组还能少算。*为什么 WHERE 不能 COUNT(*)>1？*——那时组还没形成。

**Q4：IN 和 EXISTS 怎么选？NOT IN 为什么危险？**
结论：正写 IN/EXISTS 在 MySQL 8 多数等价（半连接优化）；NOT IN 在子查询含 NULL 时恒空集，必须换 NOT EXISTS。
为什么：NOT IN 是 `x<>a AND x<>b AND ...`，遇上 NULL 项就 UNKNOWN；EXISTS 是逐行"存在性"判断，NULL 不参与比较。
常见追问：*怎么让 NOT IN 安全？*——`NOT IN (SELECT mgr FROM emp WHERE mgr IS NOT NULL)` 或干脆 NOT EXISTS。*EXISTS 里 SELECT * 还是 1？*——一样，优化器只关心行是否存在。

**Q5：COUNT(\*)、COUNT(1)、COUNT(列) 的区别？哪个快？**
结论：COUNT(\*) 与 COUNT(1) 完全等价、数所有行，InnoDB 里有专门优化（挑最小的索引树数）；COUNT(列) 数该列非 NULL 的行；COUNT(DISTINCT 列) 再去重。
为什么：COUNT 的语义差异全在"数什么"。
常见追问：*为什么 COUNT(\*) 在大表也快/慢？*——InnoDB 会选一棵最小的二级索引扫；没有二级索引才扫聚簇索引。*COUNT(主键) 和 COUNT(\*)？*——结果相同（主键非 NULL），性能上 COUNT(\*) 让优化器自由选树，通常更好。

**Q6：窗口函数和 GROUP BY 的区别？ROW_NUMBER/RANK/DENSE_RANK 怎么选？**
结论：GROUP BY 把组折叠成一行，窗口函数分区后**每行都在**（分组不折叠）；三兄弟按"并列要不要占号、要不要分先后"选：去重取每一名用 ROW_NUMBER，体育名次用 RANK，紧凑名次用 DENSE_RANK。
为什么：折叠 vs 标注是两种需求——明细+排名必须窗口函数。
常见追问：*取每组前 N 怎么写？*——`ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) ` 外层 `WHERE rn <= N`（5.2）。*窗口函数能用在 WHERE 吗？*——不能，SELECT 阶段才计算，要套一层。*MySQL 5.7 怎么办？*——自连接/变量模拟，劝升级 8.0。

**Q7：UNION 和 UNION ALL？**
结论：UNION 去重（隐式排序/哈希开销），UNION ALL 直接拼。确定无重复或不在乎重复用 ALL。
为什么：去重需要把所有行收齐比较，代价随行数涨。
常见追问：*UNION 的去重是"整行"去重？*——是，所有 SELECT 列都相同才算重复。*两个查询列类型要一致吗？*——数目必须相同，类型可隐式转换（建议显式对齐）。

**Q8：NULL = NULL 结果是什么？怎么判断 NULL？**
结论：NULL（即 UNKNOWN，不是 TRUE 也不是 FALSE）；判断用 IS NULL / IS NOT NULL，NULL 安全等号用 `<=>`；NULL 参与 AVG/SUM 等聚合被忽略，COUNT(列) 不数它。
为什么：NULL 是"未知"，未知的两个值无法断言相等。
常见追问：*NOT IN 查出空集和这有什么关系？*——见 Q4，就是 UNKNOWN 传染。*`<>` 能排除 NULL 吗？*——不能，`NULL <> 1` 也是 UNKNOWN，NULL 行照样不出现——排除 NULL 必须显式 IS NOT NULL。

## 六、实际应用

- **报表统计**：GROUP BY + HAVING + 聚合，日活/月度营收/留存的基础形态；
- **Top-N per group**：每个班级前 3 名、每个类目销量 Top5——5.2 的两层写法是标准答案，另两个解法（相关子查询 4.4、JOIN 自比较）可作对照；
- **环比/同比**：LAG/LEAD 取上期值，一条 SQL 出"本月 vs 上月"增长率；
- **累计指标**：累计销售额、累计确诊——SUM OVER (ORDER BY 日期)；注意默认 RANGE 帧对"同日期"行的处理（5.3），需要逐行时写 `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`；
- **数据对账**：找"A 有 B 没有"——`A LEFT JOIN B ... WHERE B.id IS NULL`（注意这个 WHERE 判 NULL 是**故意的**，与 2.2 的误伤相反，IS NULL 恰好只留没匹配上的行）；
- **长查询治理**：多层嵌套子查询重构成 CTE，评审成本骤降。

## 七、延伸方向

- **递归 CTE**（`WITH RECURSIVE`）：组织架构树、日历表、图遍历——本模块"性能优化"篇会用到它造测试数据；
- **EXISTS 的半连接优化**：优化器怎么把子查询"展开"进主查询——见[索引与执行计划](../索引与执行计划/知识详解.md)；
- **字符集与排序规则**：中文排序、大小写敏感、`utf8mb4_general_ci` 与 `0900_ai_ci` 的差异会影响比较和索引；
- **JSON 函数与生成列**：MySQL 8 的半结构化数据处理。

## 八、运行示例

环境：MySQL 8.0.44（8.0+ 即可，窗口函数必需），任意可连接的本地实例。

```powershell
mysql --default-character-set=utf8mb4 -t -u root -p < 示例代码.sql
```
