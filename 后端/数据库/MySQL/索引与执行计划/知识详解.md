# 索引与执行计划：B+ 树、最左前缀、回表与覆盖索引、EXPLAIN、索引失效

> 学习目标：搞懂"索引为什么快"（B+ 树与聚簇索引）、"为什么有时加了索引也不走"（最左前缀与失效场景），并学会用 EXPLAIN 读执行计划、用 key_len 判断索引用到了第几列。
>
> 前置知识：会写多条件查询（`WHERE a = ? AND b > ?`）；知道"排序"和"范围"是两种查询形态。
>
> 配套示例：[示例代码.sql](示例代码.sql)（自建 `learn_index` 库，10 万行真实数据，所有 EXPLAIN 均为真实输出）；动手部分：[互动演示.html](互动演示.html)、[练习.md](练习.md)。

## 一、解决什么问题

数据量一上来，三个问题迟早找上门：

1. **同一条查询，10 行数据时秒出，100 万行时要几秒**——因为"找一条记录"默认方式是把整张表从头读到尾（全表扫描）。索引解决"怎么不扫全表"。
2. **加了索引，有的查询快了、有的纹丝不动甚至报错**——索引是按规则建的树，查询写法不配合就上不了树。
3. **拿到一条慢 SQL 不知道从哪下手**——EXPLAIN 是优化器的"施工图"，看得懂图才知道慢在哪一段。

本文用一张 10 万行的表，把每个结论都跑出真实证据。

## 二、核心原理

### 2.1 B+ 树：为什么 3~4 层就能装下千万行

InnoDB 索引是一棵**多路平衡搜索树**，读写单位是 16KB 的"页"：

- **非叶子节点**只放"键 + 指向子页的指针"，不放数据——一页能塞约 1170 个入口（主键 BIGINT 8B + 指针 6B ≈ 14B/个）；
- **叶子节点**放数据，且叶子之间用**双向链表**串起来——范围查询沿着链表扫即可；
- 树从根到所有叶子等高，查找任何键都是同样的深度。

算一笔账（行按 1KB 估，每页约 15 行）：

```
1 层（只有根）= 15 行
2 层 = 1170 × 15 ≈ 1.7 万行
3 层 = 1170 × 1170 × 15 ≈ 2056 万行   ← 千万级表，一次点查最多 3 次页读取
```

10 万行连 3 层都用不满（本表行更窄，约 2 层）。这就是"索引一次定位 vs 全表扫 10 万行"的数学来源（示例 1.3：0.00 秒 vs 0.02 秒——表再大 100 倍，索引那侧深度只多 1 层，全表那侧线性变慢 100 倍）。

为什么是 B+ 树而不是别的？（八股追问 Q1 详谈，先给直觉：二叉树/红黑树每个节点只有 2 个叉，千万行要 20+ 层，每层一次磁盘 IO；哈希表只能等值查，范围与排序无能为力；B+ 树矮胖 + 叶子有序，两者兼顾。）

### 2.2 聚簇索引与二级索引：回表的根源

| | 聚簇索引（主键） | 二级索引（自己建的） |
| --- | --- | --- |
| 叶子节点存什么 | **整行数据** | **索引列 + 主键值** |
| 按它查到数据 | 直接拿到整行 | 先拿到主键，**再回聚簇索引查整行**（回表） |
| 一张表有几棵 | 1 棵 | 0~N 棵 |

**回表（lookup）**：`SELECT * WHERE city='北京'` 走 `idx_city_age_created` 时，二级索引叶子只有 (city, age, created_at, id)——没有 remark。于是流程变成：索引里找 1 万个 id → 拿每个 id 回聚簇索引取整行 → 共回表 1 万次（示例 2.2）。

**覆盖索引**：如果 SELECT 的列**恰好都在索引里**（含隐含的主键 id），根本不用回表，Extra 出现 `Using index`（示例 2.3）。这是"少写 SELECT *"的数学理由。

### 2.3 最左前缀：联合索引是"多列排序"

`INDEX (city, age, created_at)` 的排序规则：先按 city 排，city 相同再按 age，age 相同再按 created_at——**像字典：先比第一个字母，再比第二个**。因此：

- 从最左列开始**连续**的等值条件才能用于"定位"（例子：city+age 两列定位，key_len=83）；
- **范围条件之后的列**只能"边扫边筛"，不再参与定位（age 用 `>` 后，created_at 断链）；
- 跳过左列、或左列用前导通配符，直接失去定位能力。

三个推论：等值列放前面、范围列放最后；`LIKE '北%'` 算前缀（能定位），`LIKE '%京'` 不算；给 (a,b) 建了联合索引就不必再单独给 a 建（左前缀已覆盖）。

**MySQL 8.0 的例外**：Skip Scan（8.0.13+）——左列取值很少时（本例 city 只有 10 个值），优化器枚举左列的每个值分别钻进索引。示例 3.2 里 `WHERE age=25` 真的用上了（Extra: `Using index for skip scan`），但仍要摸约 1 万条索引记录。**能被救场 ≠ 该依赖**，写 SQL 还是带上前缀列。

### 2.4 EXPLAIN：读优化器的施工图

`EXPLAIN` 放在 SELECT/UPDATE/DELETE 前面，返回一行（多表多行）计划。重点看 6 列：

| 列 | 含义 | 本次真实取值速查 |
| --- | --- | --- |
| `type` | 访问方式，性能从好到差 | `ref`（1.2/3.1）、`range`（3.2~3.5）、`index`（3.3b/5.2）、`ALL`（1.1/4.x） |
| `key` | 实际选用的索引 | NULL 表示没用上任何索引 |
| `key_len` | 索引"用到第几列、用多少字节" | 82/83/88 的变化见 2.5 |
| `rows` | 估算要读的行数 | 1 → 10000 → 100000 的量级跳变；**是采样估算**（估 18962，实测 10000，示例 2.4） |
| `filtered` | 过滤后剩余比例估算 | 仅参考 |
| `Extra` | 附加动作 | `Using index`（覆盖）、`Using index condition`（ICP）、`Using filesort`（额外排序）、NULL |

**type 常见档位**（好 → 差）：`const`（主键/唯一索引等值，最多 1 行）→ `eq_ref`（被连表的主键/唯一索引）→ `ref`（普通索引等值）→ `range`（索引范围）→ `index`（**扫整棵索引**，不是"走索引"，是"索引全扫"）→ `ALL`（全表扫描）。上线 SQL 至少 range；ALL 出现在大表上就要警惕。

**Extra 三个高频值**：
- `Using index`：覆盖索引，免回表（好信号）；
- `Using index condition`：**索引下推 ICP**——索引里能筛的条件先在索引层筛掉，不合格的行连回表都省了（示例 3.4 的 `SELECT *` 版）；
- `Using filesort`：没法顺着索引的顺序拿结果，要额外排序（示例 5.1/5.3b）——不一定真用磁盘文件，但意味着一次排序开销。

### 2.5 key_len：算出"索引用到了第几列"

key_len = 已用于定位的列的字节数之和。常用列的算法（utf8mb4、本表列全 NOT NULL）：

| 列类型 | 字节数 | 本表对应 |
| --- | --- | --- |
| VARCHAR(N) | N×4 + 2（长度前缀） | city：20×4+2 = **82**；username：50×4+2 = **202** |
| TINYINT UNSIGNED | 1 | age：**1** |
| DATETIME | 5 | created_at：**5** |
| 可空列 | 额外 +1（NULL 标志位） | 本表无；建表时 `NULL` 标志就要算进去 |

对照真实输出：`city=` → key_len **82**；`city= AND age=` → **83**；再加 `created_at <`（范围定位）→ **88**。key_len 停在几，就说明"定位"用到第几列——比"有没有走索引"更细一档的诊断。

### 2.6 索引的代价：没有免费的午餐

- **写放大**：INSERT/UPDATE 每改一个索引列，所有含该列的索引树都要跟着动（本表结尾 4 棵树 = 1 次写要维护 4 处）；
- **空间**：每棵索引都是一份按索引列排序的完整数据副本；
- **优化器负担**：索引越多，选路越慢（极端时反而选错）。

所以索引按"查询模式"建，不按"列"无脑建。

## 三、示例逐段讲解

配套 [示例代码.sql](示例代码.sql)，自建 `learn_index` 库：`t_user` 10 万行（username 全局唯一 / city 10 城 / age 18~63 / created_at 两年内），数据用数字表交叉相乘生成，可复现。索引**故意**在演示中途才建，保证前后对比。

### 第 0 节：造 10 万行

5 张 0~9 的 `digits` 表 CROSS JOIN 出 0~99999 的编号，各列取值都是编号的确定性函数——不用随机数，每次重建数据完全一致。此时表上只有主键。

### 第 1 节：全表扫描 vs 索引定位

```
1.1 无索引：  type=ALL  key=NULL          rows=100000  Using where
1.2 建索引后： type=ref  key=idx_username  key_len=202  rows=1  Extra=NULL
```

估算行数从 10 万掉到 1，这就是"上树"。1.3 用真实计时对照：索引 0.00 秒、无索引列扫全表 0.02 秒（10 万行还太小，表放大 100 倍差距就是秒级 vs 百倍线性增长）。

### 第 2 节：回表与覆盖索引

同一个 `WHERE city='北京'`（真实 10000 行，EXPLAIN 估算 18962——见 2.4 的"rows 是估算"）：

```
2.2 SELECT *：               key=idx_city_age_created  key_len=82  Extra=NULL（要回表 1 万次）
2.3 SELECT id,city,age,created_at：                              Extra=Using index（一次不回）
```

唯一区别是 SELECT 列——覆盖索引是**查询写出来的性能**。

### 第 3 节：最左前缀全家福（本篇核心）

索引：`idx_city_age_created (city, age, created_at)`。

| 查询 | type | key_len | Extra | 解读 |
| --- | --- | --- | --- | --- |
| 3.1 `city='北京' AND age=25` | ref | 83 | Using index | 两列连续等值，定位+覆盖 |
| 3.2 只查 `age=25` | range | 83 | Using index **for skip scan** | 8.0 枚举 city 救场，但仍摸约 1 万条 |
| 3.3 `city LIKE '%京'` + `SELECT *` | ALL | — | Using where | 前导通配，定位失败，全表 |
| 3.3 `city LIKE '%京'` + 只查 id | index | 88 | Using where; Using index | 救场变体：扫整棵覆盖索引代替扫全表 |
| 3.3 `city LIKE '北%'` | range | 82 | Using where; Using index | 前缀模糊=范围，能定位 |
| 3.4 `city= AND age>30 AND created_at<`（覆盖） | range | 83 | Using where; Using index | age 范围后 created_at 只能在索引里筛 |
| 3.4 同上（`SELECT *`） | range | 83 | **Using index condition** | ICP：筛在索引层完成，省回表 |
| 3.5 `city= AND age=25 AND created_at<` | range | 88 | Using where; Using index | age 改等值，created_at 恢复定位 |

这张表建议对着脚本逐条跑一遍——"范围之后断链"不是背的，是 key_len 83→88 的现场。

### 第 4 节：四种经典失效（全部 `SELECT *` 保证非覆盖）

| 写法 | 现场 | 原因 |
| --- | --- | --- |
| `LEFT(username,9)='user_0428'` | ALL | 对列套函数：索引存的是原值，函数后的值对不上号。改写 `LIKE 'user_0428%'` 即走索引 |
| `username = 42857`（数字） | ALL + **结果错**（空集） | 隐式转换方向：把**列**转成数字（'user_042857'→0），全表逐行转换 + 65535 条 1292 截断警告；加引号即修复 |
| `city='北京' OR age=25` | ALL | OR 一边没索引，整体塌方；给 age 建索引或 UNION ALL 改写 |
| `city <> '北京'` | ALL | 命中约 9 万行（9/10），回表不如直扫——选择性太低，主动放弃 |

第 2 条最凶：不只慢，**结果是错的**——本想查 `user_042857`，写成了数字，查出空集还不报错。字符串条件永远带引号。

### 第 5 节：ORDER BY 与 filesort

```
5.1 无 created_at 索引： ALL + Using filesort（10 万行全取出再排序取前 5）
5.2 建索引后：           index + key=idx_created + rows=5 + Extra=NULL
```

顺着 B+ 树叶子天然有序的顺序读 5 行即得。**5.2 还埋了一个真实踩坑现场**：刚 `ADD INDEX` 完立刻 EXPLAIN，可能仍是老计划——统计信息没刷新，`ANALYZE TABLE` 一次后恢复正常。"建了索引没生效"先怀疑这个。

5.3 联合索引内排序：`WHERE city='北京' ORDER BY age` 无 filesort（city 定位的段内 age 本就有序）；改成 `ORDER BY created_at, age` 立刻 `Using filesort`（顺序与索引不一致）。

### 第 6 节：家底盘点

`SHOW INDEX` 列出全部 4 棵树（PRIMARY + 3 个二级）；每棵都是一份要维护的排序副本——2.6 的代价落到实处。

## 四、常见误区

| 误区 | 实际 | 本例现场 |
| --- | --- | --- |
| "建了索引就一定走" | 函数/隐式转换/前导%/OR 单边/低选择性都会让它失效 | 第 4 节四连 ALL |
| "`type=index` 是走索引，挺好" | 是**扫整棵索引**，只比全表扫略好 | 3.3b：rows=100000 |
| "rows 就是行数" | 采样估算值，能差近一倍 | 估 18962 vs 实测 10000 |
| "建完索引 EXPLAIN 没变，索引没用" | 统计信息未刷新，ANALYZE TABLE 后再看 | 5.2 |
| "SELECT \* 无所谓" | 直接杀死覆盖索引 | 2.2 vs 2.3 |
| "条件类型写错顶多慢点" | 隐式转换还会**查错结果** | 4.2 空集 |
| "索引越多越好" | 每棵树都是写放大 + 空间 | 第 6 节 4 棵树 |
| "模糊查询都走不了索引" | `'北%'` 能走（前缀=范围），`'%京'` 不能 | 3.3 |

**排查思路（拿到慢 SQL 的固定动作）**：① `EXPLAIN` 看 `type`——ALL 再往下查；② 看 `key/key_len`——用没用上、用到第几列（对照 2.5 算 key_len）；③ 看 `Extra`——filesort 想排序索引，NULL+大 rows 想覆盖索引；④ 对照第 4 节失效清单查写法；⑤ 都不行再考虑加/改索引，并想清楚代价（2.6）。

## 五、八股追问

**Q1：为什么 InnoDB 用 B+ 树，不用 B 树 / 哈希 / 红黑树？**
结论：矮胖（3~4 层装千万行，点查 IO 次数=树高）+ 叶子链表（范围查询/排序顺着走）+ 非叶子不存数据（单页塞更多入口，树更矮）。
为什么逐个比：**B 树**数据挤在内节点，单页入口少、树更高，且范围查询要回旋中序遍历；**哈希**等值 O(1) 但完全不支持范围和 ORDER BY（InnoDB 的自适应哈希是内部优化，不是可建索引）；**红黑树/二叉树**二叉太瘦，千万行 20+ 层 = 20+ 次页 IO；**跳表**是内存结构（Redis 用），磁盘场景页对齐不如 B+ 树。
常见追问：*一棵 3 层 B+ 树能存多少行？*——1170×1170×15 ≈ 2000 万（假设行 1KB；行更窄更多）。*为什么叶子要双向链表？*——范围扫 `BETWEEN`、`ORDER BY`、`LIMIT` 沿链顺序读，不用反复回到上层。

**Q2：聚簇索引和二级索引的区别？什么是回表？**
结论：聚簇=主键索引，叶子放**整行**，一张表一棵；二级索引叶子放**索引列+主键**，查完拿主键回聚簇树取整行，这一步是回表。
为什么：整行数据只存一份（否则每建一个索引都复制全表，空间爆炸），二级索引轻量化，代价是补一次查找。
常见追问：*没有主键怎么办？*——InnoDB 自动选第一个非空唯一索引；再没有就生成隐藏的 ROW_ID 列。*回表一次的成本？*——一次聚簇树查找（2~4 次页 IO）；命中 1 万行就回 1 万次，所以高命中量的二级索引可能被优化器放弃（4.4 的 <>）。

**Q3：什么是覆盖索引？为什么快？**
结论：SELECT 的列全部包含在索引里（主键天然包含），免回表，Extra 显示 `Using index`。
为什么：数据在索引树里就地取材，IO 和 CPU 都省；回表是随机 IO，命中率越高省得越多。
常见追问：*怎么把查询改成覆盖？*——SELECT 只留必要列，或把高频查询列补进联合索引尾部。*`SELECT *` 还能覆盖吗？*——基本不能，这是少写 `*` 的第一理由。

**Q4：什么是最左前缀原则？联合索引 (a,b,c)，哪些查询能用？**
结论：索引按 (a,b,c) 逐列排序，条件必须从 a 开始**连续**才用于定位：`a=1 AND b=2 AND c>3` 全用；`a=1 AND c=3` 只有 a 定位（b 断链，c 只能筛）；`b=2` 直接用不上（8.0 可能 Skip Scan 兜底）。
为什么：字典先按首字母再按次字母排序，只拿"次字母"查没法翻目录。
常见追问：*范围条件放哪？*——等值列在前、范围列放最后（放前面会把后面的列全断成"筛"）。*(a,b) 建了还要给 a 单独建吗？*——不用，左前缀已覆盖。*`LIKE 'x%'` 算等值还是范围？*——范围（能定位），`'%x'` 连范围都不是。

**Q5：哪些写法会让索引失效？**
结论（六大场景+原理）：① 列上套函数（索引存原值）② 隐式类型转换（列被转换，字符串条件必须带引号）③ 前导通配符 `'%x'`（起点未知）④ OR 一侧无索引（整体塌方）⑤ 否定条件 `<>`/`NOT IN`（命中面太大，选择性低）⑥ 违反最左前缀。
为什么统一成一个原理：索引=有序+原值，凡让优化器"没法在有序结构上框定一段"的写法都会失效。
常见追问：*`IS NULL` 走索引吗？*——走（NULL 也存在索引里，`city IS NULL` 是等值类定位）。*`!=` 一定不走吗？*——不一定，选择性高时（如命中 1%）优化器仍可能用；本例命中 90% 才放弃。*8.0 有什么新救场？*——Skip Scan（左列低基数）与 ICP。

**Q6：EXPLAIN 主要看什么？**
结论：`type`（访问方式档位）→ `key/key_len`（用哪棵、用到第几列）→ `rows`（量级）→ `Extra`（Using index / Using index condition / Using filesort / Using temporary）。
为什么：慢的本质是"读的行数多 + 额外动作（回表/排序/临时表）"，这几列分别对应。
常见追问：*type=index 和 ref 的区别？*——ref 是定位到一段，index 是整棵索引从头扫。*Using temporary 什么时候出现？*——GROUP BY/ DISTINCT 的列与索引顺序不一致等需要临时表时，代价高于 filesort。*rows 不准怎么办？*——ANALYZE TABLE 刷新统计，或实测/看 Handler 计数器。

**Q7：为什么推荐自增主键？UUID 做主键有什么问题？**
结论：推荐"全局递增"的主键（自增 ID、雪花 ID）；随机主键（UUIDv4）带来页分裂、缓存不友好、二级索引膨胀。
为什么：聚簇索引按主键有序存储——递增插入永远追加在最后一页；随机插入落在中间任意页，页满就**分裂**（挪一半数据到新页、树高变胖），写放大且空间利用率低；同时每个二级索引叶子都存一份主键，主键越宽所有索引越胖。
常见追问：*UUID 完全不能用吗？*——有序 UUID（UUIDv7、改造为时间戳前缀）可缓解；要全局唯一又无协调中心时是合理选择。*雪花 ID 好在哪？*——趋势递增 + 分布式生成不撞号。

**Q8：什么时候该建索引，什么时候不该？**
结论：为高频查询的 WHERE/JOIN/ORDER BY 列建；列的选择性（distinct/总数）越高越值得；写多读少的表、极少查询的列、选择性极低的列（性别、状态两三个值）不建。
为什么：索引是拿写放大和空间换读加速——读得不频繁、换不来收益就是纯亏。
常见追问：*性别列配联合索引有意义吗？*——单独没意义，作为联合索引的前缀之一配合高选择性列可以。*怎么量化？*——看 Q6 的 rows 估算与真实命中率，回表行数 > 表行数一定比例时索引会被放弃。

## 六、实际应用

- **慢查询排查流程**（固定动作）：定位慢 SQL（慢日志）→ `EXPLAIN` → 按 2.4 五步读图 → 改写法或调索引 → 再 `EXPLAIN` 验证对比；
- **索引设计流程**：从真实查询出发（不是从表结构出发）→ 找高频条件列 → 等值列在前、范围列在后 → 尽量让高频查询覆盖 → 评估写放大；
- **SQL 改写三板斧**：函数条件改区间（`LEFT(u,9)='x'` → `u LIKE 'x%'`）、字符串条件带引号、OR 改 UNION ALL；
- **深分页**（`LIMIT 100000,20` 慢）与延迟关联：用覆盖索引先查出目标主键再回表——本模块"性能优化"篇（规划中）展开；
- **建索引的时机**：大批量导入数据先建表后建索引（导入快一个数量级），完成后 ANALYZE。

## 七、延伸方向

- **前缀索引**（`INDEX (col(10))`）与索引选择性计算；
- **Index Merge / Skip Scan / MRR** 等优化器进阶特性；
- **慢查询日志**（`slow_query_log`、`long_query_time`）与 `sys`/`performance_schema` 视图；
- **事务与锁**：索引与行锁的关系（没有索引的更新会锁全表）——本模块"事务与锁"篇（规划中）。
