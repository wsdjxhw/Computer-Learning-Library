### 4.（概念辨析）什么是覆盖索引？为什么它快？EXPLAIN 的哪个信号说明查询被覆盖了？

### 5.（猜执行计划）`idx_username(username)`，username 是 VARCHAR(50)、utf8mb4、NOT NULL：

```sql

```

### 9.（概念）为什么推荐自增主键？把 UUID（随机值）当主键会引入哪两个问题？

### 1.

- **聚簇索引（主键索引）**：叶子节点存**整行数据**——找到了索引条目就找到了数据；一张表只有一棵。
- **二级索引**：叶子节点存**索引列的值 + 主键值**（不存整行）。
- **回表**：走二级索引先拿到主键，再回聚簇索引里把整行取出来。命中 N 行就回 N 次表，是随机 IO（对照示例 2.2：city='北京' 命中约 1 万行，回表 1 万次）。

### 2.

- **哈希表**：等值查询 O(1) 很快，但完全不支持范围（BETWEEN、>、<）和 ORDER BY——索引的大量场景是"框定一段"；
- **红黑树/二叉树**：每个节点只有 2 个分叉，千万行高约 20+ 层，每层一次页读取，IO 次数太多；
- **B+ 树**：非叶子节点只存键+指针（一页约 1170 个入口，树"矮胖"，3~4 层装千万行），叶子存数据并用双向链表串起来——**点查深度=树高，范围/排序沿叶子链表顺序扫**，两头都占。
- 附加分：B 树（不是 B+）数据挤在内节点，单页入口变少、树更高，范围查询要回到上层中序遍历，所以 InnoDB 选 B+。

### 3.

实际输出：`type=range, key=idx_city_age_created, key_len=83, Extra=Using where; Using index for skip scan`（估算 rows 约 1 万）。

这是 **Skip Scan**（8.0.13+）：第一列 city 只有 10 个取值，优化器枚举每个 city 值分别钻进索引第二层。它说明"最左前缀失效"在新版本有了兜底——但**代价仍在**：要摸约 1 万条索引记录，远不如真正的前缀定位（rows=1）。结论：写 SQL 仍应带上最左列，Skip Scan 是安全网不是免死金牌。

### 4.

**覆盖索引**：SELECT 需要的所有列（含隐含的主键 id）都包含在索引里，直接在索引树上拿到全部答案，**一次回表都不用**。回表是随机 IO，省掉它性能提升明显（示例 2.2 vs 2.3：唯一区别是 SELECT 列表）。EXPLAIN 信号：**Extra 出现 `Using index`**。

### 5.

- A：`type=ref, key=idx_username, key_len=202, rows=1`——正常走索引（202 = 50×4 + 2 长度前缀）。
- B：`type=ALL, key=NULL`——**索引失效**。
- B 的更严重症状：**结果是错的**。字符串列与数字比较时，MySQL 把**列**逐行转成数字（'user_042857' → 0），于是谁都匹配不上 42857，返回空集（还带 65535 条 1292 截断警告）。"慢"只是顺带的。
- 修复：字符串条件永远带引号 `username = 'user_042857'`。

### 6.

根因：`phone` 是 VARCHAR，与数字比较触发**隐式类型转换**——把 phone 列转成数字再比：
1. **慢**：转换发生在列上，索引失效，全表扫描；
2. **查不到**：以字母开头的手机号格式（如带 +86、空格、横线的存量数据）转数字变 0，永远不等于传入号码。

修复：`WHERE phone = '13800001234'`（带引号，类型对齐）。同理：状态码列是字符串就传字符串，别让 MySQL 替你猜。

### 7.

建 **`(city, age, created_at)`**。

- 定位角度：city、age 都是等值，放前面连续定位（key_len=83）；created_at 排最后。若把 created_at 放第一位，等值条件 city/age 全部断在范围之后，只能"扫一段筛两列"；
- 排序角度：定位到 city='北京' AND age=25 的段后，段内 created_at 天然有序（索引第三列），`ORDER BY created_at DESC LIMIT 20` 顺着读 20 行即得，**filesort 消失**；
- 预测：`type=ref`（等值定位），`key=idx_city_age_created`，`key_len=83`，`Extra=Using index`（SELECT 的四列恰好全在索引里，覆盖）——这正是示例 3.1 的实测结果。

### 8.

字节账：city = 20×4 + 2(长度) = **82**；age TINYINT UNSIGNED = **1**；created_at DATETIME = **5**（列均 NOT NULL，无 NULL 标志位）。

- ① `WHERE city= AND age=`：82 + 1 = **83**；
- ② 再加 created_at 范围：created_at 作范围端点参与定位，82 + 1 + 5 = **88**；
- ③ age 用了 `>`：age 仍是范围端点（+1），但**范围之后 created_at 不再参与定位**，只能在索引里过滤——key_len 停在 **83**，且 `SELECT *` 时 Extra 会显示 `Using index condition`（ICP，对照示例 3.4）。

### 9.

自增主键保证新行永远追加在聚簇索引**最后一页**，顺序写入。随机主键（UUIDv4）的问题：
1. **页分裂**：新键落到中间任意页，页满就分裂（挪一半数据到新页、上层节点跟着调整），写放大、页利用率下降；
2. **二级索引变胖**：每个二级索引叶子都存一份主键，36 字节的随机 UUID 让所有索引默默膨胀（查询时缓存也装得更少）。

需要全局唯一又不想要自增时，用**趋势递增**的方案（雪花 ID、UUIDv7），保留"顺序追加"的性质。
