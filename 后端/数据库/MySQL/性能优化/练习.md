### 1.

慢的原因：LIMIT 的语义是"**越过** offset 行再取 N 行"，越过不是跳过——必须逐行读出并丢弃，扫描量 = offset + N，耗时随 offset 线性增长。

- **书签法**：记上一页末尾 id，`WHERE id > ? ORDER BY id LIMIT 20`，只扫 20 行、耗时与 offset 无关。前提：排序键有序可用（自增主键典型）、无其他过滤条件；局限：**不能跳页**，只能连续翻（上一页/下一页）；
- **延迟关联**：`JOIN (SELECT id FROM t ORDER BY x LIMIT 100000,20) t ON 主表.id=t.id`——offset 仍要扫，但扫的是只含主键的窄索引（覆盖，Using index），回表只发生在最终 20 行。通用、可跳页；排序走二级索引且回表贵时收益最大。

### 2.

三个参数：`slow_query_log`（开关）、`long_query_time`（阈值）、`slow_query_log_file`（路径）。

**不立刻生效**：`SET GLOBAL` 只修改"全局默认值"，对**之后新建**的连接生效；当前连接的会话值还是旧的，要补一句 `SET SESSION long_query_time = 1;`（或重连）。这也是示例代码第 1 节 GLOBAL/SESSION 双开的原因。另一个坑：慢日志只记录**开启之后**执行的语句，开启之前的慢 SQL 不会补录。

### 3.

- ① 精确 **100000**，要把一棵最小的索引树整个扫一遍（10 万行约 0.01 秒，亿级表分钟级）；
- ② 统计值约 **99288**（本机实测，差 0.7%），毫秒级返回——它来自采样统计（ANALYZE TABLE 刷新）。

不存总行数的原因：**MVCC 下"表里有多少行"对每个事务答案都不同**（未提交的插入/删除各行其是），"一个总数"在物理上不存在。MyISAM 能存是因为它没有多版本。

### 4.

耗时从短到长：**C（0.032 秒）< B（0.098 秒）< A（4.824 秒）**。

差距来源不是 CPU 也不是网络，是**提交次数**：A 每条 INSERT 是一个独立事务，每次提交都要等 redo log 刷盘（fsync），5000 次提交 = 5000 次磁盘同步等待；B 把 5000 次写合并成 1 次提交；C 再叠加"一条 SQL 装下 5000 行"省掉的解析与往返。应用层对应：MyBatis `<foreach>` / JDBC `rewriteBatchedStatements=true`。

### 5.

排查步骤：① 接口日志/链路追踪确认耗时段在 SQL；② 慢日志捞出这条 SQL；③ EXPLAIN：type=index/ALL、rows 巨大——扫描量 = offset+N；④ 确认排序键与过滤条件。

改法：
- **延迟关联**（通用，可跳页）：先 `SELECT id FROM t_goods ORDER BY sales DESC LIMIT 99980,20`（覆盖索引 sales 上的窄扫描），再 JOIN 回表取整行；
- **书签法**：`WHERE sales < 上页末尾销量 ORDER BY sales DESC LIMIT 20`——但销量会并列，只用 sales 当游标会**漏行/重行**。补法：游标改成**复合键 `(sales, id)`**：`WHERE sales < :s OR (sales = :s AND id > :id) ORDER BY sales DESC, id DESC LIMIT 20`，且索引建成 `(sales DESC, id DESC)` 或可利用的等价形式，保证排序键全局唯一、翻页稳定。

### 6.

"差几条无所谓" → **不要每次 COUNT(\*)**。方案：展示位读 **Redis 计数器/计数表**（业务写路径在事务内 `INCR`，或监听 binlog 异步同步），毫秒级、扛百万 PV；或退一步用 information_schema 的 TABLE_ROWS 估算（毫秒级，误差百分之几）。

改成"必须精确"：只能 `COUNT(*)`（选最小索引树全扫），代价是亿级表分钟级——所以要么降频（定时任务数一次写缓存，页面读缓存，容忍分钟级延迟），要么产品上限制（"共 1000+ 页"），要么上数仓/OLAP（ClickHouse 类列存）做统计。**精确 + 实时 + 快**三者大表上不可兼得，要和业务方挑两个。

### 7.

```sql
SELECT u.* FROM t_user u
JOIN (SELECT id FROM t_user ORDER BY id LIMIT 100000, 20) t ON u.id = t.id;
```

派生表那行（DERIVED）：`type=index`（沿主键整树顺序扫）、`key=PRIMARY`、`Extra=Using index`（只取 id，覆盖，免回表）；外层对 u 是 `type=eq_ref`（主键等值）回表 20 次。实测对比：0.0189 秒 → 0.0114 秒；表更大、行更宽或排序走二级索引时差距拉开到一个数量级以上。

### 8.

1. **多值 INSERT / LOAD DATA INFILE** 而不是逐条 INSERT（减少解析与往返，LOAD DATA 是 MySQL 最快的文本导入通道）；
2. **分批事务**：每 1~10 万行一批 COMMIT（提交次数从百万级降到几十次，又不会撑爆 undo）；
3. **先建表、后建索引**：导入期间少维护索引树，导完一次性建 + ANALYZE TABLE；
4. **临时 `SET unique_checks=0; foreign_key_checks=0;`**（如有唯一/外键约束，导入完恢复并抽检验证）；
5. **错峰 + 限速**：避开业务高峰，控制导入速率防打爆主从延迟；
6. （视环境）临时调大 `max_allowed_packet`、`innodb_buffer_pool` 预热、写完 `ANALYZE TABLE` 刷新统计。

### 9.

EXPLAIN 只给优化器的**估算**计划（rows 是采样估的）；**EXPLAIN ANALYZE 真实执行**并输出每一步的实际行数、循环次数和耗时。

必须用后者的场景：怀疑**估算失真**——比如估 2 万行实际扫了 50 万（统计过期/数据倾斜），或索引建了优化器却不选。实测数字才能回答"到底慢在哪一步"。注意 ANALYZE 会真的跑完 SQL，慢语句要控制影响（低峰期、加 LIMIT 验证、UPDATE/DELETE 放在可回滚会话里）。
