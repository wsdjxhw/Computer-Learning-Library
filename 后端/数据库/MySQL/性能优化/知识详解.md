# 性能优化：慢查询定位、深分页、COUNT、批量写入

> 学习目标：掌握"SQL 慢了"的完整处理链路——慢日志定位（谁慢）→ EXPLAIN 诊断（为什么慢，见[索引与执行计划](../索引与执行计划/知识详解.md)）→ 本篇的三类高频"对症药"：深分页改写、COUNT 替代、批量写入。所有数字均为 10 万行真实表上的实测。
>
> 前置知识：B+ 树与回表/覆盖索引（[索引与执行计划](../索引与执行计划/知识详解.md)）；事务与锁的基本概念（[事务与锁](../事务与锁/知识详解.md)——批量写入的快慢本质是"提交多少次"）。
>
> 配套示例：[示例代码.sql](示例代码.sql)（自建 `learn_perf` 库，10 万行，含慢日志真实节选）；动手部分：[互动演示.html](互动演示.html)、[练习.md](练习.md)。

## 一、解决什么问题

数据库慢，八成慢在这四件事上：

1. **不知道谁慢**——几万条 SQL 里挑出拖后腿的那几条：**慢查询日志**；
2. **翻页越翻越慢**——第 5000 页要几秒，第 1 页秒开：**深分页**（offset 的代价）；
3. **一个 COUNT 把首页拖垮**——亿级表精确计数要分钟级：**COUNT 的替代方案**；
4. **批量导入慢如蜗牛**——5000 行插了快 5 秒：**逐条提交的 fsync 瓶颈**。

本篇的方法论只有一句话：**先测量，再优化，优化后再测量**。跳过第一步的优化都是猜。

## 二、核心原理

### 2.1 慢查询日志：定位"谁在慢"

三个参数决定一切：

| 参数 | 含义 | 常用值 |
| --- | --- | --- |
| `slow_query_log` | 开关 | ON/OFF |
| `long_query_time` | 阈值，超过才记录 | 生产 1~3 秒；排查期可临时调低 |
| `slow_query_log_file` | 日志文件路径 | 默认 datadir/主机名-slow.log |

日志是**纯文本**，每条记录五要素：`Query_time`（总耗时）、`Lock_time`（等锁时间）、`Rows_sent/Rows_examined`（返回/扫描行数）、SQL 原文。`Rows_examined` 巨大而 `Rows_sent` 很小 = 典型的"扫得多取得少"，直接去查索引。

两个真实的坑（脚本里都现场演示了）：

- **`SET GLOBAL` 只对之后新建的连接生效**——当前连接要再补一句 `SET SESSION`，否则你以为阈值调低了，其实自己这条连接还用旧值（生产上同理：改完全局，老连接仍是旧阈值）；
- **慢日志只记录开启之后执行的语句**——开启之前的慢 SQL 不会补录，"日志里怎么没有"先查时间线。

### 2.2 深分页：`LIMIT 100000, 20` 慢在哪

LIMIT 的语义是"越过前 100000 行，取 20 行"——**越过不是跳过**：必须逐行读出并丢弃，扫描量 = offset + N。所以直觉写法的时间随 offset 线性增长，第 1 万页 = 灾难。两种救法：

- **书签法（游标/续传式）**：记住上一页最后一条的 id，下一页 `WHERE id > 上页末尾id LIMIT 20`——B+ 树直接定位起点，只扫 20 行。**前提**：排序键有序且连续可用（主键自增最典型）、无其他过滤条件、只支持"下一页"不能跳页；
- **延迟关联**：`JOIN (SELECT id FROM t ORDER BY id LIMIT 100000, 20) t ON 主表.id = t.id`——offset 还是要扫，但扫的是"只含主键的窄索引"（覆盖，`Using index`），回表只发生在最终 20 行。通用解，能跳页。

### 2.3 COUNT：InnoDB 为什么没有"总行数"

MyISAM 把行数存在表元信息里（`COUNT(*)` 直接返回），InnoDB **不存**——因为 MVCC 下"表里有多少行"对每个事务答案都不同（[事务与锁](../事务与锁/知识详解.md) 2.3）。所以精确 `COUNT(*)` 只能选一棵最小的索引树**整个扫一遍**。

| 方案 | 精确 | 速度 | 适用 |
| --- | --- | --- | --- |
| `COUNT(*)` | 精确 | 随行数线性 | 千万级以内基本没压力 |
| `information_schema.TABLES.TABLE_ROWS` | 估算（本次实测 99288 vs 真实 100000，差 0.7%） | 毫秒 | 报表、监控看量级 |
| `EXPLAIN` 的 rows | 估算 | 毫秒 | 辅助判断，别当结果 |
| Redis/内存计数器 | 取决于维护 | 毫秒 | 首页"共 N 条"这种展示位 |
| 条件计数（如"今天的订单数"） | 精确 | 给条件建好索引后扫小段 | 把"数全表"变"数索引一小段" |

### 2.4 批量写入：瓶颈不是 CPU，是"提交次数"

autocommit 模式下每条 INSERT 是一个独立事务，每次提交都要把 redo log **刷盘（fsync）**等待确认——磁盘说"我一天只能应酬你这么多次"。实测（5000 行，同一台机器）：

| 姿势 | 实测耗时 | 差距 |
| --- | --- | --- |
| 逐条 INSERT，autocommit（5000 次提交 = 5000 次 fsync） | **4.824 秒** | 基准 |
| 同样逐条，但包在 1 个事务里（1 次 fsync） | **0.098 秒** | 49 倍 |
| 一条多值 INSERT ... SELECT 5000 行 | **0.032 秒** | 151 倍 |

对应到应用层：别在循环里逐条 `save()`（姿势1）；MyBatis 用 `<foreach>` 拼多值 INSERT、JDBC 加 `rewriteBatchedStatements=true`（姿势3）；超大导入再叠加：先建表后建索引、临时 `SET unique_checks=0; SET foreign_key_checks=0`、`LOAD DATA INFILE`。

**边界提醒**：单个事务别无限大——几万~几十万行一档即可，太大则 undo 膨胀、锁持有时间长（[事务与锁](../事务与锁/知识详解.md) Q8 的 2PL）。

### 2.5 优化路线图：从便宜到贵

1. **SQL 与索引**（最便宜）：EXPLAIN → 加/改索引 → 改写法（本篇 + 索引篇）；
2. **库表结构**：冷热分离、大字段拆表、冗余字段省 JOIN；
3. **参数**：`innodb_buffer_pool_size`（通常给到物理内存 50%~70%）、连接数、刷盘策略；
4. **架构**（最贵）：缓存前置（Redis）→ 读写分离 → 分库分表 → 换存储（OLAP 列存/ES）。

顺序不能倒：架构手段解决不了没索引的全表扫描，缓存也扛不住每条 SQL 都 miss。

## 三、示例逐段讲解

配套 [示例代码.sql](示例代码.sql)，自建 `learn_perf` 库：`t_user` 10 万行（主键自增 + idx_created），数据与索引篇同套路生成，可复现。

### 第 0 节：造 10 万行

与前两篇相同的 digits 交叉积造数法。**注意本次把慢日志开关放在了造数之后**——所以造数那条约 1 秒的 INSERT 不在日志里（2.1 的第二个坑就是它）。

### 第 1 节：慢日志现场

开启（GLOBAL + SESSION 双开）、阈值 0.1 秒、`SLEEP(0.2)` 现场制造一条慢查询。日志真实节选（脚本结尾附了原文）：

```text
# Query_time: 0.204397  Lock_time: 0.000000 Rows_sent: 1  Rows_examined: 1
SELECT SLEEP(0.2) AS 制造一条慢查询;
# Query_time: 4.823975  Lock_time: 0.000003 Rows_sent: 0  Rows_examined: 0
CALL p_insert_one_by_one();
```

第二条很有意思：**存储过程按整条 CALL 计时**——4.8 秒正是第 4 节姿势1 的总耗时，慢日志替我们把"5000 次逐条提交"记成了一笔账。

### 第 2 节：深分页三写法实测

| 写法 | EXPLAIN 要点 | 实测耗时 | 解读 |
| --- | --- | --- | --- |
| 1 直觉 `ORDER BY id LIMIT 100000,20` | type=**index**（主键整树顺序扫）rows=99288 | **0.0189 秒** | 扫 10 万行丢 10 万行 |
| 2 书签 `WHERE id>100000 LIMIT 20` | type=**range** key=PRIMARY（rows 估 1，估算而已） | **0.0003 秒** | 定位后只扫 20 行，63 倍 |
| 3 延迟关联 | 派生表 index + `Using index`（窄索引），外层 eq_ref 回表 20 次 | **0.0114 秒** | offset 仍要扫，但扫的是窄索引 |

10 万行表上写法 1 才 0.02 秒——**这正是深分页的迷惑性**：量级一上去（千万行、offset 百万），写法 1 涨到秒级而写法 2 仍是毫秒级，因为只有它和 offset 无关。另外本表 ORDER BY id 走主键、行较窄，写法 3 优势不明显；当排序走**二级索引且需要回表**时，延迟关联（先只取主键再回表）收益会大得多。

### 第 3 节：COUNT 两副面孔

`COUNT(*)` 精确 100000（本次约 0.01 秒，10 万行尚无压力）；`information_schema` 统计值 99288——**差 712 行**，这就是"估算"的含义。选型按 2.3 的表来。

### 第 4 节：批量写入三档（2.4 已给数）

同一批 5000 行，唯一变量是"提交了几次、一条语句装了几行"：4.824 → 0.098 → 0.032 秒。慢日志里那条 4.8 秒的 CALL 就是姿势1 的"案底"。

## 四、常见误区

| 误区 | 实际 | 本例现场 |
| --- | --- | --- |
| "慢就是没加索引" | 深分页有索引照样慢（扫的行没少）；批量写入慢与索引无关 | 第 2/4 节 |
| "`SET GLOBAL` 立刻全局生效" | 只对**新**连接生效，当前连接要 SET SESSION | 第 1 节 |
| "日志里没有 = 这条不慢" | 开启之前的语句不补录；阈值没对上也不录 | 2.1 |
| "书签法万能" | 有过滤条件/排序非唯一/需要跳页时失效，退回延迟关联 | 2.2 |
| "延迟关联一定快很多" | 主键有序、行窄时优势小；二级索引排序 + 回表场景才显著 | 第 2 节 0.0189 vs 0.0114 |
| "`COUNT(*)` 比 `COUNT(1)` 慢" | 优化器层面等价，都是选最小索引树扫 | Q3 |
| "批量插入就是拼 SQL" | 事务合并（姿势2）比语句合并（姿势3）先解决数量级问题，两者叠加用 | 第 4 节 |
| "事务越大越快" | 提交少了是快了，但锁持有与 undo 膨胀有代价，分批 1~10 万行 | 2.4 边界 |
| "先上读写分离再说" | 读写分离解决"读多"，解决不了单条烂 SQL；先走 2.5 路线前两级 | 2.5 |

**排查思路（"接口慢了"的固定动作）**：① 确认是不是数据库（APM/链路追踪定位耗时段）；② 慢日志捞出元凶 SQL；③ `EXPLAIN`（对照[索引与执行计划](../索引与执行计划/知识详解.md) 四、排查五步）；④ 对号入座：扫描行数爆炸→索引；offset 大→深分页；COUNT 大表→替代方案；写入慢→批量姿势；⑤ 改完**再测一遍**留证据。

## 五、八股追问

**Q1：慢查询日志怎么用？**
结论：`slow_query_log=ON` + `long_query_time` 阈值，超时的语句连时间、锁时间、扫描行数、原文记入日志；配合 `log_queries_not_using_indexes` 还能记录不走索引的语句。分析工具有 `mysqldumpslow`、`pt-query-digest`。
为什么：优化第一步是找到真凶——凭感觉优化经常修一条不痛的 SQL。
常见追问：*阈值设多少？*——生产 1~3 秒抓大头，专项排查临时调低。*SET GLOBAL 怎么才能对当前连接生效？*——补 SET SESSION（或重连）。*除了慢日志还有什么？*——`performance_schema`/`sys` 视图（语句事件统计）、`EXPLAIN ANALYZE`（真实执行+耗时）、链路追踪。

**Q2：`LIMIT 1000000, 20` 为什么慢？怎么优化？**
结论：LIMIT 必须读并丢掉 offset+N 行，扫描量随 offset 线性涨。优化三选：书签法 `WHERE id > 上页末尾 LIMIT 20`（最优，限连续有序键、不能跳页）；延迟关联（先覆盖索引取主键再回表，通用）；产品层限制翻页深度（搜索引擎只让翻几十页）。
为什么：B+ 树只能"定位到某键"，没有"直接跳到第 100 万行"的入口——位置必须靠走过来。
常见追问：*为什么第 1 页快？*——offset=0 没有丢弃成本。*书签法的坑？*——有 WHERE 过滤时"上一页末尾 id"不再能代表位置（中间可能插新行导致漏/重）；排序键不唯一时分页会乱，需加第二排序键。*ES/搜索引擎怎么解决？*——search_after（本质就是书签法）。

**Q3：`COUNT(*)`、`COUNT(1)`、`COUNT(列)` 的区别？大表怎么优化 COUNT？**
结论：`COUNT(*)` 与 `COUNT(1)` 优化器处理等价（选最小的索引树扫，都统计所有行）；`COUNT(列)` 只统计该列**非 NULL** 的行，语义就不同。大表优化：估算（information_schema/EXPLAIN rows）、外部计数（Redis/单独计数表 + 触发器或在业务写路径维护）、条件计数靠索引缩小扫描段。
为什么 InnoDB 不能像 MyISAM 存行数：MVCC 下每个事务看到的行集不同，"一个总数"根本不存在。
常见追问：*为什么 COUNT(*) 会选索引？*——优化器挑最小的那棵树扫（二级索引比主键树瘦）。*COUNT(distinct col) 呢？*——要建临时结构去重，更贵。

**Q4：批量插入几百万行怎么最快？**
结论：分层加速——语句层：多值 INSERT / `LOAD DATA INFILE`；事务层：几千~几万行一批提交；环境层：先建表后建索引、临时关 `unique_checks`/`foreign_key_checks`、`innodb_flush_log_at_trx_commit` 临时调 2（导完恢复）；架构层：错峰导入、并行按表/按段分工。
为什么：逐条提交时瓶颈是每次提交的 fsync（实测 49 倍差距），先消掉它再谈其他。
常见追问：*一批多大合适？*——1~10 万行/批常见，过大 undo 与锁风险上升。*导入时要不要禁用 binlog？*——从库依赖 binlog 就不能禁；能禁的是双一安全参数的临时调整（需评估宕机丢少量数据的容忍度）。*为什么先建表后建索引？*——插入时少维护 4 棵树，导完一次性建。

**Q5：一条 SQL 慢的完整排查思路？**
结论：五步——① 慢日志/监控定位 SQL；② EXPLAIN 读 type/key/rows/Extra（索引篇 2.4）；③ 判断类型：扫描行数大→索引或改写；offset 大→深分页三写法；排序/临时表→索引顺序；④ 改后 EXPLAIN 对比 + 真实计时；⑤ 回归业务验证（结果必须等价）。
为什么要有⑤：优化把结果改错（如书签法遇上并发插入漏行）比慢更糟。
常见追问：*EXPLAIN 的 rows 不放心怎么办？*——`EXPLAIN ANALYZE` 真实执行给出每步实际行数与耗时（8.0.18+）。*线上能直接 EXPLAIN 吗？*——可以，只读；ANALYZE 会真执行，慢 SQL 慎用（可包在 EXPLAIN 外的事务里截断）。

**Q6：除了 SQL 层还有什么优化手段？**
结论：缓存前置（Redis 挡读）、读写分离（主写从读）、分库分表（水平拆分）、冷热分离与归档、参数调优（buffer pool）、连接池（复用连接）、异步化（写请求进 MQ 削峰）。
为什么放最后：它们放大"单条 SQL 本来就快"的系统；SQL 本身烂，架构只是搬 disaster。
常见追问：*读写分离带来什么新问题？*——主从延迟下的"写后读不到"（路由到主库/短延迟读）。*分库分表代价？*——跨分片 JOIN/事务/分页全部变难，能不分就不分，先垂直拆。

**Q7：`EXPLAIN ANALYZE` 和 EXPLAIN 的区别？**
结论：EXPLAIN 只给优化器**估算**；ANALYZE 真实执行并输出每一步的实际行数、循环次数、耗时，能暴露"估 2 万实扫 10 万"的计划失真。
为什么有用：rows 是采样估算（索引篇 2.4 的 18962 vs 10000），关键决策要用实测背书。
常见追问：*代价？*——真的执行一遍（SELECT 会跑完，UPDATE/DELETE 也是实际分析——用 ROLLBACK 会话包住）。*还有谁？*——`SHOW WARNINGS` 看改写后的等价 SQL、optimizer trace 看选路过程。

**Q8：为什么"先测量再优化"？有没有反例？**
结论：没有。任何优化前先拿到基线数字（耗时/扫描行数/调用频率），改后同口径对比——"感觉快了"不是证据。本篇每个结论都配了实测就是这个意思。
常见追问：*怎么算优化成功了？*——目标明确：P99 延迟、接口整体耗时、慢日志条数——选一个业务在乎的指标。
为什么强调：性能问题充满反直觉（索引篇的 Skip Scan 救场、本篇延迟关联在主键场景收益小），不测就翻车。

## 六、实际应用

- **上线前 SQL 体检**：全量 SQL 过一遍 EXPLAIN（CI 里卡 type=ALL 的大表查询）；分页接口从第一天就用书签/延迟关联，别等翻页慢了再改；
- **慢日志例行巡检**：每天 `pt-query-digest` 出 top 10，纳入迭代；`long_query_time` 线上 1 秒起；
- **列表页总条数**：展示位用估算/缓存，精确数只在必要时查，且走条件索引；
- **数据导入脚本**：批量多值 + 分批事务 + 事后建索引 ANALYZE；凌晨跑 + 限速，避免打爆主从；
- **紧急止血套路**：慢 SQL 拖垮全站时——先 kill 长查询/限流保住可用性，再回滚最近变更（新索引/新 SQL），最后慢慢查根因。

## 七、延伸方向

- **EXPLAIN ANALYZE / optimizer trace / performance_schema**——计划级深潜；
- **读写分离与主从延迟**、**分库分表**（ShardingSphere）——本库后续"分布式"主题；
- **Redis 缓存前置**（缓存三兄弟问题：穿透/击穿/雪崩）——Redis 模块展开；
- **InnoDB 关键参数**：buffer pool、刷盘策略、连接数调优——部署运维方向；
- **OLAP 与列存**（ClickHouse/Doris）：亿级统计报表为什么不在 MySQL 里硬扛。

环境：MySQL 8.0+（本次实测 8.0.44）；涉及 `SET GLOBAL`（慢日志开关），需要高权限账号。

