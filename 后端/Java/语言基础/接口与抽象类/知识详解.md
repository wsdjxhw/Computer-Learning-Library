# 接口与抽象类

## 学习目标

- 理解抽象类"半成品模板"与接口"能力契约"的定位差异。
- 掌握 `abstract`、`default` 方法的语法与约束。
- 理解"类单继承 + 接口多实现"的组合方式。
- 能在"抽象类还是接口"之间做出正确选型（面试与设计的常考题）。

**前置知识**：[面向对象三大特性](../面向对象三大特性/知识详解.md)（尤其是继承与多态）。
**适用范围**：Java 语言核心；Java 8+ 的默认方法、函数式接口都从这里出发。

---

## 一、本节解决什么问题

有时一个类"不该被直接实例化"：比如"形状"必须会算面积，但"形状"自己算不出来，只有具体的圆、矩形才能算。抽象类和接口提供了两种**声明"必须有什么能力"，把实现留给子类**的手段——它们是多态在"设计层面"的落地工具。

## 二、核心原理

### 2.1 抽象类：是什么（is-a）的半成品模板

```java
abstract class AbstractShape {
    public abstract double area();          // 抽象方法：只有声明，无实现
    public String describe() {              // 具体方法：全部子类共享的骨架
        return name + " 的面积 = " + area();  // 骨架里调用抽象方法，由子类补全
    }
}
```

要点：① 含抽象方法的类必须声明 `abstract`，**不能 new**；② 具体子类必须实现全部抽象方法，否则自己也得是抽象类；③ 可以有字段、构造方法（供子类 `super` 调用）和具体方法——**模板方法模式**：父类写好流程骨架（describe），变化的细节（area）留给子类填。

### 2.2 接口：能做什么（can-do）的能力契约

```java
interface Drawable {
    void draw();                     // 抽象方法：实现类必须提供
    default void drawWithFrame() {   // 默认方法（Java 8+）：带实现的兜底
        System.out.println("先画边框，再调用 draw():");
        draw();                      // 默认实现可以调用抽象方法
    }
}
```

接口是一份**契约**：实现它 = 承诺提供这些方法。传统上接口只能有常量和抽象方法；Java 8 起允许 `default`（默认实现）和 `static` 方法，Java 9 起允许 `private` 方法。

### 2.3 单继承 + 多实现

```java
class Circle extends AbstractShape implements Drawable, Swimmer, Runner { ... }
```

- Java 类**只能 extends 一个**父类（避免多继承的菱形冲突）；
- 但可以 **implements 多个**接口——一个对象可以同时具备多种能力（Bob 既是 Swimmer 又是 Runner）；
- 接口引用同样能指向实现类对象：`Swimmer s = bob; s.swim();`——接口也是多态类型。

### 2.4 选型对比（高频面试题）

| 维度 | 抽象类 | 接口 |
| --- | --- | --- |
| 关系语义 | is-a（是一种） | can-do（具备能力） |
| 继承数量 | 单继承 | 多实现 |
| 字段 | 可有实例字段、状态 | 只能有常量（public static final） |
| 构造方法 | 有（子类 super 调用） | 无 |
| 方法 | 抽象 + 具体均可 | 抽象 + default/static |
| 典型场景 | 一族相关类的公共骨架与状态 | 跨谱系的同一能力（Comparable、Runnable） |

**经验法则**：要在"同一族类"间共享代码与状态 → 抽象类；要给"不相关的类"统一能力约定 → 接口。典型组合是"抽象类搭骨架 + 接口定契约"，如 `AbstractList` 实现 `List`。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 试图 new 抽象类/接口 | 都不能实例化，只能 new 具体子类/实现类 |
| 子类没实现全部抽象方法 | 该子类必须也声明 abstract，否则编译错误 |
| 接口里写字段当状态用 | 接口字段天然是常量（final），不能存可变状态 |
| 实现两个接口有同名 default 方法 | 必须自己重写该方法解决冲突，否则编译错误 |
| 把接口当"更弱版本的类" | 语义不同：接口是能力契约，与父类构成 has-capability 而非 is-a |
| 抽象类必须含抽象方法？ | 反了——含抽象方法的必须抽象；抽象类也可以全是具体方法（单纯禁止实例化） |

**排查思路**："必须实现 xxx 方法"的编译错误 → 检查父类/接口新增的抽象方法；default 方法行为怪 → 看是否被实现类覆盖或多个接口冲突。

## 五、八股追问

"接口 vs 抽象类"是设计与语法双料的必考题，答案要有维度对比再加选型理由。

**Q1（必考）：接口和抽象类的区别？怎么选？**
抽象类是 is-a 半成品模板：可有实例字段、构造方法、具体方法，只能单继承；接口是 can-do 能力契约：只含常量与抽象/default 方法，可多实现。**同一族类共享骨架与状态 → 抽象类；跨谱系的类统一能力约定 → 接口。**
**追问：两者能配合吗？** 典型组合是"抽象类搭骨架 + 接口定契约"，如 `AbstractList implements List`。

**Q2：抽象类可以有构造方法吗？接口呢？**
抽象类**可以**——它有实例字段要初始化，构造方法供子类 `super(...)` 链式调用，但自己不能 new；接口**没有**构造方法——无实例状态可初始化。
**追问：抽象类可以不含抽象方法吗？** 可以，此时 abstract 仅表示"禁止直接实例化"（如 `HttpServlet`）。

**Q3：Java 8 为什么引入 default 方法？**
让接口**在不破坏已有实现类的前提下演进**：给 `List` 补 `stream()` 时，不可能要求全世界所有 List 实现类同步改写——default 提供带实现的兜底。
**追问：两个接口有同名 default 方法，实现类怎么办？** 必须自己重写该方法消解冲突，否则编译错误；另有"类优先"规则——从父类继承的方法总是优先于接口的 default 方法。

**Q4：接口的成员变量有什么特点？**
默认且只能是 `public static final`（常量）。不能有实例字段，因为接口是行为契约不承载状态——何况一个类可实现多个接口，实例状态归属无法判定。方法默认 `public abstract`（default/static/private 除外）。

**Q5：抽象方法能用 private / static / final 修饰吗？**
都不能：private——子类看不见，永远无法实现；static——属于类，没有"留给子类补全"的多态意义；final——与"必须被重写"直接矛盾。

**Q6：面向接口编程的好处是什么？**
调用方依赖契约而非实现：实现可替换（ArrayList/LinkedList 随切）、可测试（用 Mock 替换真实依赖）、可插拔（Spring 的依赖注入整个建立在"注入接口类型"上）。设计原则层面的名字叫**依赖倒置**——高层与低层模块都依赖抽象。

## 六、实际应用与取舍

- **JDK 中的实例**：`Comparable`（可比较）、`Runnable`（可执行）、`AutoCloseable`（[异常处理](../异常处理/知识详解.md)的 try-with-resources 依赖它）、`List`/`Map`（集合契约，配 `AbstractList` 等骨架类）。
- **框架中**：Servlet 的 `HttpServlet`（抽象类骨架）、Spring 的 `ApplicationContext`（接口多实现切换）。
- **函数式接口**：只有一个抽象方法的接口可写 Lambda（如 `Comparator`）——Lambda 一课的入口。
- **取舍**：需要共享状态/骨架 → 抽象类；需要给不相关类挂同一能力、或要表达"可插拔"→ 接口。

## 七、可继续学习的方向

- Lambda 与函数式接口（`@FunctionalInterface`、`Function`/`Predicate` 家族）。
- 模板方法模式、策略模式——两种抽象各自的设计模式代表。
- 面向接口编程与依赖倒置原则（Spring 的核心思想）。
