# 异常处理

## 学习目标

- 掌握 Throwable 的家族树，分清 Error、受检异常、非受检异常。
- 理解 try/catch/finally 的执行顺序。
- 会自定义异常，理解"受检"在编译期强制什么。
- 掌握 try-with-resources 的自动关闭机制。

**前置知识**：[面向对象三大特性](../面向对象三大特性/知识详解.md)（异常体系就是继承树的实例）；[数据类型与变量](../数据类型与变量/知识详解.md)。
**适用范围**：Java 语言核心；写任何真实程序都绕不开。

---

## 一、本节解决什么问题

程序运行时会遇到"计划外情况"：文件不存在、网络断了、用户输入了字母当数字。异常机制回答三个问题：**怎么表示错误**（对象）、**在哪里处理**（调用链上抛，直到有人 catch）、**怎么保证收尾**（finally / try-with-resources）——让错误处理代码与业务逻辑分离。

## 二、核心原理

### 2.1 异常家族树

```text
Throwable
├── Error                          严重错误：OutOfMemoryError、StackOverflowError
│                                  程序处理不了，不要 catch 它
└── Exception
    ├── RuntimeException           非受检（unchecked）：空指针、越界、算术……
    │                              多为程序 bug，编译器不强制处理
    └── 其他（IOException 等）      受检（checked）：外部环境问题
                                   编译器强制 try/catch 或 throws 上抛
```

用 `getSuperclass()` 沿继承链上溯，能现场打印出这棵树（见示例第 1 段）。**受检/非受检的分界**：受检异常是"合理可预期的外部故障"（文件、网络），编译器强制你表态；非受检多为"程序写错了"，靠修代码而不是 catch 解决。

### 2.2 try/catch/finally 执行顺序

```text
try 出错:   try(出错前的语句) → 匹配的 catch → finally
try 正常:   try 全部 → (跳过 catch) → finally
```

finally **无论如何都执行**（含 try 中 return 的情形），标准用途是释放资源。注意：finally 里写 return 会"吞掉"异常和返回值，属于禁手。

### 2.3 自定义异常与异常包装

```java
class InvalidAgeException extends Exception {          // 继承 Exception → 受检
    public InvalidAgeException(String message) {
        super(message);                                 // 传给父类，getMessage() 可取
    }
}
```

- 方法声明 `throws InvalidAgeException` 后，**调用方必须 try/catch 或继续上抛**——这就是"受检"的强制力。
- 常见手法：catch 底层异常（NumberFormatException）后 `throw new 业务异常(更好懂的说明)`——把技术错误翻译成业务语言，必要时把原异常作为 cause 传入（`new Xxx(msg, e)`）保留现场。

### 2.4 try-with-resources（Java 7+）

资源（文件、连接）实现 `AutoCloseable` 后，放进 `try(...)` 括号里声明，无论正常结束还是中途抛异常，**编译器自动调用 close()**，且多个资源**逆序关闭**（后打开的先关，符合依赖关系）：

```text
打开: 配置文件 → 数据库连接
关闭: 数据库连接 → 配置文件   （逆序）
```

它取代了手写 finally + close 的老套路，还避免了"close 的异常覆盖业务异常"的老坑。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| `catch (Exception e) {}` 空吞异常 | 最恶劣的习惯：错误被藏起来还打断流程；至少记录日志 |
| catch 里只 `e.printStackTrace()` | 不算处理；要么恢复、要么转成语义更清晰的上抛 |
| 用异常控制正常流程 | 异常机制代价高，可预期的分支判断用 if/返回值 |
| finally 里 return | 会吞掉 try 的返回值和异常，禁止 |
| 忘记关闭资源 | 用 try-with-resources；手写时 finally 里 close 还要防 null |
| catch Error"防止崩溃" | Error 处理不了；OOM 后 catch 大概率继续失败 |
| 异常信息丢失 | 包装时传入 cause：`new InvalidAgeException(msg, e)` |

**排查思路**：看异常的**第一行**（类型 + 消息）和**caused by 链**；行号在堆栈里从上往下找自己代码的包名。

## 五、八股追问

异常体系的考题特点是"边界情况多"，每题背后都有一条设计理由。

**Q1：Error 和 Exception 的区别？受检和非受检异常怎么分？**
Error 是系统级严重错误（OutOfMemoryError、StackOverflowError），程序处理不了，**不要 catch**；Exception 分两支——受检异常（IOException 等）是"合理可预期的外部故障"，编译器强制 try/catch 或上抛；非受检（RuntimeException 及子类：NPE、越界、算术）多为程序 bug，靠**修代码**而不是 catch 解决。
**追问：为什么受检异常要强制？** 让"文件可能不存在"这类调用方必须知晓的故障无法被静默忽略。

**Q2（经典）：final / finally / finalize 的区别？**
三胞胎但毫无关系：final 是修饰符（常量/不可继承/不可重写）；finally 是 try 的收尾块，正常与异常路径都执行；finalize 是 Object 的"回收前回调"——**JDK 9 起已废弃**，替代方案是 try-with-resources 或 Cleaner。
**追问：finalize 为什么废弃？** 执行时机不确定、甚至可能不执行，且拖慢 GC。

**Q3：try-with-resources 的原理？**
语法糖：编译器把 close() 调用编入 finally。多个资源**逆序关闭**（后打开的先关，符合依赖关系）；若 close 也抛异常，它会以 suppressed（被抑制异常）的形式挂在主异常上，不再覆盖业务异常。
**追问：自定义类怎么受益？** 实现 `AutoCloseable` 即可进 try 括号。

**Q4：throw 和 throws 的区别？**
throw 是**语句**，在方法体内抛出一个具体异常对象；throws 是**签名声明**，告知调用方本方法可能抛出哪些（受检）异常，调用方必须处理或继续声明。

**Q5：子类重写方法时能抛出更宽的受检异常吗？**
不能：只能相同、更窄或不抛；非受检异常则无此限制。原因在多态——调用方按**父类声明**写 catch，子类抛宽了就接不住。（对照：返回类型可以协变变"窄"，异常只能变窄不能变宽。）

**Q6：finally 一定执行吗？finally 里写 return 会怎样？**
`System.exit()`、JVM 崩溃、进程被 kill 时不执行；其余路径（含 try 中 return、catch 匹配）都执行。finally 里 return 是**禁手**：它会吞掉 try 的返回值，甚至吞掉正在传播的异常。

**Q7：生产代码怎么防 NPE？**
组合拳：契约先行（参数用 `Objects.requireNonNull` 快速失败）、用 `Optional<T>` 表达"可能没有"、从集合/数据库取出的包装类型拆箱前判空（案例见[数据类型与变量](../数据类型与变量/知识详解.md)第 4 段）。

## 六、实际应用与取舍

- **分层处理**：DAO 层抛 SQLException → Service 层包装成业务异常 → Controller 层统一转错误响应——Spring 的 `@ControllerAdvice` 全局异常处理就是这个思想的框架化。
- **可恢复**（重试、降级）才 catch；不可恢复就上抛或快速失败。
- 自定义异常体系：一个 `BaseException` + 业务子类，让调用方能按业务粒度捕获。

## 七、可继续学习的方向

- [接口与抽象类](../接口与抽象类/知识详解.md)：`AutoCloseable` 就是接口契约的实例。
- Lambda 与 `Optional`：用返回值表达"可能没有"，减少 NPE。
- 并发中的异常：线程里抛出的异常 catch 不住，需要 `UncaughtExceptionHandler`。
- Spring 全局异常处理 `@RestControllerAdvice`。
