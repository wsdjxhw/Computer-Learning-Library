# 反射与注解

## 学习目标

- 理解 Class 对象是什么，掌握三种获取方式。
- 会用反射查看类的成员、动态创建实例、调用方法、访问私有字段。
- 理解注解的本质（贴在代码上的标签）与 `@Retention`/`@Target` 两个元注解。
- 通过"注解 + 反射生成 SQL"体会框架的基本套路。

**前置知识**：[面向对象三大特性](../面向对象三大特性/知识详解.md)（类与对象的关系）、[接口与抽象类](../接口与抽象类/知识详解.md)、[异常处理](../异常处理/知识详解.md)。
**适用范围**：Java 语言核心；Spring/MyBatis/JUnit/Jackson 等一切框架的地基。

---

## 一、本节解决什么问题

正常写代码是"编译期就知道类型"：`new User()`、`user.getName()`。但框架面对的是**编译期不认识的类**——Spring 启动时扫描你的 Controller，JUnit 发现你的 `@Test` 方法，Jackson 把任意类转 JSON。它们靠的就是两样东西：

- **反射**：程序在运行期"看着类本身干活"——拿到类有哪些字段方法、创建实例、调用方法；
- **注解**：给类/方法/字段贴上"标签"，让框架通过反射读到标签后决定怎么处理你。

## 二、核心原理

### 2.1 Class 对象：类本身的"说明书"

JVM 加载每个类时会在堆里创建**唯一一个** `Class` 对象，记录这个类的全部元信息（字段表、方法表、构造器、注解……）。三种获取方式殊途同归——`obj.getClass()`、`User.class`、`Class.forName("全限定名")` 拿到的是**同一个对象**（示例第 1 段直接验证 `==` 为 true）。

区别在使用场景：已有实例用 getClass；编译期已知类型用类字面量；**只有字符串名字**（配置文件、跨包动态加载，如 JDBC 驱动类）用 forName。

### 2.2 反射 API 一览

| 操作 | 方法 |
| --- | --- |
| 查字段 | `getDeclaredFields()`（本类全部，含 private）/ `getFields()`（仅 public，含继承） |
| 查方法 | `getDeclaredMethods()` / `getMethod(名字, 参数类型...)` |
| 查构造器 | `getDeclaredConstructor(参数类型...)` |
| 创建实例 | `con.newInstance(参数...)` |
| 调用方法 | `method.invoke(目标对象, 参数...)` |
| 读/写字段 | `field.get(对象)` / `field.set(对象, 值)`，private 需先 `setAccessible(true)` |

注意 `getDeclaredXxx` 与 `getXxx` 的分野：declared = "本类声明的（不论访问级别）"，不带 declared = "公开的（含从父类继承的）"。

### 2.3 注解：标签 + 读取协议

注解**本身不做任何事**——它只是贴在代码上的结构化标签（名字 + 若干属性），必须有程序去读它才有意义。自定义注解要认识两个"注解的注解"（元注解）：

- **`@Retention`**：标签存活多久。`SOURCE`（编译后丢弃，如 @Override）、`CLASS`（进 class 文件但运行期不可见，**默认值**）、`RUNTIME`（运行期可被反射读到）。**想让反射读到的注解，必须显式声明 RUNTIME**——这是最容易踩的坑。
- **`@Target`**：标签能贴在哪（类/方法/字段/参数……）。

属性名叫 `value` 时，使用处可以省略 `value =` 直接写值。

### 2.4 注解 + 反射 = 框架的基本套路

```text
你写的类贴上注解（@MyTable/@MyColumn、Spring 的 @Component、JUnit 的 @Test）
      ↓
框架启动时扫描拿到 Class 对象
      ↓
反射读注解 → 知道该干什么 → 反射执行（建实例/调方法/映射字段）
```

示例第 5 段用 30 行实现了"注解标记的类 → CREATE TABLE 语句"，这就是 MyBatis、Jackson 序列化、Spring 依赖注入的最小原型。

## 三、示例代码逐段讲解

示例文件：`示例代码.java`（与下述段落编号一一对应；主类 `ReflectionDemo` 在文件最前）

**第 1 段：获取 Class**。三种方式拿到的对象 `==` 相等；单文件源码模式类在默认包，`forName("User")` 即可（工程代码里要写全限定名 `com.x.User`）。

**第 2 段：解剖 User**。getDeclaredFields/Constructors/Methods 打印成员清单；方法返回顺序不保证，别依赖遍历顺序。

**第 3 段：动态操作**。按参数类型取构造器 `newInstance("小红", 20)`；`invoke` 调 getName；`setAccessible(true)` 越过 private 读写 age——这就是反射"破坏封装"的能力（单例被它击穿也是同理）。

**第 4 段：读注解**。`isAnnotationPresent` + `getAnnotation` 读出 @MyTable 的表名；顺带解释 @Override 为什么读不到（SOURCE 级）。

**第 5 段：生成 SQL**。遍历字段，带 @MyColumn 的映射成数据库列，拼出建表语句——框架套路完整落地。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 自定义注解反射读不到 | 默认 @Retention 是 CLASS；要读必须显式 `RetentionPolicy.RUNTIME` |
| 以为注解"执行"了逻辑 | 注解只是数据；逻辑在读取它的框架代码里 |
| 分不清 getDeclaredXxx / getXxx | declared=本类全部（含 private）；非 declared=public（含继承） |
| 热路径频繁反射 | 反射比直接调用慢（访问检查、装箱、无法内联），框架都会缓存 Method/Field |
| setAccessible 当普通技巧用 | 破坏封装且在高版本 JDK 对 JDK 内部类受限（模块系统） |
| newInstance 没有构造器参数类型 | `getDeclaredConstructor(String.class, int.class)` 按类型匹配，写错反射 NoSuchMethodException |
| forName 拼错类名 | ClassNotFoundException；注意默认包与全限定名的差别 |

**排查思路**：注解读不到先查 @Retention；NoSuchMethod/Field 检查参数类型与 declared/public 的选择； IllegalAccessException 是忘了 setAccessible。

## 五、八股追问

反射与注解是"框架题"的前置八股，高频问法如下。

**Q1（必考）：什么是反射？有什么用？**
程序在**运行期**通过 Class 对象检查和操作类成员（创建实例、调方法、改字段）的能力。用途一句话：**让编译期未知的类也能被处理**——IoC 容器实例化 Bean、ORM 映射字段、JSON 序列化、注解驱动的各类框架，全是反射。
**追问：原理是什么？** JVM 加载类时把元信息（字段/方法表）存进方法区/元空间，堆上生成唯一的 Class 对象做入口，反射 API 就是查这些元数据再执行。

**Q2：三种获取 Class 的方式有何区别？**
`getClass()` 拿运行时真实类型；`类.class` 编译期已知、最安全；`Class.forName(名字)` 按字符串加载。
**追问（高频）：forName 和 类.class 的隐藏差异？** `forName` 默认会**执行类初始化**（静态块运行），`类.class` 只加载不初始化——所以 JDBC 注册驱动用 forName（要触发静态块里的 DriverManager.registerDriver）。

**Q3：注解的本质是什么？**
一种可被编译器/工具/运行时读取的**结构化元数据**。编译后本质是继承了 `java.lang.annotation.Annotation` 接口的特殊类型；RUNTIME 级注解通过反射以**动态代理**对象的形式返回（所以 `table.value()` 像方法调用）。

**Q4（必考）：@Retention 的三个值分别什么含义？**
SOURCE——只留在源码（@Override、@SuppressWarnings，编译器用完即弃）；CLASS——进 class 文件但运行期不可见（**默认值**，极少用）；RUNTIME——运行期可被反射读取（框架注解全是它：@Component、@Test）。
**追问：@Target 呢？** 限定注解能贴的位置（TYPE/FIELD/METHOD/PARAMETER...），贴错位置直接编译报错。

**Q5：反射能访问 private 吗？有什么问题？**
能，`setAccessible(true)` 关闭访问检查。问题：① 破坏封装，违背类的设计意图；② 经典面试题——**反射可以击穿单例**（绕过私有构造器再 new 一个），防御办法是构造器里加"已存在则抛异常"的标志位或用枚举单例；③ JDK 9+ 模块系统对跨模块 setAccess 到 JDK 内部类有限制（IllegalAccessError）。

**Q6：反射为什么慢？框架为什么还用？**
慢在：方法查找、访问检查、参数装箱、JIT 难以内联优化。框架的解法是**缓存** Method/Field 对象、方法内联化（LambdaMetafactory、MethodHandle），把反射成本摊薄到启动期一次。

**Q7：Spring 里哪些地方用了反射与注解？**
@Component/@Autowired 扫描注入（读注解 + 构造器反射建实例）、@RequestMapping 路由（读方法注解 + Method.invoke 调 handler）、@Transactional/AOP 动态代理、Jackson 按 getter 反射序列化——"注解声明 + 反射执行"贯穿始终。

## 六、实际应用与取舍

- **写业务代码**：很少直接用反射——用注解声明，让框架去反射。
- **写"半框架"性质的东西**：自定义注解 + 扫描做参数校验、日志埋点、权限标记、报表字段映射（示例第 5 段的放大版）。
- **通用工具**：BeanUtils 拷贝属性、JSON 序列化、`@Override` 这类编译检查。
- **取舍**：能在编译期用接口/泛型解决的，不要留到运行期反射（丢类型安全、难重构、慢）；确需动态性时优先考虑接口 + 策略模式。
