# Lambda 与 Stream

## 学习目标

- 理解函数式接口（单抽象方法）是 Lambda 的类型基础。
- 掌握方法引用的四种形式。
- 理解 Stream 的"流水线"模型：中间操作惰性、终端操作触发。
- 会用 `collect`（groupingBy/averagingInt/joining）与 `reduce` 完成分组统计。
- 掌握 Optional 的定位：用类型系统表达"可能没有"。

**前置知识**：[接口与抽象类](../接口与抽象类/知识详解.md)（接口是契约）、[泛型](../泛型/知识详解.md)（`Stream<T>`、`Function<T,R>` 全是泛型）、[ArrayList](../../集合框架/ArrayList/知识详解.md)（集合遍历的"前世"）。
**适用范围**：Java 8+ 的核心编程范式；集合处理、数据转换的现代标准写法。

---

## 一、本节解决什么问题

Java 8 之前，"把行为当数据传"只能写匿名内部类——五行模板包一行逻辑；集合处理则是一层层 for 循环 + 中间变量。Lambda 解决前者（**行为参数化**），Stream 解决后者（**声明式数据处理**：说"要什么"而不是"怎么循环"）。两者配合加上 Optional（"可能没有"显式化），构成 Java 函数式编程的三件套。

## 二、核心原理

### 2.1 函数式接口：Lambda 的类型

Lambda 不是独立类型，它是**函数式接口的实例**——接口有且只有一个抽象方法（`@FunctionalInterface` 让编译器把关），`(a, b) -> a + b` 就能赋给它。JDK 预置了一整族：`Runnable`（无参无返回）、`Comparator<T>`、`Function<T,R>`（转换）、`Predicate<T>`（判断）、`Consumer<T>`（消费）。

### 2.2 方法引用：Lambda 的缩写

判断标准：**lambda 体只是转发调用一个已有方法**时，就能改成 `::` 写法。四种形式：

| 形式 | 写法 | 等价 lambda |
| --- | --- | --- |
| 类::静态方法 | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| 类::实例方法 | `String::length` | `s -> s.length()`（第一个参数当接收者） |
| 对象::方法 | `prefix::concat` | `s -> prefix.concat(s)` |
| 类::new | `StringBuilder::new` | `s -> new StringBuilder(s)` |

### 2.3 Stream：三段式流水线

```text
数据源.list() → 中间操作（filter/map/sorted/distinct/limit/peek，可链多层）
           → 终端操作（collect/forEach/count/reduce/findFirst，只能一个）
```

两条铁律：**中间操作是惰性的**——只登记不执行，没有终端操作整条流水线静默不动（示例第 3 段现场验证）；**流是一次性的**——用过就废，再操作抛 IllegalStateException。流不存数据，只定义"怎么处理"。

### 2.4 collect：终端操作的主力

`Collectors.toList()/toSet()` 收集；`joining(", ", "[", "]")` 拼接；`groupingBy(分类函数)` 分组；`groupingBy(f, downstream)` 分组后再统计（`averagingInt`/`counting`/`summingInt`）——一行等价于传统写法"建 Map + 判空 + 循环累加"五步。`reduce(初值, BinaryOperator)` 把流折叠成一个值。

### 2.5 Optional

容器型返回值：`Optional<Employee>` 明确告诉调用方"可能查不到"，逼你用 `map/orElse/orElseThrow` 处理空的情况，替代"返回 null + 调用方忘判空"的祖传 bug。`orElse` 立即计算默认值，`orElseGet` 惰性求值（默认值很贵时用）。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 流被消费后再用 | 抛 IllegalStateException；要再次处理就重新 `list.stream()` |
| 只链中间操作，以为执行了 | 惰性求值——没有终端操作整条链白写 |
| 循环里创建流 / 大数据频繁开流 | 流创建有成本，热路径注意复用数据源 |
| lambda 里改外部局部变量 | 只能捕获 effectively final 变量；要可变状态用数组/AtomicXXX/收集结果 |
| `peek` 当 forEach 用 | peek 设计给调试；带副作用的处理放终端操作 |
| Optional 当字段/方法参数 | 设计定位是**返回值**；字段/参数用它反而添乱（序列化也不支持） |
| 无脑 parallelStream | 小数据量反而慢；共享可变状态会出错；IO 场景线程数不受控（见[线程池](../../并发编程/线程池/知识详解.md)） |

**排查思路**："流没有输出" → 查终端操作是否存在；"IllegalStateException: stream has already been operated upon" → 流复用；"类型不匹配"编译错 → 函数式接口的签名对不上，画一下参数和返回类型。

## 五、八股追问

Lambda/Stream 是 Java 8 的门面考点，函数式接口与惰性求值是追问焦点。

**Q1（必考）：Lambda 与匿名内部类的区别？**
四点：① **this 指向**——匿名类的 this 是匿名类实例自身，lambda 的 this 是外围类实例；② **字节码**——匿名类编译出独立 class 文件，lambda 编译成 invokedynamic 指令、运行时由 LambdaMetafactory 生成（不落地 class 文件）；③ **语义**——lambda 没有类型，它的类型由目标函数式接口推断；④ lambda 只能实现函数式接口，匿名类可实现任意接口/抽象类。

**Q2：为什么 lambda 只能捕获 effectively final 的局部变量？**
实例字段存在对象里、有明确的生命周期，而局部变量在栈帧上——lambda 捕获的是**值的拷贝**，若允许修改，拷贝与原值分道扬镳会造成语义混乱，干脆要求"事实不变"。需要累加这类可变状态就收集结果（reduce/collect）而不是改外部变量。

**Q3：函数式接口的判定标准？**
**有且只有一个抽象方法**——default/static/Object 的 public 方法都不算数。`@FunctionalInterface` 注解让编译器在写错时（写了两个抽象方法）直接报错。

**Q4（必考）：什么是惰性求值？Stream 怎么体现？**
中间操作只把"处理步骤"登记进流水线，直到终端操作才一次性开闸，且**短路操作**（limit、findFirst、anyMatch）能让上游提前收工——`findFirst` 命中第一个就不再遍历剩余元素。示例第 3 段的 peek 无输出是惰性的直接证据。

**Q5：map 和 flatMap 的区别？**
map：一进一出（`Stream<R>`）；flatMap：一进多出再摊平（`Stream<Stream<R>>` → `Stream<R>`）——"订单列表转商品列表"这种一对多展开必须用 flatMap，map 只会得到流的嵌套。

**Q6：reduce 和 collect 有什么不同？**
reduce 把流折叠成**一个不可变值**（数值累加、字符串拼接）；collect 是**可变归约**——把元素累积进容器（List/Map/StringBuilder），适合分组、去重、装集合。规则：结果是不可变标量用 reduce，结果是容器用 collect。

**Q7：Optional 的设计目的是什么？常见误用？**
目的：让"可能没有"进入**方法签名**，编译器逼调用方面对空的情况，消灭"忘了判 null"型 NPE。误用：`optional.get()` 不判直接取（换了个地方裸奔）、当字段/参数用、`isPresent()+get()` 的伪函数式写法（不如 map/orElse 链）。

**Q8：parallelStream 的原理与坑？**
底层用公共 ForkJoinPool（并行度 ≈ CPU 核数 - 1）。坑：小数据量开并行的线程调度成本 > 收益；任务里有阻塞 IO 会占死公共池拖累全局；操作共享可变状态直接出并发 bug；forEach 顺序不保证。经验：数据量大 + 元素处理贵 + 无共享状态 + 无阻塞，才值得 parallel。

## 六、实际应用与取舍

- **集合加工**：过滤/映射/分组/统计的首选写法，替代 for + if + 临时集合三件套。
- **与 IO 结合**：`Files.lines` 逐行处理日志、`Files.walk` 遍历目录（见[文件与Path](../../IO流/文件与Path/知识详解.md)）。
- **API 设计**：`Comparator.comparing(...).thenComparing(...)` 组合排序；返回 Optional 表达可空查询。
- **取舍**：简单的一次遍历，for-each 更直白；流的强项是"多步链式变换 + 声明式分组统计"。别为了炫技把简单循环流化。
