# 字符串

## 学习目标

- 理解 String **不可变（immutable）**的含义与设计理由。
- 理解字符串池，掌握 `==` 与 `equals` 的区别（面试高频）。
- 掌握常用字符串方法与文本块。
- 理解循环拼接的性能问题，会正确使用 StringBuilder。

**前置知识**：[数据类型与变量](../数据类型与变量/知识详解.md)（引用类型的概念）。
**适用范围**：Java 语言基础；字符串是 Java 出场率最高的类型。

---

## 一、本节解决什么问题

Java 没有"字符串基本类型"——String 是**引用类型**，本质是一个 `final char[]`（JDK 9 后为 `byte[]`）包装成的对象。理解"它是对象、且不可变"，就能解释日常遇到的三类现象：为什么修改方法"不生效"、为什么 `==` 时对时错、为什么循环拼接会卡。

## 二、核心原理

### 2.1 不可变（Immutable）

String 内部的字符数组声明为 `final` 且不提供任何修改入口，所以 `concat`、`replace`、`toUpperCase` 等"修改"方法全部**返回新对象**，原串永不改变：

```java
String s = "abc";
s.concat("def");       // 返回了新串，但没人接 → s 还是 "abc"
s = s.concat("def");   // s 改指向新对象，旧串 "abc" 依然存在于别处
```

**为什么设计成不可变**：① 可以安全共享（字符串池的前提）；② 天然线程安全；③ hashCode 可缓存——String 做 HashMap 的键高效又可靠（可变对象做键会"存进去找不回"，参见[哈希表](../../../../数据结构与算法/数据结构/哈希表/知识详解.md)的可哈希性一节）。

### 2.2 字符串池与 `==` 陷阱

JVM 维护一个字符串池：**字面量**创建时先查池，同内容直接复用；**`new String(...)`** 强制在堆里新建对象：

```java
String a = "hello";              // 池中对象
String b = "hello";              // 复用 a 的同一个对象
String c = new String("hello");  // 堆里新对象

a == b        // true：同一对象
a == c        // false：不同对象
a.equals(c)   // true：内容相同
```

`==` 比较引用（是不是同一个对象），`equals` 比较内容。**比较字符串内容永远用 `equals`**——与 Integer 缓存陷阱同理，`==` 在池内碰巧为 true，超出池就翻车。

### 2.3 循环拼接与 StringBuilder

String 不可变 ⇒ 每次 `+=` 都要**新建串并整体复制**。循环 n 次的累计复制量是 O(n²)：

```java
String s = "";
for (...) { s += "a"; }          // 每轮生成一个更长的全新字符串 → O(n²)

StringBuilder sb = new StringBuilder();
for (...) { sb.append("a"); }    // 内部可变字符数组，追加 O(1)，必要时扩容
String result = sb.toString();   // 拼完一次性转回 String
```

实测拼接 10000 次：`+=` 约 17 毫秒，StringBuilder 不足 1 毫秒；字符串越长差距越大。注意：**单行拼接直接用 `+` 即可**（编译器会优化），只有循环/多次拼接才需要 StringBuilder。多线程场景用 `StringBuffer`（同步版，单线程没必要）。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 用 `==` 比较字符串 | 一律 `equals`；`equalsIgnoreCase` 忽略大小写 |
| 调用"修改"方法后不接返回值 | concat/replace/strip 都返回新串，原串不变 |
| 循环里用 `+=` 拼接 | 换 StringBuilder；单行拼接用 `+` 没问题 |
| substring 越界 | `[2, 9)` 含头不含尾，end 超过 length 抛 `StringIndexOutOfBoundsException` |
| split 的正则 | 参数是正则表达式，`.` `|` 等特殊字符要转义（`\\.`） |
| 忽略编码 | char 是 UTF-16 码元；处理文本 IO 时明确指定字符集 `StandardCharsets.UTF_8` |

**排查思路**："改了没反应" → 十有八九没接返回值；"比较时对时错" → 把 `==` 换 `equals`；"越拼越慢" → 检查循环里的 `+=`。

## 五、八股追问

String 是面试出场率最高的类之一，且题题都能追问到底层设计。

**Q1（必考）：String 为什么设计成不可变？**
四个理由层层递进：① **字符串池**存在的前提——同内容共享一个对象，可变则一处改动全局遭殃；② hashCode 可以**缓存**——做 HashMap 的键高效可靠；③ 天然**线程安全**，可自由跨线程传递；④ **安全性**——路径、URL、类名等不可被中途篡改。
**追问：怎么做到的？** final 类（防继承覆盖）+ 私有 final 数组 + 不提供任何修改方法（所有"修改"都返回新对象）。真要可变就用 StringBuilder/StringBuffer。

**Q2：`String s = new String("abc")` 创建了几个对象？**
最多 2 个：常量池里没有 "abc" 时，先在池中创建字面量，再在堆里 new 一个；池里已有则只 new 堆对象这 1 个。
**追问：`intern()` 干什么？** 返回常量池中同内容字符串的引用；JDK 7 起池在堆中，首次 intern 直接记录该堆对象的引用。

**Q3：字符串的 `==` 和 `equals`？**
`==` 比引用、`equals` 比内容，比较内容**永远用 equals**。字面量 `==` 碰巧为 true 是因为池复用——测试时成立、换成 `new` 或外部输入就翻车，这是最典型的"侥幸 bug"。

**Q4：String / StringBuilder / StringBuffer 怎么选？**
只读文本 String；单线程频繁拼接 StringBuilder；多线程共享同一拼接缓冲才 StringBuffer（方法加 synchronized，单线程用它白付锁开销）。
**追问：单行 `+` 拼接要换成 StringBuilder 吗？** 不用——编译期常量直接折叠，JDK 9+ 运行期拼接也由 indy 指令优化；**只有循环/多次拼接**才必须手写 StringBuilder。

**Q5：循环里 `+=` 拼接为什么慢？**
不可变 ⇒ 每轮 `+=` 都新建一个更长的串并整体复制，累计 O(n²)；StringBuilder 内部是可变数组，追加均摊 O(1)。
**追问：StringBuilder 也扩容吗？** 会，默认容量 16，装满同样翻倍复制——预知大小用 `new StringBuilder(n)` 预分配（同 ArrayList 的道理，原理见[数据结构/数组](../../../../数据结构与算法/数据结构/数组/知识详解.md)）。

**Q6：String 的 hashCode 为什么用 31 做乘数？**
`h = 31 * h + c`。31 是奇质数：乘偶数会丢掉溢出位信息、分布变差；`31 * i` 恰好能被优化成 `(i << 5) - i`，乘法变移位；再有就是历史沿袭（老牌哈希算法惯例）。
**追问：hashCode 每次都算吗？** 首次计算后缓存在 hash 字段——不可变对象才敢缓存，这是"不可变设计红利"的直接证据。

**Q7：字符串常量池在哪里？**
JDK 7 起从方法区（永久代）移到了堆。原因：永久代大小固定、容易 OOM；移到堆后池内对象可被正常 GC 回收。

## 六、实际应用与取舍

- 键名、配置、消息文本等只读场景：String 是最合适的类型（可共享、可缓存 hash）。
- 解析文本：split + indexOf/substring 组合，或 `String.format`/`formatted` 拼模板。
- 频繁拼接、字符流处理：StringBuilder。
- 大量字符串相等比较（如爬虫去重）：考虑 `intern()` 或直接用 HashSet。
