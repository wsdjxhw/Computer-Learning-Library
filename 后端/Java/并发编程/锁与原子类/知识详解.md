# 锁与原子类

## 学习目标

- 说清 synchronized 的局限，以及 ReentrantLock 补上的四项能力（tryLock、可中断、公平锁、多条件队列）。
- 掌握 lock/unlock 三件套写法与可重入语义。
- 用 Condition 写出"两个等待室"的生产者-消费者，对比 wait/notify。
- 理解读写锁的并发策略（读读共享、读写/写写互斥）与适用场景。
- 掌握 CAS 的原理与手写自旋，认识它的两大代价：自旋空转、ABA。

**前置知识**：[多线程基础](../多线程基础/知识详解.md)（synchronized、wait/notify、volatile——本篇处处与之对照）。
**适用范围**：JUC（java.util.concurrent）中"锁与原子"这一族；高并发计数、读多写少配置、精细线程协作。

## 一、本节解决什么问题

synchronized 有三个"不够"：

1. **拿不到锁只能傻等**——没有"试一下""等到几点""等的时候能被打断"这些选项，死锁了也只能一起卡死。
2. **一个监视器只有一个等待队列**——notifyAll 是全村广播：生产者消费者混在一个等待室里互相叫醒，效率低还可能叫错人。
3. **无法公平排队**——锁释放时谁抢到算谁的，某些线程可能永远抢不到（饥饿）。

再加上一个老问题：`volatile` 保证可见性但不保证原子性，`count++` 仍会丢更新——计数这类小场景需要比加锁更轻的方案。本篇就是解决这些问题的"进阶货架"：ReentrantLock、Condition、ReadWriteLock、AtomicInteger（CAS）。

## 二、核心原理

### 2.1 ReentrantLock：显式锁的标准三件套

```java
lock.lock();          // ① 先加锁（在 try 之外）
try { ...临界区... }   // ② try 里干活
finally { lock.unlock(); }   // ③ finally 必解锁——漏了就是事故级死锁
```

**可重入**：同一线程可以对同一把锁连续 lock 多次（内部持锁计数 +1），unlock 逐一抵消；不会把自己锁死。synchronized 同样可重入——重入是"锁"这个抽象的基本要求（否则嵌套调用自己的同步方法就死锁了）。

### 2.2 tryLock：synchronized 给不了的"抢不到就算了"

`tryLock()` 立即返回成功/失败；`tryLock(n, unit)` 限时等待。用途：避免无限排队、按序加锁防死锁（两个锁都 tryLock，失败就全释放重来）。

### 2.3 Condition：一把锁，N 个等待室

```java
ReentrantLock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();   // 等待室1：生产者
Condition notEmpty = lock.newCondition();   // 等待室2：消费者
```

对照表（语义一一对应，能力升级）：

| wait/notify 世界 | Condition 世界 | 升级点 |
| --- | --- | --- |
| synchronized(obj) | lock.lock() | — |
| obj.wait() | condition.await() | 可限时、可中断 |
| obj.notifyAll() | condition.signalAll() | **按条件唤醒**（notFull 只叫生产者） |
| 一个对象一个等待队列 | 一把锁 N 个 Condition | 精确制导，不再全村广播 |

`await/signal` 同样必须**持有锁**时调用；等待条件同样用 **while** 检查（防虚假唤醒）——两条纪律与 wait/notify 完全一致。

### 2.4 ReadWriteLock：按操作类型分道

| | 读锁 | 写锁 |
| --- | --- | --- |
| 读锁 | **兼容**（并发读） | 互斥 |
| 写锁 | 互斥 | 互斥 |

读不改数据，天生可并发；写则与一切互斥（防止读到写了一半的状态）。适用**读多写少**：配置、缓存、路由表。注意"读锁里别改数据"——读写锁防的是并发写坏数据，防不了你自己写错代码。

### 2.5 CAS 与原子类：不用锁的线程安全

CAS（Compare-And-Set）三操作数：**内存地址 V、期望值 E、新值 N**——"我认为 V 现在是 E，是的话就改成 N，不是就告诉我失败"。由 CPU 一条原子指令实现（x86 的 cmpxchg），JVM 通过 Unsafe/VarHandle 调用。

`AtomicInteger.incrementAndGet()` 内部就是一个 CAS 自旋循环（示例第 5 段手写了一遍）：

```java
do {
    oldValue = get();          // 读现值
    newValue = oldValue + 1;   // 算新值
} while (!compareAndSet(oldValue, newValue));  // 没被抢就写入；被抢就重读重试
```

这是**乐观策略**：先假定没冲突，冲突了再重试；synchronized 是**悲观策略**：先锁住再说。乐观免了加锁开销，代价有二：

- **自旋空转**：高竞争下大量线程反复失败重试，CPU 空转（LongAdder 用分段计数解决——见八股追问 Q6）。
- **ABA 问题**：值从 A 被改成 B 又改回 A，CAS 以为"没动过"（见 Q4）。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| unlock 不放 finally | 异常路径漏解锁 → 锁永久被占；lock() 在 try **外**、unlock() 在 finally 内 |
| lock() 写在 try 里面第一行 | 若 lock 抛异常，finally 的 unlock 会对未持有的锁操作 → IllegalMonitorStateException |
| await/signal 写在 lock 之外 | 与 wait/notify 一样必须持锁调用，否则 IllegalMonitorStateException |
| Condition 等待用 if 判断 | 用 while——醒来后条件可能又被改变（虚假唤醒防线不能拆） |
| 读锁的方法里修改数据 | 读写锁按"你声明的操作类型"放行，不检查你实际干了什么 |
| 以为 Atomic 类是万能线程安全 | 单个变量原子；**多个原子变量的组合操作不原子**（先 a 再 b 中间可被插入），仍需锁 |
| CAS 只看值就以为没问题 | ABA：值转一圈回到原点，CAS 察觉不到"中间发生过变化" |
| 高竞争计数仍用 AtomicLong | 自旋浪费大，统计场景换 LongAdder（见八股 Q6） |

**排查思路**："疑似死锁" → jstack 看 BLOCKED 线程持有什么锁等什么锁（jstack 自带死锁检测）；"锁性能差" → jstack 看锁上排队的线程数，考虑缩小临界区/换读写锁/换原子类。

## 五、八股追问

锁与 CAS 是并发面试的**核心战场**，以下按频率排布。

**Q1（必考）：synchronized 和 ReentrantLock 的区别？**
六个维度：① 层次——关键字(JVM 层) vs JDK 类(API 层)；② 释放——异常时自动释放 vs 必须手动 unlock（忘记=死锁）；③ **可中断**——synchronized 等锁不可中断，lockInterruptibly() 可；④ **超时**——tryLock(超时) 支持限时获取；⑤ **公平锁**——ReentrantLock 可选公平(true)，synchronized 只有非公平；⑥ **条件队列**——synchronized 一个监视器一个等待队列，ReentrantLock 可配多个 Condition。
**追问：功能是超集，为什么日常还推荐 synchronized？** 简单场景写法更短、不会漏 unlock，且 JVM 持续优化（锁升级）；ReentrantLock 的增益只在"需要 tryLock/可中断/多条件/公平"这些高级能力时才用得上。

**Q2（高频）：公平锁和非公平锁的区别？为什么默认非公平？**
公平锁按申请顺序排队（FIFO），非公平锁允许插队（释放瞬间新来的线程可直接抢到）。默认非公平是因为**吞吐高**：唤醒一个排队线程需要时间，非公平让"正在 CPU 上的线程"趁热直接拿锁，省去上下文切换；代价是可能饥饿。ReentrantLock(true) 开公平；synchronized 只有非公平。

**Q3（必考）：CAS 是什么？底层怎么实现？**
Compare-And-Set：内存值 V、期望值 E、新值 N；V==E 才写入 N 并返回成功，否则失败。底层是 CPU 原子指令（x86 cmpxchg、ARM LL/SC），Java 经 Unsafe/VarHandle 调用，是**硬件级原子性**，不需要锁。
**追问：compareAndSet 是怎么保证原子性的？** 单条 CPU 指令 + 缓存锁/总线锁保证该指令执行期间缓存行不被其他核修改。

**Q4（高频）：什么是 ABA 问题？怎么解决？**
线程 1 读到 A；期间线程 2 把 A→B→A；线程 1 的 CAS 看到 A，以为"从没人动过"，实际值经历过变化。纯数值累加场景无害（加回来结果也对），但**带状态的结构**（无锁栈：A 节点被弹出又压回，next 已变）会出错。解法：**AtomicStampedReference** 给值加版本号（A,1→B,2→A,3，版本不同 CAS 失败）；AtomicMarkableReference 用布尔标记。
**追问：AtomicInteger 有 ABA 问题吗？** 有这个现象但通常无害（整数值只关心最终值）；引用类型/复合状态才是重灾区。

**Q5：AtomicInteger 为什么不用锁也线程安全？incrementAndGet 的实现？**
基于 CAS 自旋：读现值→算新值→CAS 失败重试（示例第 5 段手写了这段循环）。JDK 8 中是 Unsafe.getAndAddInt 的循环；JDK 9+ 换成 VarHandle 实现，思路不变。
**追问：这比加锁好在哪？坏在哪？** 好：无阻塞、无上下文切换、读的人完全不受影响。坏：高竞争下自旋空转烧 CPU；一次只保一个变量。

**Q6（高频）：LongAdder 和 AtomicLong 的区别？**
AtomicLong：所有线程 CAS 同一个值——高竞争下大量自旋失败。LongAdder：把值**分段**（base + Cell 数组），各线程 CAS 不同段，sum() 时再相加——以空间换竞争度。**追问：怎么选？** 高并发**统计计数**（QPS、打点）用 LongAdder；需要**精确的即时值或 CAS 语义**（做全局序号、限流阈值判断）用 AtomicLong——LongAdder 的 sum 是"各段相加的瞬时快照"，不是原子点。

**Q7：ReadWriteLock 的原理？写锁能降级成读锁吗？**
内部一个同步器维护状态：读锁共享计数 + 写锁独占。读读并行、读写/写写互斥。**写锁可降级**：持有写锁时可直接获取读锁再释放写锁（保证降级瞬间数据不被别人改）；**读锁不可升级**：两个读线程同时申请升级会死锁。JDK 8 的 StampedLock 还提供"乐观读"——读时不加锁，读完校验期间有没有写发生，没有则直接用（性能更高，适合极读多写少）。

**Q8：Condition 相比 wait/notify 的优势？**
① 一把锁多个条件队列，signal 精确唤醒同类（notifyAll 广播还叫错人）；② await 支持不可中断/限时等变体；③ 是 Lock 体系的组成部分，可与 tryLock 等能力组合。典型应用就是 ArrayBlockingQueue 内部的 notFull/notEmpty 两个 Condition（见[并发工具类](../并发工具类/知识详解.md)）。

**Q9（必考连线）：死锁产生的四个必要条件？怎么破坏？**
互斥、持有并等待、不可剥夺、循环等待——四者同时成立才死锁。破坏任意一个即可：**循环等待**最常破坏（所有线程按相同顺序加锁）；**不可剥夺**可用 tryLock 超时（拿不到第二把就释放第一把重来）。工具：jstack 死锁检测、`ThreadMXBean.findDeadlockedThreads()`。

**Q10（高频）：synchronized 的锁升级过程？**
JDK 6 以后：无锁 → **偏向锁**（只有一个线程反复获取，在对象头记线程 id，近乎零成本）→ **轻量级锁**（第二个线程来竞争，CAS 自旋）→ **重量级锁**（自旋失败/竞争加剧，膨胀为 monitor，涉及内核态阻塞）。升级不可逆。JDK 15 起偏向锁默认废弃（维护成本高于收益）。
**追问：synchronized 优化还有哪些？** 锁消除（JIT 证明无竞争直接删）、锁粗化（相邻小临界区合并）、自适应自旋。

## 六、实际应用与取舍

- **高并发计数/打点**：LongAdder（QPS 统计）、AtomicInteger（全局序号）——比锁轻一个量级。
- **读多写少的配置/缓存**：ReadWriteLock（或 StampedLock 乐观读），读吞吐随核数扩展。
- **防死锁的加锁顺序**：多个锁按固定顺序获取，或 tryLock+重试（示例第 2 段的延伸用法）。
- **取代 wait/notify 的协作**：Condition 双等待室（生产者/消费者分流），[线程池](../线程池/知识详解.md)的 BlockingQueue 内部就是这么写的。
- **取舍**：能用"少共享、不可变对象"解决的就不上锁（[多线程基础的取舍](../多线程基础/知识详解.md)依然适用）；上锁优先 synchronized，确有高级需求再换 ReentrantLock。

## 七、可继续学习的方向

- **AQS（AbstractQueuedSynchronizer）**：ReentrantLock/Semaphore/CountDownLatch 的共同地基——state + CLH 等待队列；理解它，JUC 锁族一通百通。
- **LongAdder / LongAccumulator 源码**：分段思想的标准范本。
- **StampedLock**：乐观读的三段式用法与陷阱（不可重入）。
- [并发工具类](../并发工具类/知识详解.md)：同一族 AQS 的另一批封装（Latch/Barrier/Semaphore）。
