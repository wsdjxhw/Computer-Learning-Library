# CompletableFuture 与异步编程

## 学习目标

- 说清 Future 的局限与 CompletableFuture 的解法（回调、编排、异常传播）。
- 熟练区分 thenApply / thenCompose / thenCombine 三兄弟，掌握 allOf/anyOf 并行编排。
- 掌握异常处理三件套：exceptionally / handle / whenComplete 的分工。
- 理解默认线程池的坑（ForkJoinPool.commonPool）与生产规范（自定义池 + 超时）。

**前置知识**：[线程池](../线程池/知识详解.md)（Future/get、ExecutorService）、[Lambda与Stream](../../语言基础/Lambda与Stream/知识详解.md)（函数式接口是 API 的语言底座）。
**适用范围**：异步任务编排——并行调下游、聚合、降级、超时控制；Web 后端异步化与响应式框架的直系前置。

---

## 一、本节解决什么问题

[线程池](../线程池/知识详解.md)的 Future 有两个先天不足：

1. **取结果只能 get() 阻塞或 isDone() 轮询**——没有"完成时通知我"，主线程要么卡死等，要么反复问；
2. **没有编排能力**——"A 完成后接着异步做 B""A、B 都完成再合并""任何一个成功就用哪个""中间出错走降级"这些日常需求，用 Future 写出来是一堆 get + if 的面条。

CompletableFuture 把 Future 升级成**流水线**：每一步完成自动触发下一步，异常沿流水线自动流到出口，支持几十种组合算子——可以理解为"异步版的 Stream"。

## 二、核心原理

### 2.1 两种模型：轮询等待 vs 回调链

```java
// Future：主动问（阻塞/轮询）
while (!future.isDone()) { ...干等... }
String r = future.get();

// CompletableFuture：被动通知（回调链）
CompletableFuture.supplyAsync(() -> 查询())
        .thenApply(d -> 加工(d))     // 上一步完成自动触发
        .thenAccept(r -> 消费(r));   // 无需任何人阻塞等待
```

### 2.2 链式三兄弟（必须一次分清）

| 方法 | 函数签名 | 语义 | 类比 |
| --- | --- | --- | --- |
| thenApply | T → R | **同步加工**：拿到结果直接算出新值 | Stream.map |
| thenCompose | T → CompletableFuture\<R\> | **依赖型异步**：下一步本身又是一个异步任务 | Stream.flatMap |
| thenCombine | (T, U) → R | **汇合型合并**：两条互不依赖的链都完成后合并 | 两路 zip |

选型口诀：下一步是普通计算用 thenApply；下一步又要异步（返回 CF）用 thenCompose；两条独立链最后碰头用 thenCombine。

### 2.3 并行编排：allOf / anyOf

`allOf(cf1, cf2, cf3)`：全部完成才完成——并行调多下游再汇总；**注意返回 CompletableFuture\<Void\>**，join 之后要再从各个原 future 取结果。`anyOf(...)`：任一完成即完成——多副本竞速，最快者胜。

### 2.4 异常传播：流水线的水只会流到出口

中间某步抛异常：**后面的 thenApply 全部跳过**，异常直达最近的异常处理节点——不处理它就一直流到 join()/get()（分别包成 CompletionException / ExecutionException 抛出）。

三件套分工：

| 方法 | 看到异常 | 能改变结果 | 定位 |
| --- | --- | --- | --- |
| exceptionally | 只在异常时 | 是（返回兜底值） | catch：降级 |
| handle | 正常+异常都走 | 是（两个分支都给返回值） | catch+finally 合体：统一收口 |
| whenComplete | 正常+异常都走 | **否（原样透传）** | finally：旁观打日志/埋点 |

### 2.5 线程池与超时（生产必修）

- `supplyAsync(task)` 不传池 → **ForkJoinPool.commonPool()**：全 JVM 共享、为 CPU 密集设计、daemon 线程。把慢 IO 扔进去会占住公共池拖累所有人。
- 生产规范：**传自己的线程池**（隔离、有界、可监控——道理同[线程池篇的规约](../线程池/知识详解.md)）。
- `orTimeout(n, unit)`：超时以 TimeoutException 完结；`completeOnTimeout(v, n, unit)`：超时给默认值。
- `join()` 抛非受检的 CompletionException，`get()` 抛受检的 ExecutionException——代码里 join 写起来更顺，但异常会往外冒。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 链尾不 join/get，main 先退 | commonPool 是 daemon 线程，JVM 不等它——回调还没跑进程就结束了（输出凭空消失的经典元凶） |
| 在 thenApply 里做长时间阻塞 | 它跑在上一环节的线程上，会把该线程占死，拖住整条流水线（阻塞活儿用 thenApplyAsync+专用池） |
| 用 thenCompose 接普通计算 | 功能不炸但套了层 CF；反过来用 thenApply 接异步调用会得到 CF\<CF\<R\>\> 嵌套 |
| allOf 后直接读 allOf 的结果 | allOf 返回 CF\<Void\>，没有结果——join 它只是等齐，结果要从各个原 future 再 join |
| exceptionally 写在链首想兜全程 | 只兜**它之前**的环节；兜全程要放在链尾（或每段局部兜底） |
| 忘了 CompletableFuture 只是"任务描述" | 没 join/get/whenComplete 消费它，异常静默吞掉，任务失败也无感 |
| 默认池跑 IO 密集任务 | commonPool 是共享的 CPU 型池；慢 IO 会饿死同池的其他任务，务必传专用池 |
| 一个池异步套异步（同池依赖） | A 任务在池里又等同池的 B——线程互相等可能饿死（池要够大或分层） |

**排查思路**："异步结果没输出" → 先查是不是没等（join）daemon 线程；"线上偶发超时没兜底" → orTimeout + exceptionally/completeOnTimeout；"异步任务卡死" → jstack 看回调线程堵在哪个阻塞调用上。

## 五、八股追问

CompletableFuture 是并发面试**新一代高频题**，正逐步接管 Future/线程池的一部分出题份额。

**Q1（必考）：Future 和 CompletableFuture 的区别？**
Future 只能 get() 阻塞或 isDone() 轮询取结果，无回调、无编排、无异常链。CompletableFuture：① 回调式（完成自动触发下一步）；② 编排能力（thenCompose 依赖、thenCombine 合并、allOf/anyOf 并行）；③ 异常沿链传播可统一处理；④ 可手动 complete（外部完成结果）、支持超时。
**追问：CompletableFuture 还能用线程池跑吗？** 当然——supplyAsync(task, executor)；不传才默认 commonPool。

**Q2（最高频）：thenApply、thenCompose、thenCombine 的区别？**
thenApply 同步转换（map）；thenCompose 下一步返回 CF（flatMap，依赖型异步）；thenCombine 合并两条独立链（zip）。
**追问①：thenApply 的函数里返回了 CompletableFuture 会怎样？** 得到嵌套的 CF\<CF\<R\>\>——这就是要换 thenCompose 的信号。
**追问②：thenAccept/thenRun 呢？** 消费型（无返回值）与纯通知型（连参数都不看），链条的终点站。

**Q3（高频）：thenApply 和 thenApplyAsync 的区别？不带 Async 的回调到底在哪个线程跑？**
带 Async：强制把下一步提交给线程池（默认 commonPool，或指定 executor）。不带 Async：**谁完成谁执行**——若上一步已算完，就在调用 thenApply 的线程（如 main）立刻执行；未完成则在完成那个任务的线程（如池里的 worker）执行。所以不带 Async 的回调线程是"看运气"的，对线程有要求（如操作 ThreadLocal/需并行）就明确 Async+指定池。

**Q4（高频）：exceptionally、handle、whenComplete 的区别？**
exceptionally=catch（只异常分支，可给兜底值）；handle=catch+正常两分支都处理且可改写结果；whenComplete=finally（两分支都看但不改结果，异常继续透传）。
**追问：whenComplete 里把异常吞了行吗？** 吞不掉——它没有返回值改不了链，异常照样往下流；要吞用 handle 返回正常值。

**Q5：CompletableFuture 的异常是怎么传播的？get 和 join 抛的异常有什么区别？**
异常发生处之后的**同步回调全部跳过**，沿链流到最近的异常处理节点；没人处理则在终点的 get/join 抛出。get 抛受检的 ExecutionException（原异常为 cause）；join 抛非受检的 CompletionException——lambda 里写 join 不用到处声明异常，但错误可能被无意忽略。

**Q6：allOf 的返回值是什么？怎么拿到所有结果？**
CF\<Void\>——它只表达"全部完成"这个事件，不携带结果。标准姿势：`allOf(a,b,c).join()` 等齐后再分别 `a.join()/b.join()`（此刻立即返回）。anyOf 返回 CF\<Object\>，是最先完成任务的结果。
**追问：有一个失败 allOf 会怎样？** allOf 正常完成（不抛），各自 join 时才抛各自异常——逐个 join 时要处理失败项。

**Q7（高频）：不传线程池时任务跑在哪个池？有什么问题？**
ForkJoinPool.commonPool()：进程级单例、并行度≈CPU核数-1、daemon 线程。问题：① 全 JVM 共享，你的慢 IO 会占住公共线程，拖垮同池的其他并行计算（parallelStream 也在用它）；② daemon——main 退出不等人；③ 无法定制/监控/隔离。**生产三件套：自定义池 + 超时 + 异常兜底**。

**Q8：orTimeout 和 completeOnTimeout 的区别？（JDK 9+）**
orTimeout(n, unit)：到点任务没完就以 TimeoutException 异常完结（配合 exceptionally 降级）；completeOnTimeout(默认值, n, unit)：到点直接以默认值正常完结（不产生异常）——"超时了就用缓存值"一行搞定。

**Q9：supplyAsync 立即返回的 CF，后面才来的 thenApply 会怎样？**
立即执行——已完成的 CF 上注册回调，回调直接在当前线程跑（这就是 Q3 说"看运气"的另一面）。这个设计让"先启动、后补充步骤"的写法天然安全。

**Q10（架构题）：CompletableFuture 适合所有异步场景吗？和响应式（Reactor/RxJava）什么关系？**
CF 适合**一次性任务的有向编排**（调几个下游、合并、降级）；它的回调仍会阻塞线程（每一步占一个线程等结果）。响应式库基于事件流 + 少量事件循环线程，能表达无限流、背压、更复杂的组合。经验：业务编排 CF 足够；网关/流式/超高并发长链路再上响应式。Spring WebFlux 底层即响应式。

## 六、实际应用与取舍

- **并行聚合**：一个接口要查 用户+订单+积分 三张表——supplyAsync×3 + thenCombine/allOf，总耗时从相加变成取最大。
- **降级兜底**：库存服务挂了走本地缓存（exceptionally）、风控超时放行并告警（handle/orTimeout+completeOnTimeout）——示例第 5 段的三个场景全是生产原样。
- **多副本竞速**：同一数据多机房各存一份，anyOf 谁快用谁。
- **异步化改造**：Controller 里耗时操作移交异步链，立即返回受理结果（配自定义池，别蹭 commonPool）。
- **取舍**：链超过三四层、分支一多，可读性开始崩——及时抽方法/画流程图；纯"等一批任务完成"用 [CountDownLatch](../并发工具类/知识详解.md) 反而更直白。

## 七、可继续学习的方向

- 响应式流与 Project Reactor：Flux/Mono、背压（backpressure）——CF 的进化形态。
- Spring 的 @Async / WebClient：框架层对异步的封装。
