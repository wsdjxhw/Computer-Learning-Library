# 线程池

## 学习目标

- 理解线程池解决什么问题（线程复用、并发度控制）。
- **背熟并理解 ThreadPoolExecutor 七个参数**与任务执行流程（面试最高频）。
- 掌握四种拒绝策略、Future 的用法。
- 理解为什么生产代码不建议用 Executors 工厂方法。

**前置知识**：[多线程基础](../多线程基础/知识详解.md)（线程创建、synchronized）。
**适用范围**：Java 并发工程化的核心组件；Web 服务、批处理、异步任务的标配。

---

## 一、本节解决什么问题

直接 new Thread 有三宗罪：**创建/销毁开销大**（每个线程约 1MB 栈内存 + 系统调用）、**无节制**（请求洪峰一起开线程直接 OOM）、**不可管理**（没有统一的关闭、监控、排队）。线程池的思路是"银行柜台"：固定几个窗口（核心线程），忙了先取号排队（工作队列），队满了临时加窗口（弹性线程），实在不行限流（拒绝策略）——**复用线程 + 削峰 + 可管理**。

## 二、核心原理

### 2.1 七个参数（必须能逐个说出含义）

```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数：常驻"正式工"，哪怕闲着也不裁
    maximumPoolSize,   // 最大线程数：正式工 + 临时工的上限
    keepAliveTime, unit, // 临时工的空闲存活时间：超时就裁掉（不裁正式工）
    workQueue,         // 任务队列：正式工都忙时，新任务排队等着
    threadFactory,     // 线程工厂：定制线程属性（名字！排查问题全靠它）
    handler)           // 拒绝策略：队列满 + 线程满时的处理办法
```

### 2.2 执行流程（必考，示例第 2 段现场演算）

```text
提交任务
  ├─ 线程数 < core？      → 直接开新线程执行（不排队！）
  ├─ 线程数 ≥ core？      → 进 workQueue 排队
  ├─ 队列也满了？         → 再开临时线程（直到 maximumPoolSize）
  └─ 到了 maximum 还满？  → 执行拒绝策略
```

示例的算术：core=2、queue=2、max=3 → 容纳能力 2+2+1=**5**，提交第 6 个任务当场被拒。**注意反直觉点**：队列满了才扩线程——所以用无界队列时 maximumPoolSize 永远不生效。

### 2.3 四种拒绝策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| AbortPolicy（默认） | 抛 RejectedExecutionException | 快速暴露容量问题 |
| CallerRunsPolicy | 谁提交谁自己跑 | 自动降速（反压），不丢任务 |
| DiscardPolicy | 静默丢弃 | 允许丢的可选场景（慎用，无声无息） |
| DiscardOldestPolicy | 丢队头最老的再重试 | 只要最新数据的场景 |

### 2.4 shutdown 的两个阶段

`shutdown()`：不接新任务，存量任务跑完；`shutdownNow()`：尝试 interrupt 正在跑的任务、返回未执行的任务清单。标准收尾：`shutdown()` + `awaitTermination(超时)`，超时再 `shutdownNow()`。

### 2.5 线程数怎么定

- CPU 密集（计算为主）：**核数 + 1**——再多也是互相抢核，线程切换纯亏。
- IO 密集（等数据库/网络为主）：**核数 × 2 起步**，等待比例越高可越大（经验公式 核数 × (1 + 等待时间/计算时间)）。
- 最终以**压测**为准，公式只是起点。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 用 Executors.newFixedThreadPool/CachedThreadPool | 阿里规约禁用：无界队列/无限线程导致 OOM；显式 new ThreadPoolExecutor |
| 以为先扩线程再排队 | 顺序反了：**先排队，队列满才扩到 max** |
| 无界队列配 maximumPoolSize | 队列永远不满，max 形同虚设 |
| 忘了 shutdown | 线程池核心线程常驻，进程关不掉（非 daemon）；finally 里收尾 |
| ThreadFactory 不起名 | 出问题时满屏 pool-1-thread-3 分不清是谁；命名的线程打 jstack 才有意义 |
| 任务里吞 InterruptedException | 破坏 shutdownNow 与 cancel 的语义；catch 后 interrupt() 补回 |
| execute 提交要拿结果的任务 | 要返回值/异常细节用 submit 拿 Future |
| 多个池共享同名前缀 | jstack 里全是 pool-1-thread-1；每个池独立命名 |

**排查思路**：任务"没执行" → 先查是不是被拒绝（捕获 RejectedExecutionException 打日志）；"线程越来越多" → 查是否每次请求都 new 池（池应该单例复用）；"进程关不掉" → 有核心线程没 shutdown。

## 五、八股追问

线程池是 Java 面试**出现频率第一梯队**的题目，七参数与流程必须条件反射。

**Q1（必考中的必考）：ThreadPoolExecutor 七个参数分别是什么？**
corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime + unit（临时线程空闲存活时间）、workQueue（任务队列）、threadFactory（线程工厂）、handler（拒绝策略）。逐个能说"是什么 + 干什么"才算过，光背名字不够。
**追问：核心线程能被回收吗？** 默认不回收；`allowCoreThreadTimeOut(true)` 可让核心线程也参与超时回收。

**Q2（必考）：任务提交后的执行流程？**
线程数 < core → 建线程执行；≥ core → 入队；队列满 → 建临时线程直到 max；到 max 还装不下 → 拒绝策略。
**追问①：为什么"先入队再扩容"而不是"先扩容再排队"？** 设计取向是**尽量少开线程**（线程贵），排队是比开线程更便宜的缓冲。
**追问②：什么情况下 maximumPoolSize 不生效？** 用了无界队列（如 LinkedBlockingQueue 默认构造）——队列永远不满，永远走不到"扩容"分支。

**Q3（必考）：四种拒绝策略？**
Abort（抛异常，默认）、CallerRuns（提交线程自己跑，天然反压）、Discard（静默丢新）、DiscardOldest（丢最老的）。**追问：线上服务选哪个？** 多数场景 Abort + 上层限流/重试最稳（问题尽早暴露）；允许延迟的异步任务用 CallerRuns 自动降速。Discard 系列只在明确可丢的业务用。

**Q4（高频）：为什么不建议用 Executors 工厂？**
newFixedThreadPool/singleThreadPool 用**无界队列** LinkedBlockingQueue——任务堆积把内存撑爆（OOM）；newCachedThreadPool 线程数上限是 **Integer.MAX_VALUE**——请求尖峰无限开线程，栈内存 OOM；此外工厂方法无法定制线程名、拒绝策略等关键项。阿里规约因此强制显式 new ThreadPoolExecutor。

**Q5：execute 和 submit 的区别？**
execute(Runnable)：无返回值，任务异常直接抛给默认处理器。submit(Runnable/Callable)：返回 Future，可拿结果/取消任务；**注意：任务异常被吞进 Future 里，不调 get() 就无声无息**——这是"任务没报错但也没执行完"的经典元凶。

**Q6：shutdown 和 shutdownNow 的区别？**
shutdown：温和——拒新任务、跑完存量。shutdownNow：激进——interrupt 在跑的任务、清空队列并返回未执行任务。生产标准姿势：`shutdown()` → `awaitTermination(超时)` → 仍没结束再 `shutdownNow()`。

**Q7：线程池的线程数怎么定？**
CPU 密集 ≈ N+1（N=核数）；IO 密集 ≈ 2N 起步或 N×(1+等待/计算)。本质：CPU 密集时线程多了切换纯亏，IO 密集时线程在等、多开才能填满 CPU。**结论必须落在"以压测为准"**，公式只是初始值。

**Q8：线程池有哪几种状态？**
RUNNING（收任务+处理）→ SHUTDOWN（不收、处理存量）→ STOP（不收、不处理、interrupt 在跑的）→ TIDYING（全部结束）→ TERMINATED（terminated() 钩子执行完）。`shutdown` 触发 RUNNING→SHUTDOWN，`shutdownNow` 触发→STOP。

**Q9：Future 的 get 是怎么实现的？**
任务未完成时把调用线程挂到 Future 内部的等待队列（LockSupport.park），任务跑完 set 结果时唤醒。所以 get() 无超时版本可能永久阻塞——**生产代码一律用带超时的 get**。

## 六、实际应用与取舍

- **Web 服务异步化**：耗时的发短信/写日志丢给独立线程池，接口立刻返回（配合 Future/CompletableFuture）。
- **批处理/文件扫描**：固定池 + 每任务一个文件，并发度由池控制（[文件与Path](../../IO流/文件与Path/知识详解.md)的 walk 是天然任务源）。
- **不同业务隔离**：核心交易与边缘任务分池，避免互相拖垮（也是 Bulkhead 隔离思想）。
- **取舍**：池要**单例复用**（随应用生命周期），不是每次请求建一个；队列选型：有界（保护内存）优先，容量按压测设定。

## 七、可继续学习的方向

- `CompletableFuture`：Future 的进化版——回调、编排、异常传播（thenApply/thenCompose/allOf）。
- JUC 同步器：`Semaphore`（限流）、`CountDownLatch`（等一组任务完成）、`CyclicBarrier`。
- `ScheduledThreadPoolExecutor`：定时/周期任务。
- Spring 的 `@Async`/`ThreadPoolTaskExecutor`——线程池的框架化封装。
