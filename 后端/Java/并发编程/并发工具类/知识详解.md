# 并发工具类

## 学习目标

- 掌握四大协作工具的心智模型与适用场景：CountDownLatch（倒计时门闩）、CyclicBarrier（循环栅栏）、Semaphore（信号量）、BlockingQueue（阻塞队列）。
- 说清 CountDownLatch 与 CyclicBarrier 的区别（高频面试题）。
- 掌握 BlockingQueue 四组 API 的行为差异（抛异常/特殊值/阻塞/超时）。
- 理解"毒丸"结束模式与生产者-消费者的工程化写法。

**前置知识**：[多线程基础](../多线程基础/知识详解.md)（wait/notify 手写生产者消费者——本篇是它的工程化替代）、[锁与原子类](../锁与原子类/知识详解.md)（Condition 双等待室，BlockingQueue 的内部原理）。
**适用范围**：任务编排、并行等待、限流、线程间数据传递——JUC 协作场景的"标准件"。

---

## 一、本节解决什么问题

多线程真正难的不是"同时跑"，而是**协调**：

- 主线程要等 3 个并行任务全部完成再汇总——轮询 isDone 太笨，join 只能等线程死不能等"事情完"；
- 5 个线程要分阶段推进，每阶段**全员到齐**才能进下一阶段；
- 5 辆车抢 3 个车位，同时在场的不许超过 3——限流；
- 生产者消费者的手写 wait/notify 又长又容易错（while 条件、notifyAll、虚假唤醒……）。

这四件事 JVM 都造好了轮子：CountDownLatch 管"等 N 件事完成"，CyclicBarrier 管"全员到齐开会"，Semaphore 管"同时最多 N 个"，BlockingQueue 把生产者消费者一行搞定。它们底层都是 AQS（见延伸方向）——同一套地基上的不同房型。

## 二、核心原理

### 2.1 四个工具的心智模型

| 工具 | 心智模型 | 一句话 |
| --- | --- | --- |
| CountDownLatch | 倒计时门闩 | countDown 划掉一格，await 等计数归零——**单向、一次性** |
| CyclicBarrier | 会议室栅栏 | 人没到齐各自 await 堵着，到齐全员放行——**可循环复用** |
| Semaphore | 车位/许可证 | acquire 抢证，release 还证——**限制同时在场数量** |
| BlockingQueue | 传送带 | 满了 put 自动等，空了 take 自动等——**速率解耦** |

### 2.2 CountDownLatch：一等多 与 多等一

两个方向都要会用：

- **一等多**（等 Everyone）：3 个 worker 各自 countDown，主线程 await 到归零再汇总——并行任务汇合。
- **多等一**（Everyone 等一）：发令枪模式——3 个线程先 await，主线程一声 countDown(1) 全员起跑。

**关键限制：计数不能重置**，归零即作废；要再来一轮只能 new 一个新的（要循环请用 CyclicBarrier）。countDown() **不阻塞**调用方——划完格子自己接着跑。

### 2.3 CyclicBarrier：互相等的会合点

`await()` 凑够 parties 个线程后：先执行构造时传入的 barrierAction 回调（**由最后到达的线程执行**，此刻其他人还堵着），然后全员同时放行。下一轮 await **无需重建**（Cyclic 的含义）——直接复用同一实例。

**Latch vs Barrier（必考）**：Latch 是"观众等演出结束"——等的是**事件**（countDown 的人彼此不需要认识）；Barrier 是"演员到齐才开演"——等的是**线程本身**（参与者互相等待、同时行动）。

### 2.4 Semaphore：许可证管理

`acquire()` 取证（没有就阻塞），`release()` 还证。构造 `new Semaphore(3)` = 3 个并发额度。典型用途：限流、连接池/资源池、`new Semaphore(1)` 退化为互斥锁。release 可以多于 acquire（相当于**增发许可证**）。

### 2.5 BlockingQueue：生产者消费者的成品

| 操作 | 抛异常组 | 特殊值组 | **阻塞组** | 超时组 |
| --- | --- | --- | --- | --- |
| 入队 | add(e)→满抛 IllegalStateException | offer(e)→false | **put(e)**→满则等 | offer(e,n,u)→false |
| 出队 | remove()→空抛 NoSuchElement | poll()→null | **take()**→空则等 | poll(n,u)→null |

四组 API 行为（**必背表格**）：同一动作四种失败策略。生产者消费者标准搭配就是 put + take。

**内部原理**：一把 ReentrantLock + notFull/notEmpty 两个 Condition——正是[锁与原子类第 3 段](../锁与原子类/知识详解.md)手写的那个双等待室模型，ArrayBlockingQueue 源码里就是这么实现的。

**结束问题**：消费者 take 永远等下去怎么办？——**毒丸（poison pill）**：约定一个"结束信号"对象入队（示例的 "END"），消费者收到即退出；多消费者要放消费者数量个毒丸。

**实现选型**：

| 实现 | 特点 | 坑 |
| --- | --- | --- |
| ArrayBlockingQueue | 有界数组、一把锁 | 容量必须给 |
| LinkedBlockingQueue | 链表、读写两把锁（吞吐高） | **无参构造是无界**（Integer.MAX_VALUE）——[线程池篇](../线程池/知识详解.md)说过的 OOM 元凶 |
| SynchronousQueue | 零容量，手递手交接 | 直接传递，不存储 |
| DelayQueue | 到期才能取 | 定时任务场景 |
| PriorityBlockingQueue | 按优先级出队 | 无界 |

## 三、示例代码逐段讲解

示例文件：`示例代码.java`（段落与下述一一对应；线程打印顺序已在注释标注"不保证"）

**第 1 段：CountDownLatch**。先"一等多"：3 个 worker 工期不同（50/100/150ms），主线程 await 归零后汇总；再"多等一"：3 个选手 await 等同一声枪响。

**第 2 段：CyclicBarrier**。3 个成员先后到集合点（40/80/120ms），到齐触发回调"开会"，随后各自进入第二阶段——观察输出：三个"到达"有先后，"第二阶段"在回调之后。

**第 3 段：Semaphore**。3 车位 5 辆车。**看点在数字不在顺序**：`当前在场 N 辆` 由原子计数器维护，acquire 之后才 +1，所以打印出的 N **永远不会超过 3**——即使"停入/离开"的打印顺序因线程调度而交错（这本身就是"打印顺序≠事件顺序"的活教材）。

**第 4 段：BlockingQueue**。容量 2 的队列：生产者 4 件商品 + 1 个毒丸；消费者消费慢（每件 100ms），队列顶满后生产者被 put 自动阻塞——手写 wait/notify 的所有代码一行不用写。注意输出里"队列现有 1 个"出现两次：消费者瞬间取走了一件，长度在涨落——这是并发下的正常现象。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 想 reset CountDownLatch | 没有这个方法；归零即作废，重新 new 或改用 CyclicBarrier |
| CyclicBarrier 的回调里写重活 | 回调由最后到的线程在锁内执行，写重活会拖住全员放行 |
| countDown 忘在 finally | worker 异常导致没划格子，await 方永久卡死——countDown 放 finally |
| await/take 被中断后不管 | InterruptedException 是"请你退出"的信号；catch 后补 interrupt() 并做好收尾 |
| Semaphore 只 acquire 不 release（异常路径） | 许可证泄漏，后面的车永远进不来——release 放 finally |
| 队列长度打印出来"不对" | size() 是瞬时值，并发下与你的直觉不符是常态；演示数字要靠受保护的计数器（第 3 段的做法） |
| 无界队列当有界用 | LinkedBlockingQueue() 无参=无界，堆积 OOM；容量显式给 |
| 消费者循环没有退出条件 | 毒丸/关闭策略要设计，否则线程泄漏（池关不掉） |

**排查思路**："卡在 await 不动" → 数 countDown 次数是否等于构造数（jstack 看 WAITING 在哪）；"池关不掉" → 大概率有线程堵在 take()——查毒丸是否投递、数量是否匹配消费者数。

## 五、八股追问

协作工具是并发面试的中频固定曲目，Latch vs Barrier 与 BlockingQueue API 表几乎必问其一。

**Q1（必考）：CountDownLatch 和 CyclicBarrier 的区别？**
五个维度：① **等的东西**——Latch 等**事件**（countDown 方互不认识），Barrier 等**线程**（参与者互相等、一起行动）；② **复用**——Latch 一次性（计数不能重置），Barrier 可循环；③ **回调**——Barrier 支持到齐后先跑 barrierAction，Latch 没有；④ **角色**——Latch 的 countDown 不阻塞、await 阻塞；Barrier 人人 await；⑤ **实现**——都基于 AQS，但 Barrier 额外用可重入的"代（generation）"结构支持复用。
**追问：并行调 3 个接口等全部返回再汇总，用哪个？** Latch（等的是 3 件事件完成）；"3 个线程分 5 个阶段、每阶段全员会合"用 Barrier。

**Q2：CountDownLatch 的计数能增加吗？await 期间 countDown 线程会阻塞吗？**
不能增加也不能重置，只能递减到 0。countDown() 是非阻塞的——划完格子线程立刻继续跑自己的活；阻塞的只有 await()。

**Q3（高频）：Semaphore 的原理和应用？release 比 acquire 多会怎样？**
AQS 的共享模式：state=剩余许可证；acquire 就是 CAS 减 1，减成负数就进等待队列；release CAS 加 1 并唤醒等待者。release 多于 acquire 等于**增发许可证**（比如初始 0，动态放行）。用途：限流、资源池（连接池借还）、Semaphore(1) 当互斥锁。
**追问：和锁的区别？** 锁是"谁加谁解"（同一线程），Semaphore 的 acquire/release 可以在不同线程（车位谁抢谁停、谁停谁走）。

**Q4（必背）：BlockingQueue 四组插入/移除 API 的区别？**
add/remove：满/空抛异常；offer/poll：返回 false/null；**put/take：阻塞等待**；offer(e,n,u)/poll(n,u)：限时等待后放弃。生产者消费者用 put/take，轮询场景用超时组。
**追问：offer 和 put 分别适合什么场景？** put 适合"任务不能丢"（接受背压阻塞）；offer 适合"满了就放弃/降级"（配合拒绝策略，[线程池](../线程池/知识详解.md)就是用 offer 入队失败的返回值触发扩线程/拒绝的）。

**Q5：什么是毒丸（poison pill）？**
约定的特殊元素，消费者收到即退出循环——优雅关闭无界消费者循环的标准手法。**追问：3 个消费者要放几个毒丸？** 3 个（一人一颗）；或用"关闭标志+毒丸"组合。

**Q6：ArrayBlockingQueue 和 LinkedBlockingQueue 的区别？**
数组 vs 链表；**一把锁 vs 读写两把锁**（Array 的 put/take 共享一把锁，Linked 拆成 putLock/takeLock，读写可并行吞吐更高）；**默认容量**——Array 必须指定，Linked 无参=无界。都预置 notFull/notEmpty 两个 Condition。
**追问：线程池为什么常用 LinkedBlockingQueue？** 吞吐更好；但必须显式给容量，否则无界堆积 OOM（阿里规约的由来）。

**Q7：CyclicBarrier 的 barrierAction 在哪个线程执行？**
**最后到达的那个线程**（在它持有"代锁"时执行，此刻其他参与者还在 await）——所以回调里别做耗时操作，全员都在等它。执行完（含正常/异常）才统一放行。

**Q8：一个参与者抛异常/被中断，Barrier 会怎样？**
栅栏被打破（broken），所有等待者收到 **BrokenBarrierException** 立刻醒来——Barrier 的设计是"要么全员过，要么全散伙"；可用 reset() 主动打破。Latch 的 await 被中断只影响自己（InterruptedException），不影响别人计数。

**Q9（一句话题）：Exchanger 和 Phaser 是干什么的？**
Exchanger：两个线程在栅栏点**交换**各自的数据（遗传算法、双向管道）；Phaser：Barrier 的增强版——支持动态注册/注销参与者、分阶段计数（多阶段但人数会变的场景）。知道定位即可，深问概率低。

## 六、实际应用与取舍

- **并行任务汇合**：并行调多个下游再汇总——CountDownLatch 或 CompletableFuture.allOf（[CompletableFuture](../CompletableFuture异步编程/知识详解.md)是更现代的编排方案）。
- **服务启动等待依赖**：等配置/数据库/缓存全就绪再开门接客——Latch。
- **限流与资源池**：Semaphore 控并发度（伪代码：acquire → 用连接 → finally release）。
- **异步写日志/消息解耦**：BlockingQueue + 单消费者线程——[线程池](../线程池/知识详解.md)的 workQueue、所有"任务队列"的本质。
- **取舍**：能用现成工具绝不手写 wait/notify（手写版仅在[多线程基础](../多线程基础/知识详解.md)里作为原理教学存在）；用 Latch 还是 CompletableFuture 取决于要"等完成"还是要"完成后继续编排"——后者是前者的超集。

## 七、可继续学习的方向

- **AQS 源码**：state + CLH 双向队列 + 独占/共享两种模式——Latch(共享)/Semaphore(共享)/ReentrantLock(独占) 在其上的不同封装。
- [CompletableFuture 异步编程](../CompletableFuture异步编程/知识详解.md)：任务编排的现代化方案（allOf ≈ Latch + 结果收集一步到位）。
- 队列的数据结构原理（环形数组、链表）：见[数据结构与算法/队列](../../../../数据结构与算法/数据结构/队列/知识详解.md)。
