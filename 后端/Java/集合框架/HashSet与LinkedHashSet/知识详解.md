# HashSet 与 LinkedHashSet

## 学习目标

- 理解 Set 的定位：去重 + O(1) 成员判断，并用实测对比 List 的差距。
- 说清 HashSet 去重的本质：equals + hashCode 成对工作（必考）。
- 知道 HashSet 底层就是 HashMap，解释它是怎么"借壳"实现的。
- 掌握 LinkedHashSet 的保序原理与三家 Set 的选型。

**前置知识**：[ArrayList](../ArrayList/知识详解.md)（List 视角）、[HashMap](../HashMap/知识详解.md)（hash 与桶——Set 的底层就是它）、[常用API](../../语言基础/常用API/知识详解.md)（equals/hashCode 五约定）。
**适用范围**：标签、黑名单、判重、缓存键集合——一切"只关心在不在、不关心顺序"的场景。

---

## 一、本节解决什么问题

List 允许重复且 `contains` 是 O(n) 线性扫描——元素一多，"这个有没有？"就成了性能灾难。Set（集合）从语义上禁止重复、从结构上把判断降到 O(1)：数学里"集合"就是它的模型。本篇主角 HashSet 顺带回答一个更本质的问题：**两个对象算不算"同一个"？**——答案是 equals + hashCode 这对搭档，这也是全篇最重要的知识点。

## 二、核心原理

### 2.1 HashSet 是"借壳"的 HashMap

HashSet 内部只持有一个 `HashMap<E, Object>`：**元素当作 key**（key 天然不重复，去重白送），value 是一个共用的占位对象 `PRESENT`。所以——

- `add(e)` = `map.put(e, PRESENT)` 返回 false 即已存在；
- `contains(e)` = `map.containsKey(e)`：先 hashCode 定位桶，再桶内 equals——O(1)；
- 想懂 HashSet 的一切行为，去读 [HashMap](../HashMap/知识详解.md) 就对了。

### 2.2 equals + hashCode：去重的双子星

判等流程（两步缺一不可）：

```text
新元素进来
  ① hashCode 定位桶：哈希值不同 → 直接判定【不相等】，根本不比 equals
  ② 桶内逐个 equals：哈希值相同 → 才进一步比内容
```

由此推出**三条铁律**（也是[常用API五约定](../../语言基础/常用API/知识详解.md)的落地）：

1. 只重写 equals 不重写 hashCode：相等的对象算出不同哈希 → 落进不同桶 → **去重失效**（示例第 2 段的 BadKey）；
2. 只重写 hashCode 不重写 equals：进了同一个桶却比不出相等 → 同样失效；
3. 两者必须基于**相同的字段**：equals 用姓名判等、hashCode 却用年龄——逻辑分裂。

顺带记住：hashCode 相同不代表对象相等（哈希冲突正常存在），equals 相等则 hashCode 必须相同。

### 2.3 LinkedHashSet：多付一条链，买来顺序

`LinkedHashMap`（HashSet 对应的底层）在 HashMap 的桶数组之外，用一条**双向链表**把所有条目按插入先后串起来；遍历时顺链走，不扫空桶。代价：每个条目多两个引用（前驱/后继）的内存。accessOrder 形态见[LinkedHashMap与LRU](../LinkedHashMap与LRU/知识详解.md)。

### 2.4 选型表

| 实现 | 顺序 | 查找/增删 | 底层 | 适用 |
| --- | --- | --- | --- | --- |
| HashSet | 无序（hash 决定） | O(1) | HashMap | 默认首选 |
| LinkedHashSet | 插入顺序 | O(1) | HashMap+链表 | 去重且要稳定遍历顺序 |
| TreeSet | 升序 | O(log n) | 红黑树 | 去重+排序/范围查询（[下篇](../TreeMap与比较器/知识详解.md)） |

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 自定义类不重写 equals/hashCode 就放进 Set | 去重与 contains 全部失效（示例第 2 段） |
| 只重写其中一个 | 同样失效；两套规则必须成对、同字段 |
| 以为 HashSet 有序 / 依赖它的遍历顺序 | 无序且不保证跨版本稳定；要顺序用 Linked/Tree |
| mutable 对象放进 Set 后又改它的字段 | hashCode 变了，元素"迷路"——contains 找不到、remove 删不掉；Set 里放不可变对象 |
| 追问 HashSet 线程安全 | 不是；并发方案见[ConcurrentHashMap与并发容器](../ConcurrentHashMap与并发容器/知识详解.md) |
| 以为 add 失败会抛异常 | 静默返回 false；依赖返回值判断才靠谱 |

**排查思路**："Set 里出现重复" → 十有八九 equals/hashCode 没重写或不同步；"contains 明明有却返回 false" → 同上，或对象放进后被改了（哈希漂移）。

## 五、八股追问

**Q1（必考）：HashSet 怎么保证元素不重复？**
底层是 HashMap，元素作 key。add 时：hashCode 定位桶 → 桶内（或红黑树中）逐个 equals 比较 → 全不等才插入。**追问：那 value 存的什么？** 一个静态常量 PRESENT（Object 对象），所有 entry 共用，纯占位。
**追问②：由此推断 HashSet.add 的返回值语义？** true=插入成功；false=已存在被拒收。

**Q2（必考）：为什么重写 equals 必须重写 hashCode？**
约定要求 equals 相等的对象 hashCode 必须相等。只重写 equals 时两个"相等"对象继承了 Object 的地址哈希 → 哈希不同 → HashSet/HashMap 第一步就判"不相等"，equals 根本没机会执行 → 去重、查改全失效。
**追问：反过来说，hashCode 相等就是同一个对象吗？** 不是——哈希冲突正常存在（"香蕉"和"苹果"完全可能同桶）；相等要靠 equals 收尾判定。

**Q3（高频）：hashCode 是怎么参与定位的？**
JDK 8：`(h = key.hashCode()) ^ (h >>> 16)`——高 16 位与低 16 位异或，让高位也参与运算；再 `& (capacity-1)` 取模定位桶（容量恒为 2 的幂，位运算代取模）。详见[HashMap](../HashMap/知识详解.md)。**追问：为什么要扰动？** 桶下标只取低位，若 hashCode 只在高位有差异会挤进同一桶；扰动把高位特征混进低位，摊薄冲突。

**Q4：HashSet 允许 null 吗？**
允许存一个 null（底层 HashMap 对 null 键有专门处理：hash 取 0）。但并发容器（ConcurrentHashMap.newKeySet）禁 null——歧义问题见[并发容器篇](../ConcurrentHashMap与并发容器/知识详解.md)Q2。

**Q5（高频）：哈希冲突多了怎么办？链表什么时候变红黑树？**
同一个桶里的元素排成链表，查询退化 O(n)。JDK 8 起：链表长度 ≥ 8 **且** 数组容量 ≥ 64 时转红黑树（O(log n)）；容量不足 64 则优先扩容（resize 摊薄）。树节点缩到 6 个时退回链表。**追问：为什么阈值是 8？** 按泊松分布，理想 hash 下单桶达到 8 个的概率约千万分之六——真到 8 基本说明 hash 质量差，树化是兜底保险。

**Q6：HashSet 是线程安全的吗？并发场景怎么办？**
不是。方案按序：① `ConcurrentHashMap.newKeySet()`（并发首选）；② `Collections.synchronizedSet`（全表一把锁，吞吐差）；③ `CopyOnWriteArraySet`（读多写少）。详见[ConcurrentHashMap与并发容器](../ConcurrentHashMap与并发容器/知识详解.md)。

**Q7：HashSet 和 LinkedHashSet 怎么选？TreeSet 什么时候用？**
不关心顺序 → HashSet（最省）；要按插入顺序遍历（展示、去重保序输出）→ LinkedHashSet（多一条链的内存）；要排序遍历、最值、范围查询 → TreeSet（O(log n)，需可比较，见[TreeMap与比较器](../TreeMap与比较器/知识详解.md)）。
**追问：TreeSet 的"去重"和 equals 有关吗？** 无关！TreeSet 按 compareTo/compare 返回 0 判重——比较器说相等才算相等，equals 说了不算（两套判等体系，混用是坑）。

## 六、实际应用与取舍

- **判重/黑名单/白名单**：请求进门先 `set.contains(userId)`——O(1) 是接口防刷的地基。
- **标签系统**：`Set<Tag>` 天然去重；要展示顺序用 LinkedHashSet。
- **两集合运算**：`retainAll`（交）、`addAll`（并）、`removeAll`（差）语义清晰，内部实现走 size 小的一方。
- **取代 List.contains 的习惯**：任何"反复查在不在"的列表都该先问一句要不要换 Set（示例第 1 段的 600 倍差距）。
- **取舍**：Set 丢了下标随机访问与有序性——需要按序取第 N 个时老实用 List 或转数组。
