# ConcurrentHashMap 与并发容器

## 学习目标

- 说清 JDK 8 ConcurrentHashMap 的核心方案：CAS + synchronized 锁单个桶头节点。
- 对比 JDK 7 分段锁，理解"锁粒度越来越细"的演进思路（必考）。
- 掌握原子复合操作三剑客：putIfAbsent / computeIfAbsent / merge。
- 解释 CHM 为什么禁 null，记住并发容器全家福的选型表。

**前置知识**：[HashMap](../HashMap/知识详解.md)（桶数组结构）、[锁与原子类](../../并发编程/锁与原子类/知识详解.md)（CAS 是什么）、[并发工具类](../../并发编程/并发工具类/知识详解.md)（BlockingQueue）。
**适用范围**：缓存、配置表、计数器、多线程共享的任何 Map/Set/队列——并发集合几乎只有这一族答案。

## 一、本节解决什么问题

多线程共享一个 HashMap 会怎样？丢数据（两个线程同时写同一个桶互相覆盖）是起步价，JDK 7 的并发扩容甚至能把链表搞成环导致**死循环**。传统解法 `Collections.synchronizedMap` 包一层锁——安全了，但**一把大锁**让所有读写排队，4 线程写出单线程的速度。ConcurrentHashMap 要同时拿下两头：**线程安全 + 高并发吞吐**，思路是"把锁的粒度从整张表缩到单个桶，再配合无锁的 CAS"。本篇顺带解决两个工程高频痛点：并发下的"先查再放"竞态（原子方法），以及并发容器为什么连 null 都不让存。

## 二、核心原理

### 2.1 JDK 8：CAS + synchronized 锁桶头

put 的关键路径（简化版）：

```text
① 计算 hash，定位桶
② 桶是空的        → CAS 直接放入（无锁！竞争失败重试）
③ 桶不空          → synchronized(该桶的头节点)——只锁这一个桶
④ 链表尾插 / 红黑树插入，结构同 HashMap
⑤ 长度超阈值 → 协助扩容（helpTransfer：别的线程一起来搬）
```

要点：

- **锁粒度 = 一个桶**：不同桶的写入完全并行（示例第 1 段 4 线程写 200 万条，吞吐近乎翻倍）；
- **桶空走 CAS 无锁快路径**：低冲突时连 synchronized 都不碰；
- **get 全程无锁**：Node 的 val 与 next 用 `volatile` 保证可见性。

### 2.2 JDK 7 分段锁 → JDK 8 的演进（必考）

| | JDK 7 | JDK 8 |
| --- | --- | --- |
| 结构 | Segment 数组（每段一个小 HashMap） | Node 桶数组 + 链表/红黑树（同 HashMap） |
| 锁对象 | ReentrantLock 锁一个 Segment | synchronized 锁一个**桶头节点** |
| 粒度 | concurrencyLevel 段（默认 16） | 桶数（扩容后成千上万） |
| 附加 | — | CAS 空桶快路径、协助扩容、红黑树化 |

一句话总结演进：**锁的边界从"一段"缩到"一个桶"，还叠加了无锁路径**；另外 synchronized 在 JDK 6 后升级为偏向/轻量级锁，无竞争时开销极低，不再需要重量级 ReentrantLock。

### 2.3 原子复合操作：并发 Map 的真正杀手锏

`if (map.get(k) == null) map.put(k, v)` 是两步——中间能插进别的线程（check-then-act 竞态），synchronizedMap 时代只能外面再裹锁。CHM 把"查+算+放"**打包成原子方法**：

| 方法 | 语义 | 典型用途 |
| --- | --- | --- |
| `putIfAbsent(k, v)` | 没有才放；返回**旧值**（没有则 null） | 幂等初始化、缓存兜底 |
| `computeIfAbsent(k, f)` | 没有才**计算**放入；返回已存在的值 | 一键多值建索引、复用列表 |
| `merge(k, v, f)` | 有则按 f 合并旧新值，无则放 v | 词频统计、累加器 |
| `compute(k, f)` | 无条件按 f 重算 | 状态机式更新 |

`map.merge(word, 1, Integer::sum)` 一行就是并发安全的词频统计——这是面试与实战的双料高频。

### 2.4 null 禁令：歧义无法在并发下消除

`get(k)` 返回 null 到底是"键不存在"还是"值就是 null"？HashMap 单线程下可以 `containsKey` 补查分清；**并发下两次调用之间状态可能被别人改掉**，补查也不可信——歧义永久无法消除。所以 CHM 键、值都禁 null，**逼你用无歧义的表达**（如 `Optional`、哨兵值、或 `containsKey` 配合外部锁的场合直接换设计）。记法：**并发容器普遍禁 null**（CHM、ArrayDeque、BlockingQueue），HashMap 允许。

### 2.5 size() 与弱一致迭代

- `size()` 不是精确计数：内部是 `baseCount + 各 CounterCell`（分段累加，同 [LongAdder](../../并发编程/锁与原子类/知识详解.md) 思想）——并发写的瞬间总和可能略偏，这是**换吞吐的自觉取舍**（并发场景本就没有"某一刻的精确总数"）。
- 迭代器**弱一致**：遍历不抛 ConcurrentModificationException，尽量反映最新状态但不保证——与 [CopyOnWriteArrayList 快照](../迭代器与fail-fast/知识详解.md) 同属 fail-safe 阵营。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 以为用了 CHM 就万事大吉 | 单操作安全；get+put 组合仍竞态——用 putIfAbsent/computeIfAbsent 等原子方法 |
| 在 CHM 里存 null 值 | 键值都 NPE；无值语义用哨兵或 Optional 表达 |
| 把 synchronizedMap 当 CHM 平替 | 一把大锁吞吐差数倍（示例第 1 段）；且它连 get 都锁 |
| 以为 size() 精确 | 分段计数（baseCount+CounterCell），并发瞬间是近似值 |
| 迭代 CHM 时期望强一致快照 | 弱一致——不抛异常，但不保证含遍历开始后的修改 |
| 计算函数里再操作同一个 map | computeIfAbsent 的函数在桶锁内执行，重入/长任务会拖死该桶 |
| 网传"JDK 8 HashMap 也会死循环" | JDK 8 HashMap 改尾插不成环，但丢数据依旧——仍然永不许裸奔 |

**排查思路**："并发下偶发数据丢失/覆盖" → 是不是 check-then-act 没用原子方法；"put null 抛 NPE 觉得是 bug" → 设计如此，改表达；"多线程遍历报 ConcurrentModificationException" → 用的是普通容器不是 CHM。

## 五、八股追问

**Q1（必考中的必考）：ConcurrentHashMap 的底层实现？JDK 7 和 JDK 8 有什么区别？**
JDK 8：Node 桶数组 + 链表/红黑树；空桶 CAS 无锁放入，冲突桶 synchronized 锁**头节点**；get 全程无锁（volatile）；扩容可多线程协助。JDK 7：Segment 分段（默认 16 段），每段一把 ReentrantLock 锁一段小 HashMap。演进 = **锁粒度从段到桶、叠加 CAS 快路径**；synchronized 升级锁成熟后无需手写 ReentrantLock。
**追问：为什么桶空用 CAS、桶不空用锁？** 空桶无竞争结构可言，CAS 一次成功即完成；不空时要保护的是整条链/树的插入过程，必须临界区。

**Q2（必考）：ConcurrentHashMap 为什么不允许 null 键和 null 值？**
get 返回 null 无法区分"不存在"和"值就是 null"。单线程可用 containsKey 二次确认；**并发下确认的瞬间状态可能又被改**，歧义永存。禁止 null 逼开发者用无歧义表达，把隐患消灭在设计层。
**追问：HashMap 为什么就允许？** 它默认单线程环境，containsKey 补查可信；null 键还有专属桶（hash 记 0）。

**Q3（高频）：putIfAbsent / computeIfAbsent / merge 分别什么时候用？**
putIfAbsent：值现成、只要"没有才放"。computeIfAbsent：值要**现算**（如 new ArrayList）且要复用计算结果——幂等初始化建索引一绝。merge：存在就**合并**（累加、拼接）——词频/计数器标准写法 `merge(k, 1, Integer::sum)`。
**追问：`get(k) == null` 再 `put` 错在哪？** 两步非原子，两个线程可能同时通过检查各放一次——经典 check-then-act 竞态。

**Q4：ConcurrentHashMap 的 size() 是怎么实现的？准确吗？**
baseCount + CounterCell[] 分段累加（思想同 LongAdder）：写冲突时各线程往不同 Cell 计数，读时求和——避免所有线程挤一个热点的 CAS 失败重试。代价：并发写的瞬间求和是**近似值**（无锁快照做不到）。追问到底就答：并发场景"精确总数"本身没有良定义，这是吞吐换精确的自觉设计。

**Q5：ConcurrentHashMap 的迭代器是 fail-fast 吗？**
不是，是**弱一致**（weakly consistent）：创建后尽量反映最新状态，但不保证遍历开始后的修改都被看到，绝不抛 ConcurrentModificationException。因为并发遍历时"禁止他人写"既不现实也不高效。
**追问：CopyOnWriteArrayList 也是 fail-safe，两者有何不同？** COW 迭代的是创建瞬间的**完整快照**（旧数组），遍历期间绝对稳定；CHM 弱一致是"尽力看到最新"，没有快照拷贝成本。

**Q6：get 为什么可以不加锁？**
Node 的 val 和 next 声明为 **volatile**：写线程修改后对读线程立即可见（happens-before），且桶数组一旦发布不再原地改单个槽的引用结构（扩容迁移由写侧完成并转发）。读路径无锁是 CHM 吞吐的另一半支柱。
**追问：volatile 和锁差在哪？** volatile 只保证可见性与有序性，不保证原子性——所以读可以裸读，写（复合步骤）仍要 CAS/synchronized。完整理论在并发深入的 JMM 主题（规划中），现阶段先看[锁与原子类](../../并发编程/锁与原子类/知识详解.md)。

**Q7：什么是"协助扩容"？**
写线程发现桶数组达到阈值时不独扛扩容：先标记 ForwardingNode，其他线程 put 时撞见转发节点就**先去帮忙搬桶**（helpTransfer），搬完再回来写自己的数据——把一次大停顿摊给多个线程。这是"把大任务分而治之"的并发设计范式。

**Q8：并发容器全家福怎么选？**
Map → ConcurrentHashMap（默认唯一正解）；有序 Map → ConcurrentSkipListMap（跳表，范围查询，并发版 TreeMap）；Set → ConcurrentSkipListSet / CopyOnWriteArraySet / `ConcurrentHashMap.newKeySet()`；List → CopyOnWriteArrayList（仅读多写少）；阻塞队列 → [BlockingQueue 家族](../../并发编程/并发工具类/知识详解.md)（生产者消费者）。
**追问：为什么没有 ConcurrentArrayList？** 数组随机写难做细粒度锁（下标移动牵一发动全身）；并发 List 场景大多该重新审视是否本来就该用队列/Map。

## 六、实际应用与取舍

- **本地缓存/共享配置表**：`ConcurrentHashMap<K, V>` + `computeIfAbsent` 加载——读无锁、加载不重复。
- **计数器/统计**：`merge(key, 1, Integer::sum)`；超高频计数换 LongAdder（见[锁与原子类](../../并发编程/锁与原子类/知识详解.md)）。
- **多线程任务去重**：`putIfAbsent(taskId, …)` 当分布式锁的单机版语义用（谁放入成功谁执行）。
- **读多写少的监听器/订阅列表**：CopyOnWriteArrayList，通知遍历期间可安全注册注销。
- **取舍**：CHM 不解决"多操作组合"的原子性（Q3）；需要事务式的复合读写仍要外部锁或改用数据库/Actor 模型。
