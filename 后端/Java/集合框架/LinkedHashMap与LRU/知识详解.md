# LinkedHashMap 与 LRU

## 学习目标

- 理解 LinkedHashMap 的结构：HashMap 的桶 + 一条贯穿所有条目的双向链表。
- 掌握 accessOrder 两种形态：插入顺序（默认）与访问顺序。
- 会用 removeEldestEntry 钩子 10 行实现 LRU 缓存（高频手撕题的正解之一）。
- 知道手写 LRU（HashMap+双向链表）与工业级方案（Caffeine）的位置。

**前置知识**：[HashMap](../HashMap/知识详解.md)（底层桶结构）、[HashSet与LinkedHashSet](../HashSet与LinkedHashSet/知识详解.md)（HashSet 借壳 HashMap——本篇是同一个底层逻辑的升华）。
**适用范围**：缓存（LRU 淘汰）、去重保序输出、配置表按加载顺序展示。

## 一、本节解决什么问题

缓存不能无限大：内存有限，就得决定**淘汰谁**。最经典的答案是 LRU（Least Recently Used，最近最少使用）——"最久没用的先滚"，依据是访问局部性（最近用过的大概率还会用）。实现 LRU 需要两个 O(1)：查找快（HashMap 的强项）+ 能随时知道"谁最久没用"并 O(1) 摘掉它（一条按访问时间排好的双向链表）。JDK 把这两样**拼好了**直接给你——就是 `LinkedHashMap` 的 accessOrder 形态。

## 二、核心原理

### 2.1 结构：HashMap + 一条链

LinkedHashMap 完全复用 HashMap 的桶数组，只是把条目对象换成带 prev/next 的版本，再让所有条目**额外**串成一条双向链表。两个视角并存：

- 找一个 key：走 HashMap 的 hash 桶定位（O(1)，性能几乎不受影响）；
- 遍历所有条目：顺着链表走（有序、且不用扫空桶——大表遍历也比 HashMap 快）。

### 2.2 两种顺序：insertion-order 与 access-order

构造器第三个参数 `accessOrder`：

- **false（默认）**：链按 put 的先后排——插入顺序，去重保序就用它；
- **true**：**每次 get 或 put 命中**都把该条目挪到链尾——链头永远是"最久没碰的"，链尾是"刚碰过的"。

链头=最旧、链尾=最新——这就是 LRU 需要的全部秩序。

### 2.3 removeEldestEntry：官方预留的淘汰钩子

`protected boolean removeEldestEntry(Map.Entry eldest)`——每次 put 之后 JDK 自动回调它，返回 true 就把链头（eldest）摘掉。子类只需一行：

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) { super(16, 0.75f, true); this.capacity = capacity; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;    // 超容量即淘汰链头
    }
}
```

get/put 都是 O(1)，淘汰也是 O(1)——完整满足 LRU 的复杂度要求。

### 2.4 手写 LRU（LeetCode 146 视角）

LinkedHashMap 的结构拆开手写就是面试标准答案：**HashMap<K, Node> 定位 + 双向链表（带虚拟头尾哨兵）维护顺序**；get 命中后把节点移到尾部，put 超容删头部下一个节点。理解了 2.1~2.3 再手写，等于"照着 LinkedHashMap 抄"。

### 2.5 线程安全提醒

LinkedHashMap 非线程安全，且 accessOrder 形态下 **get 也会改链**（结构性变动）——多线程并发 get 都可能踩坏链表。并发缓存要么加锁包装，要么直接用 Caffeine。

示例文件：`示例代码.java`（段落与下述一一对应；输出全部确定）

**第 1 段：插入顺序**。购物车 put 三个商品，遍历严格按放入顺序——默认形态即"会保序的 HashMap"。

**第 2 段：访问顺序**。A B C 链上：get(A) → A 挪到链尾变 [B,C,A]；put(B,20) 命中已有键也算访问 → [C,A,B]。"链头最旧、链尾最新"的秩序在本段现场建立。

**第 3 段：LRU 缓存**。容量 3：装 A B C → get(A)（A 从最旧变最新）→ put(D) 超容 → **被淘汰的是 B 而不是 A**——LRU 语义的关键一跳（很多实现把"最先进来的"当成"最久没用的"，FIFO 和 LRU 的区别就在这）。结尾对照 LeetCode 146 手写版与生产 Caffeine 的定位。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 把 LRU 写成 FIFO（按插入时间淘汰） | get 要刷新位置：访问过的不算"旧"——示例第 3 段 A/B 之别 |
| accessOrder=true 忘了第三个构造参数 | 默认 false，get 不挪位置，LRU 语义全错 |
| 以为 get 是"只读"操作就并发随便用 | accessOrder 形态 get 改链，非线程安全；并发上锁或用 Caffeine |
| removeEldestEntry 里写复杂清理逻辑 | 它在 put 的锁内路径上回调，重活会拖慢每次 put |
| 淘汰钩子想同时打日志/落盘 | 返回 true 前可顺带处理 eldest，但别做慢 IO |
| 键参与顺序判断后又被修改字段 | 与[HashMap 键不可变](../HashMap/知识详解.md)同理 |

**排查思路**："缓存淘汰了不该淘汰的" → 检查是不是 FIFO（accessOrder 没开）；"并发下偶发链表错乱/死循环" → 多线程用了非安全容器。

## 五、八股追问

**Q1（必考）：LinkedHashMap 的实现原理？**
HashMap 的桶数组 + 条目对象多出 prev/next 两个引用，全部条目串成一条双向链表。查找走 hash 桶 O(1)；遍历顺链走（有序、不扫空桶）。构造参数 accessOrder 决定链按插入序还是访问序维护。
**追问：它对 HashMap 性能的影响？** 定位路径完全不变；每个条目多两个引用的内存、put/get 时多几次指针操作——几乎无感。

**Q2（高频手撕）：用 LinkedHashMap 实现 LRU？**
继承 + 三步：`super(16, 0.75f, true)` 开访问序；重写 `removeEldestEntry` 返回 `size() > capacity`；按容量构造。get/put/淘汰全 O(1)。**追问：为什么必须 accessOrder=true？** LRU 按"最近使用"排序，get 也要刷新位置；false 形态 get 不动链，退化成 FIFO。

**Q3（高频追问）：LinkedHashMap 的 LRU 和手写 HashMap+双向链表什么关系？**
同一结构：LinkedHashMap 就是官方版"HashMap+双向链表"。LeetCode 146 禁用现成类时才手写：HashMap<K,Node> 定位 + 虚拟头尾哨兵链表，get 命中移尾、put 超容删头。**追问：哨兵节点（dummy head/tail）图什么？** 让"删头/插尾/移动节点"不用判空边界，代码短且不漏 case。

**Q4：LRU 和 FIFO 的区别？**
淘汰依据不同：FIFO 看插入时间（先进先出），LRU 看最近访问时间（get 也会续命）。热点数据在 FIFO 下可能只因"来得早"被误杀；LRU 靠访问局部性保住热点。LFU 再进一步按访问频次——各有开销：LRU 每次访问 O(1) 挪链，LFU 维护频次桶更复杂。

**Q5：LinkedHashMap 遍历为什么可能比 HashMap 快？**
HashMap 遍历要扫整个桶数组（含大量空桶），代价与 capacity 相关；LinkedHashMap 顺链恰好走 size 步。元素稀疏（刚扩容完）的大表差距明显。**追问：那为什么平时不用它替代 HashMap？** 顺序多数场景不需要，白付链表内存；按需选型。

**Q6：怎么让 LRU 线程安全？**
按场景：低并发 → `Collections.synchronizedMap` 包装（粗锁，get 也串行）；高并发 → Caffeine（W-TinyLFU 淘汰 + 并发条目）或手写分段。**追问：ConcurrentHashMap 能直接做 LRU 吗？** 不能——它没有顺序维护；常见组合是 CHM + 过期时间戳定期清理（近似 LRU）。

**Q7（加分）：说一个 LinkedHashMap 的非缓存用途。**
插入序形态：接口返回的去重列表要保持用户输入顺序（Set 版即 LinkedHashSet）；"配置项按配置文件出现顺序展示"；MyBatis/一些框架用它存有序配置节点——凡是"Map 的查找 + List 的顺序"双需求，它都是本命。

## 六、实际应用与取舍

- **本地缓存**：低频/简单场景 LruCache 完全够用；生产用 Caffeine（过期策略、命中率统计、异步刷新）。
- **去重且保序**：LinkedHashSet / insertion-order LinkedHashMap——比"List contains 判重"又快又对。
- **请求/操作日志的有序键值表**：按发生顺序回放。
- **取舍**：明确要什么顺序（插入？访问？）再选形态；内存敏感且不需顺序就回 HashMap；并发永远单独考虑（Q6）。
