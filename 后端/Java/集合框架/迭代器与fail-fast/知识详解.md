# 迭代器与 fail-fast

## 学习目标

- 看穿 for-each 的糖衣：它就是 `Iterator` 的编译器生成写法。
- 掌握遍历中删除元素的三种正确姿势（`removeIf` 日常首选）。
- 讲清 fail-fast 机制：modCount 与 expectedModCount 的两份计数核对。
- 见识"倒数第二元素陷阱"——fail-fast 漏检的真实证据，理解"尽力而为"四个字。

**前置知识**：[ArrayList](../ArrayList/知识详解.md)（遍历的主角）、[HashMap](../HashMap/知识详解.md)（同样用 modCount 做 fail-fast）。
**适用范围**：一切"边遍历边筛选/删除"的业务代码；读懂数据结构源码的钥匙（几乎所有集合都用 modCount）。

---

## 一、本节解决什么问题

"把列表里所有 xxx 删掉"是再日常不过的需求，而随手写的 for-each + `list.remove(s)` 十有八九当场抛 `ConcurrentModificationException`——更可怕的是**偶尔不抛**（第 4 段的陷阱），静默吞掉错误。本篇回答三个问题：为什么遍历中直接 remove 会炸（fail-fast 机制）？怎么删才是对的（三种姿势）？以及"不抛异常"为什么反而更危险。

## 二、核心原理

### 2.1 for-each 的真面目

能 for-each 的前提是实现 `Iterable`；编译器把

```java
for (String s : list) { ... }
```

翻译成等价的迭代器循环：

```java
for (Iterator<String> it = list.iterator(); it.hasNext(); ) {
    String s = it.next();
    ...
}
```

迭代器协议三件套：`hasNext()`（还有吗）→ `next()`（前进并取出）→ `remove()`（删除**刚取出的**那个——唯一的合法删除方式，会同步更新两份计数）。

### 2.2 fail-fast：两份修改计数

ArrayList 内部有个修改计数 `modCount`，**每次增删都 +1**；迭代器创建时抄一份存进 `expectedModCount`。此后每次 `next()`/`remove()` 都核对：**两份不一致 → 立刻抛 ConcurrentModificationException**。

为什么需要它：迭代器内部按"当前下标 + 剩余数量"走路，集合若被外部增删，数组可能移位、size 变化——迭代器再走就是踩虚空（漏元素、越界、死循环）。与其走出错数据，不如**尽早掀桌**——这就是 fail-fast（快速失败）的设计哲学：错误暴露得越早，排查越容易。

关键认知两条：

1. 抛异常的目的是**暴露 bug**，不是让你 catch 了继续跑；
2. Javadoc 明说这是**尽力而为（best-effort）的检测，不做保证**——第 4 段将给出漏检实证。

### 2.3 三种正确删除姿势

| 姿势 | 写法 | 说明 |
| --- | --- | --- |
| ① 迭代器 remove | `it.remove()` | 同步更新两份计数，最经典；面试必会 |
| ② removeIf（JDK 8+） | `list.removeIf(s -> 条件)` | 内部就是迭代器删除，日常首选 |
| ③ 下标倒序删 | `for (int i = size-1; i >= 0; i--)` | 纯 for 循环场景；**必须倒序** |

正序下标删为什么漏：删除一个元素后**全体前移一位**，而 i 却 +1 跳过去了——紧挨着的下一个元素被跳过。倒序则前移的只是已经检查过的尾部，不受影响。

### 2.4 倒数第二元素陷阱（fail-fast 漏检）

[苹果, 香蕉, 橘子] 遍历中删**香蕉**（倒数第二个）——不抛异常，静默通过。机制：删除后 size 变 2，恰好等于迭代器光标位置 → `hasNext()` 返回 false → 循环自然结束 → `next()` 再没被调用 → **计数核对根本没机会执行**。

这是面试的隐藏加分题，更是工程教训：**同样的代码，删别的元素当场爆炸，删倒数第二个却安然无恙**——fail-fast 的保护是概率性的，绝不能赌它。

### 2.5 fail-safe：另一条路线

- **CopyOnWriteArrayList**：写时复制——每次增删复制整个新数组；迭代器拿的是**创建瞬间的数组快照**，遍历期间原集合怎么改都不影响本次遍历，也不抛异常。代价：写 O(n) 复制 → 只适合**读多写少**（如监听器列表）。
- **ConcurrentHashMap**：迭代器**弱一致**——不抛异常，不保证反映遍历开始后的修改，但尽量看到最新状态。见[并发容器篇](../ConcurrentHashMap与并发容器/知识详解.md)。

fail-fast 与 fail-safe 的取舍 = **尽早暴露错误** vs **并发下的可用性**：单线程 bug 用 fail-fast 快速定位；多线程并发读写用 fail-safe 容器，但你得接受"读到的是某一刻的状态"。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| for-each 里 list.remove(s) | 第 2 段当场爆炸；就算不炸也是漏检（第 4 段）——两种结果都不对 |
| catch ConcurrentModificationException 继续跑 | 异常是 bug 警报，不是流程分支；修姿势而不是吞异常 |
| 正序下标遍历删除 | 删一个全体前移、i 又 +1 → 跳过紧邻元素；要下标就倒序 |
| it.remove() 前不调 next() | IllegalStateException——删的是"刚取出的"，没取过就没得删 |
| 连续两次 it.remove() | 同上——一次 next 只配一次 remove |
| 以为 fail-fast 一定会抛 | 倒数第二陷阱就是反例；best-effort 不做保证 |
| 在遍历中 add 元素 | 与 remove 同罪，一样触发 fail-fast；要边遍历边加用 ListIterator.add |
| 遍历 CopyOnWriteArrayList 时期望看到并发新增 | 快照语义——看不见才是设计本意 |

**排查思路**："偶发 ConcurrentModificationException" → 有别的线程（或同线程的 lambda/回调）在遍历期间改了集合；"删完发现有漏网的" → 十有八九是正序下标删；"想删却抛 IllegalStateException" → it.remove() 没先 next()。

## 五、八股追问

**Q1（必考）：遍历 ArrayList 时删除元素为什么会抛 ConcurrentModificationException？**
迭代器创建时把集合的 modCount 抄进 expectedModCount；每次 next()/remove() 核对两份计数，不一致即抛。for-each 里调 `list.remove()` 只加 modCount 不动迭代器的抄本 → 下一次 next() 核对失败掀桌。
**追问：为什么设计成抛异常而不是容忍？** 结构性修改后迭代器的下标和 size 全部失准，继续走只会漏元素/越界/死循环——尽早失败把 bug 暴露在第一现场。

**Q2（必考）：遍历时删除元素的正确姿势？**
① 迭代器 `it.remove()`（同步两份计数）；② `removeIf(predicate)`（JDK 8+，内部同①，最推荐）；③ 下标**倒序**删（避免前移漏删）；④ 新建一个结果列表收保留项，最后替换原列表（函数式思路）。
**追问：正序下标删为什么漏？** 删除后尾部整体前移一位，i 却 +1，紧邻被删元素的下一个被跳过；倒序时前移的是已处理区，安全。

**Q3（隐藏加分题）：有没有可能遍历中 remove 不抛异常？**
有——删**倒数第二个**元素时：remove 后 size 恰好等于迭代器光标 → hasNext() 提前 false → next() 不再执行 → 核对被跳过 → 静默通过。这证明 fail-fast 是 best-effort（Javadoc 原话"cannot be guaranteed"），不能依赖它兜底。
**追问：删最后一个元素呢？** 同样可能不抛（remove 后光标已到头）；本质是"核对只发生在 next()/remove() 里"，循环提前结束就检不到。

**Q4：fail-fast 和 fail-safe 的区别？**
fail-fast：遍历中检测到结构性修改立刻抛异常（ArrayList/HashMap 等普通容器，靠 modCount 实现）。fail-safe：遍历不受修改影响、不抛异常——典型 CopyOnWriteArrayList（快照）与 ConcurrentHashMap（弱一致）。取舍：fail-fast 尽早暴露 bug（单线程）；fail-safe 牺牲实时性换并发可用（多线程）。
**追问：fail-safe 有什么代价？** COW 每次写复制整个数组（写 O(n)、内存翻倍），只适合读多写少；弱一致迭代读不到最新写入，业务上要能接受。

**Q5：Iterator 和 ListIterator 的区别？**
ListIterator 是 List 专属：支持**双向**（hasPrevious/previous）、**修改**（set/add）、**定位**（nextIndex/previousIndex）；普通 Iterator 只能单向 next + remove。要倒序遍历或边遍历边插入，只有 ListIterator 能干。

**Q6：为什么 ArrayList 要用 modCount 而不是直接比较 size？**
size 只能反映数量，不能区分"改了又改回去"的序列，也无法覆盖"替换不增删"之外的所有结构变化；modCount 是**修改版本号**——任何结构性修改都递增，迭代器核对版本号即可，不依赖具体数量。这也是**乐观并发控制**（版本号校验）的微型样本，数据库 MVCC、CAS 里的版本思想同源。

**Q7：ConcurrentHashMap 的迭代器抛 ConcurrentModificationException 吗？**
不抛——它的迭代器是**弱一致**（weakly consistent）：不抛异常、遍历开始后的修改"尽量"反映但不保证。因为并发场景下"遍历中不许别人写"本身就不现实，CHM 选择不锁遍历，用一致性换并发度。

## 六、实际应用与取舍

- **日常筛选删除**：`removeIf` 一行；要边遍历边做复杂逻辑（多次交互、提前 break）用显式迭代器。
- **倒序处理**：ListIterator 从尾部走，撤销栈类逻辑顺手。
- **监听器/订阅者列表**：注册销毁频繁度低、触发通知频繁度高 → CopyOnWriteArrayList 正中靶心（通知遍历期间允许注册/注销）。
- **并发容器遍历**：CHM 迭代不怕并发写，但读到的是弱一致视图——统计类任务要接受微小误差或外加协调。
- **取舍**：永远不要写"遍历中集合自身 remove/add"再靠 try-catch 兜底——那是把警报器拆了。
