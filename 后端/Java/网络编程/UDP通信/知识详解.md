# UDP 通信（DatagramSocket）

## 学习目标

- 掌握 DatagramSocket/DatagramPacket 的收发模型：一次 send 对应一个包。
- 理解数据报与字节流的本质差异（有边界 vs 无边界）。
- 会写 UDP 的一问一答（无连接的请求-响应）。
- 能回答 TCP vs UDP、UDP 实现可靠传输、UDP 包大小限制等高频八股。

**前置知识**：[TCP通信](../TCP通信/知识详解.md)（本篇处处与之镜像对照）、[字节流与字符流](../../IO流/字节流与字符流/知识详解.md)（编码知识通用）。
**适用范围**：实时音视频、游戏、DNS、心跳探测——"快比全重要"的场景。

---

## 一、本节解决什么问题

TCP 为可靠付出了代价：连接建立（握手）、确认重传、排序、流量/拥塞控制——每一样都要时间和状态。有些场景**宁丢不等**：

- 视频通话丢一帧，补发到时早过时了（要新帧不要旧帧）；
- 游戏同步要 30ms 内的最新位置，不需要 100ms 前的旧位置；
- DNS 查询就一问一答两个小包，为这两个包握手挥手四次不值得。

UDP（User Datagram Protocol）把 TCP 的"可靠全家桶"全部拆掉：**无连接、不保证送达、不保证顺序、数据报有边界**——换来的是头部仅 8 字节（TCP 20+）、无需建连、延迟极低。

## 二、核心原理

### 2.1 DatagramSocket 与 DatagramPacket

TCP 的 Socket 是"电话线"（连接状态），UDP 的 DatagramSocket 只是**本地的收发口**：

```java
DatagramSocket socket = new DatagramSocket(端口);   // 绑端口（接收方）；发送方可不绑

byte[] data = "hello".getBytes(UTF_8);
// 发：数据 + 目标地址全部装进"包裹"里
socket.send(new DatagramPacket(data, data.length, InetAddress, 目标端口));

DatagramPacket packet = new DatagramPacket(buf, buf.length);
socket.receive(packet);      // 阻塞等包裹；收到后包裹里带着【发件人地址】
```

关键认知：**包（Packet）自包含**——内容、长度、发件人地址端口都在包里；socket 本身不记任何"对方是谁"。

### 2.2 与 TCP 的编程差异（一张表看清）

| | TCP | UDP |
| --- | --- | --- |
| 建立连接 | connect/accept（握手） | 无——发包前什么都不用做 |
| 数据单位 | 无边界字节流（需自定界） | **数据报：一次 send 一次 receive，边界天然保留** |
| 回复对方 | 用已建立的连接直接写 | 再 send 一个包，**地址要从请求包里取** |
| 丢/乱序/重复 | 协议保证不发生 | 可能发生，应用层自理 |
| 一对多 | 一连接一端 | 一个 socket 可发给任何地址（广播/多播） |

### 2.3 一问一答：UDP 也能做"请求-响应"

没有连接，但请求包带着发件人地址——服务端 receive 后按 `packet.getAddress()/getPort()` **原路回信**即可。与 TCP 的区别：每次交互都要自己带地址、自己处理"请求丢了没回音"（超时重传）。

### 2.4 接收缓冲区的两条纪律

1. 用 `packet.getLength()` 取实际长度，**别用 buf.length**——buf 是你分配的大小，包里可能只装了一半；
2. 缓冲区小于包体时**静默截断**（多余部分直接丢弃，无异常）——这就是"UDP 包别超限"的编程侧体现（见八股 Q3）。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 用 buf.length 当数据长度 | 用 packet.getLength()——接收缓冲区多大和数据多长是两回事 |
| 以为 receive 会拆/粘包 | UDP 有边界：一次 receive 恰好一个完整数据报（截断除外） |
| 缓冲区开很大以为安全 | 超过 MTU 会被 IP 分片，丢一片整包作废——包要小（见八股 Q3） |
| 一问一答不等回信就干别的 | UDP 请求可能丢；生产要"超时+重传+序号防重" |
| 在 UDP 上按 TCP 思路写大流量可靠传输 | 等于重新发明 TCP（且大概率更差）；要可靠要么用 TCP，要么用 QUIC/KCP 这类现成方案 |
| 广播/多播当单播发 | 广播用 255.255.255.255/子网地址，多播用组播组地址，socket 需相应配置 |

**排查思路**："偶发收不到" → 本就是 UDP 特性，先确认是丢包还是逻辑丢（加序号日志）；"大数据偶发损坏/丢失整包" → IP 分片问题，缩小包体；"完全不通" → 检查两端绑定的端口与地址（绑了 loopback 就收不到外部包）。

## 五、八股追问

**Q1（必考第一题）：TCP 和 UDP 的区别？**
七个维度：**连接**（有/无）、**可靠性**（确认重传/尽力而为）、**有序性**（保证/不保证）、**数据形态**（字节流无边界/数据报有边界）、**速度与开销**（慢、头部 20 字节+/快、头部 8 字节）、**收发模型**（成对 Socket/双方独立 socket + 包自含地址）、**适用**（要全/要快）。
**追问：各举三个应用？** TCP：HTTP、文件传输、邮件、数据库连接；UDP：DNS、视频直播、游戏、DHCP、心跳。

**Q2（高频）：怎么在 UDP 上实现可靠传输？**
应用层把 TCP 的机制搬过来：**序号+确认应答+超时重传**（可靠）、**滑动窗口**（流量控制）、丢包策略可定制（视频：丢关键帧才重传，其余跳过——比 TCP 的"全都要"更贴合实时业务）。现实作品：**QUIC**（HTTP/3 底层，UDP 上重建可靠+多路复用+TLS）、KCP（游戏加速）。
**追问：为什么 QUIC 选 UDP 不新建传输层协议？** 内核协议栈改动成本极高、中间网络设备只认 TCP/UDP；跑在 UDP 上是用户态可迭代的 pragmatic 选择。

**Q3：UDP 一次最多能发多大的包？**
理论 65507 字节（65535 − IP 头 20 − UDP 头 8）。但超过 MTU（以太网 1500，UDP 载荷 1472）会被 **IP 分片**：任一分片丢失则整包作废，丢包率被放大。**实践建议：单包 ≤1472 字节**，或应用层自己分包重组。

**Q4：DNS 为什么用 UDP？什么时候又用 TCP？**
查询-应答就两个小包，UDP 免握手、延迟低——默认 UDP 53。转 TCP 的情形：应答超过约 512 字节（传统限制；EDNS 可扩到 4096 仍可能转 TCP）、**区域传送**（zone transfer，大量数据要求可靠）。这是"按单次交互特点选协议"的教科书案例。

**Q5：receive 的缓冲区比包小会怎样？**
**静默截断**——多出的数据被丢弃，不抛异常（除非开启相应选项）。所以接收缓冲要么按协议约定的最大包体开，要么协议里明确包长上限。

**Q6：广播和多播是什么？**
广播：发给同子网所有设备（255.255.255.255 或子网广播地址，如 DHCP 发现阶段）；多播：发给"订阅了组播组"的一组成员（224.0.0.0~239.255.255.255，如 IPTV/路由协议）。TCP 点对点做不到——这是 UDP 独有的能力。

**Q7：UDP 头部有哪些字段？**
8 字节：源端口、目标端口、长度、校验和（可选）。对照 TCP 头（20+ 字节：序号、确认号、窗口、标志位……）——没有的字段正是它不提供的服务。

## 六、实际应用与取舍

- **实时音视频/游戏**：RTP over UDP，丢帧不重传（要最新不要最旧）。
- **DNS/心跳/服务发现**：小包一问一答；丢了重问即可。
- **QUIC/HTTP3**：大厂已把"UDP 上重建可靠"投入生产——可靠与低延迟的现代平衡点。
- **取舍**：默认 TCP（可靠性是大多数业务的隐形需求）；确认"丢一点没关系、快最重要"再上 UDP；要在 UDP 上要可靠，直接考察 QUIC/KCP 而非手写。

## 七、可继续学习的方向

- **QUIC 协议**：UDP 上的可靠传输 + 0-RTT 建连 + 连接迁移（HTTP/3 的地基）。
- [NIO基础](../../IO流/NIO基础/知识详解.md)：DatagramChannel——UDP 的 NIO 形态（同样可注册 Selector）。
- **RTP/RTCP**：音视频传输协议族。
- 《计算机网络》：IP 分片、MTU、路由——UDP 行为的底层解释。
