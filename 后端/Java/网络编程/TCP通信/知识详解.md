# TCP 通信（Socket / BIO）

## 学习目标

- 掌握 InetAddress、ServerSocket、Socket 三件套与一次 TCP 服务的完整生命周期。
- 理解 accept/read/write 的阻塞语义（BIO 的 B），会写多客户端并发服务。
- 掌握 SO_TIMEOUT 超时保护——"不能信任对面"的生产铁律。
- 认识粘包/拆包问题与三种定界方案。
- 能回答三次握手、四次挥手及 TIME_WAIT 等高频八股。

**前置知识**：[多线程基础](../../并发编程/多线程基础/知识详解.md)（多客户端=线程协作）、[字节流与字符流](../../IO流/字节流与字符流/知识详解.md)（Socket 拿到的就是 InputStream/OutputStream，编码乱码的原理相同）。
**适用范围**：自定义协议通信、中间件客户端（数据库/Redis 连接的本质）、理解 Netty 与 HTTP 容器的底层。

## 一、本节解决什么问题

两个进程不在同一台机器（甚至同一机器想走标准协议）时，需要**网络编程**：IP 定位机器、端口定位进程，传输层协议负责把字节送过去。Java 把传输层的系统调用封装成了类：

- **TCP**（本篇）：可靠、有序、面向连接的字节流——像打电话，先接通再说话，说的每句都送到；
- **UDP**（[下一篇](../UDP通信/知识详解.md)）：无连接的数据报——像寄包裹，发出去就不管，快但可能丢。

本篇用 BIO（Blocking IO，JDK 1.0 的经典 API）写 TCP 服务。它简单直观，是理解通信全流程的最佳起点；它的天花板（一连接一线程）正是 [NIO](../../IO流/NIO基础/知识详解.md) 要解决的问题。

## 二、核心原理

### 2.1 ServerSocket 与 Socket：两端各一个电话

```java
// 服务端：绑端口 → 等连接 → 拿到对端的 Socket
ServerSocket server = new ServerSocket(端口);
Socket socket = server.accept();          // 阻塞，直到有客户端连入

// 客户端：连地址 → 直接拿到 Socket
Socket socket = new Socket("localhost", 端口);   // connect（三次握手）在这步完成

// 两端对称：从 Socket 拿流读写
socket.getInputStream() / socket.getOutputStream()
```

**accept 只管接客**：真正的 TCP 握手由内核在 accept 前/中完成，accept 返回的是"已建立连接"的对端插座。端口传 0 = 系统自动分配空闲端口（示例全部这么做，永不冲突）。

### 2.2 字节流与应用层协议：TCP 不管"消息"边界

TCP 给你的是**无边界的字节流**（见[字节流与字符流](../../IO流/字节流与字符流/知识详解.md)），"一条消息"是应用层的概念，双方必须约定定界规则：

1. **固定长度**：每条消息都是 N 字节（简单浪费）；
2. **分隔符**：换行符、特定字节（文本协议常用；readLine 就是按 \n 定界）；
3. **长度前缀**：头 4 字节写明后续长度（二进制协议标配，最通用）。

示例用 `println / readLine` 即"换行定界"——最朴素的应用层协议。

### 2.3 多客户端：accept 循环 + 线程池

单线程服务端 accept 一个连接就进去 readLine 死等，第二个客户端永远进不来。标准 BIO 解法：

```java
while (true) {                    // accept 循环只管接客
    Socket socket = server.accept();
    pool.submit(() -> handle(socket));   // 一连接一任务（复用《线程池》的结论）
}
```

天花板也在明面上：**连接数=线程数**，几千连接把线程（每线程约 1MB 栈）耗光——海量连接换 [NIO Selector](../../IO流/NIO基础/知识详解.md)。

### 2.4 超时：SO_TIMEOUT 与连接超时

阻塞读的默认行为是**永远等**——对端卡死/网络黑洞会把线程永久挂起。`socket.setSoTimeout(ms)` 给读操作上闹钟：超时抛 SocketTimeoutException。同理 `new Socket()` 前可 `socket.connect(addr, timeout)` 限制连接超时。**生产铁律：一切网络读都要有超时**。

### 2.5 生命周期与挥手

连接关闭（close）触发四次挥手；主动关闭方进入 TIME_WAIT 等 2MSL（见八股 Q2）。服务端先 close 还是客户端先 close，影响 TIME_WAIT 落在谁头上——高频短连接会堆 TIME_WAIT，长连接（连接池、HTTP keep-alive）是常见解法。

## 三、示例代码逐段讲解

示例文件：`示例代码.java`（段落与下述一一对应；全部走 localhost 回环 + 自动端口，离线可运行）

**第 1 段：InetAddress**。回环地址、localhost 解析、本机地址；点出 getByName(域名) 触发 DNS——可能阻塞可能失败，生产要有意识。

**第 2 段：最简回显服务**。服务端 accept → 按行读 → 原样回显 → 约定 "bye" 结束；客户端发三句收三句。**完整生命周期**（建连/读写/约信号关闭）的最小骨架；reader/writer 工具方法显式指定 UTF-8——Socket 流的乱码就是[字节流与字符流](../../IO流/字节流与字符流/知识详解.md)的老问题。

**第 3 段：多客户端**。accept 循环收满 3 连接，处理交给 2 线程的池（tcp-worker-N）；3 个客户端并发连入。**输出看点**：哪个客户端由哪个 worker 处理、各行先后顺序都不保证——并发下只该依赖"都处理完了"，不该依赖顺序。

**第 4 段：SO_TIMEOUT**。"装死服务器"接受连接但一言不发；客户端 setSoTimeout(500) 后 readLine 在 500ms 处抛 SocketTimeoutException 而不是永久卡死。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| PrintWriter 忘了 autoflush/flush | 对端永远等不到数据——println 数据还在发送缓冲里；示例第二个参数 true 解决 |
| 流/Socket 不用 try-with-resources | 连接泄漏，端口与 fd 迟早耗尽 |
| readLine 返回 null 当异常 | null=对端关闭且数据读完了；正常结束信号，不是错误 |
| 不设任何超时 | 对端卡死=线程永久挂起；SO_TIMEOUT/connect 超时必须配 |
| 服务端 accept 后忘了客户端还会"半开" | 对端崩溃时你不读永远不知道；心跳（定期探测）是长连接标配 |
| 假设"一次 write 对应一次 read" | TCP 是字节流，write 的边界到对端可能黏成一块/拆成几块——粘包拆包（八股 Q5） |
| 端口冲突还想硬绑 | BindException；测试用端口 0 自动分配，或 setReuseAddress 缓解 TIME_WAIT 占用 |
| 每请求建连接 | 三次握手+慢启动成本高；高频通信用连接池/长连接 |

**排查思路**："连不上" → 先 ping/telnet 分辨网络与端口、防火墙；"连上但没数据" → 查 flush；"过一会卡死" → 查超时与对端是否关闭；"偶发乱码" → 两端字符集不一致。

## 五、八股追问

Socket 编程的八股集中在"TCP 协议本身 + 编程模型"两条线。

**Q1（必考中的必考）：三次握手的过程？为什么不是两次？**
客户端 SYN(seq=x) → 服务端 SYN+ACK(seq=y, ack=x+1) → 客户端 ACK(ack=y+1)。**为什么三次**：① 双方都要确认"我发你能收"（两次无法让服务端确认自己的发送能力）；② 防止旧的重复 SYN（历史连接）突然到达建立无效连接——第三次 ACK 给了客户端否决的机会。
**追问：第三次 ACK 丢了会怎样？** 服务端重传 SYN+ACK 直到超时；此时客户端已 ESTABLISHED 并可能发数据（数据包带 ACK 可弥补）。

**Q2（必考）：四次挥手？为什么握手三次挥手四次？TIME_WAIT 为什么等 2MSL？**
主动方 FIN → 对端 ACK →（对端把剩余数据发完）FIN → 主动方 ACK。多的那次是因为**被动方的 ACK 和 FIN 分两步**：收到 FIN 先回 ACK，等自己数据发完再发 FIN。TIME_WAIT（主动关闭方，等 2MSL）目的：① 最后的 ACK 若丢失，能在重传的 FIN 到达时再补 ACK；② 让旧连接的报文在网络中自然消亡，避免污染相同四元组的新连接。
**追问：服务器出现大量 TIME_WAIT 正常吗？** 说明服务器在主动关闭大量短连接（如响应完就 close）；调长连接/连接复用比调内核参数更治本。

**Q3：accept 和三次握手是什么关系？**
握手由内核完成：收到 SYN 放**半连接队列**，握手完成放**全连接队列**，accept 只是从全连接队列取一条现成连接。**追问：全连接队列满了会怎样？** 默认丢弃客户端的 ACK（客户端以为连上了，服务端没接）——奇怪的超时/拒绝症状来源；SYN Flood 攻击打的就是半连接队列（syncookies 缓解）。

**Q4：BIO、NIO 在服务端编程上的区别？**
BIO：accept/read 都阻塞，一连接一线程撑并发（示例第 3 段就是它的极限形态）。NIO：非阻塞 + Selector 多路复用，一个线程管全部连接的就绪事件——详见[NIO基础](../../IO流/NIO基础/知识详解.md)（第 4 段就是单线程版服务端）。

**Q5（高频）：什么是 TCP 粘包/拆包？怎么解决？**
TCP 是字节流，**没有消息边界**：应用层两次 write 到对端可能被读成一块（粘）或一次 write 被拆成几块（拆）——本质不是 TCP 的 bug，是"流"与"消息"的语义差。解决：固定长度、分隔符（readLine 协议）、长度前缀（头 N 字节声明包长，最通用）。示例的"换行定界"就是分隔符方案。
**追问：UDP 有粘包吗？** 没有——数据报有边界，一次 send 对应一次 receive（见[UDP通信](../UDP通信/知识详解.md)第 1 段的对照输出）。

**Q6：readLine 什么时候返回 null/抛异常？**
对端正常关闭且缓冲读尽 → 返回 null；本端设了 SO_TIMEOUT 且到点 → SocketTimeoutException；连接被重置（RST）→ IOException（SocketException: Connection reset）。null 是"读完了"的语义，循环退出条件常靠它。

**Q7：短连接和长连接怎么选？**
短连接：用完即关，实现简单，不怕对端僵死——低频请求。长连接：省去反复握手、便于复用缓冲与状态——高频通信、推送、数据库/Redis 连接池、HTTP keep-alive。代价是要处理心跳保活与断线重连。

**Q8：一台机器最多多少 TCP 连接？瓶颈在哪？**
理论四元组（源IP 源端口 目的IP 目的端口）决定：**服务端**监听一个端口可接受约 2^32×(可用端口数) 的连接，瓶颈在**内存（每连接缓冲+线程）与 fd 上限**（ulimit），客户端侧才受 65535 端口限制（对单一目标地址）。C10K 问题（单机万级并发）由此而来——解法就是 epoll/NIO。

**Q9：SO_TIMEOUT 和 connect 超时的区别？**
connect 超时管"建立连接"阶段（new Socket(addr, port) 或 socket.connect(addr, timeout)）；SO_TIMEOUT 管"连上之后"每次阻塞读的等待上限。**两个都要设**——只设其一仍可能永久卡死。

## 六、实际应用与取舍

- **中间件客户端**：MySQL/Redis 的 JDBC/客户端 SDK 本质就是 TCP Socket + 私有二进制协议（长度前缀定界）+ 连接池。
- **自定义内部协议**：两系统间高效通信：TCP + Protobuf（长度前缀），或直接 HTTP/REST 换通用性。
- **学习读代码**：Tomcat 的 BIO/NIO Connector、Dubbo/Netty 的 IO 线程模型，都是本篇模型的工程化放大。
- **取舍**：需要可靠传输选 TCP，能容忍丢包要低延迟选 UDP；连接数大用 NIO/Netty 而非线程池硬扛；协议设计优先复用 HTTP，吞吐敏感再自定义二进制协议。
