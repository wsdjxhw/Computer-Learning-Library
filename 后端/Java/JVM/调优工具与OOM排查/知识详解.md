# JVM 调优工具与 OOM 排查实战

## 学习目标

- 记住进程外工具家族的分工：jps / jstat / jmap / jstack / jcmd / JFR / Arthas。
- 掌握三大排查套路：CPU 100%、内存泄漏、OOM 现场的标准动作序列。
- 分清内存泄漏与内存溢出（必考概念题），知道常见泄漏源头。
- 会用关键启动参数预埋"事故记录仪"：HeapDumpOnOutOfMemoryError、-Xlog:gc。

**前置知识**：[内存结构](../内存结构/知识详解.md)（堆/元空间读数）、[GC与垃圾收集器](../GC与垃圾收集器/知识详解.md)（YGC/FGC 含义）。
**适用范围**：生产事故排查、性能压测、面试场景题（"线上 CPU 100% 怎么查"是高频原题）。

---

## 一、本节解决什么问题

JVM 出事的表现无非三种：**CPU 打满、内存涨崩、卡死不动**。调优工具的存在意义是把"感觉慢"翻译成"数字定位到行/类"：进程外一组命令行工具（jstat/jmap/jstack）是 JDK 自带的听诊器，JFR 是常开的行车记录仪，Arthas 是免重启的手术刀。本篇以"事故 → 命令 → 结论"的顺序组织——所有排查都有标准动作序列，照着走就不会在半夜的生产事故里迷路。示例代码把听诊器在进程内复刻了一遍，让你在本机零环境成本地"看懂仪表盘"。

## 二、核心原理

### 2.1 工具分工表（背下这张表）

| 工具 | 作用 | 一句话时机 |
| --- | --- | --- |
| jps -l | 列 Java 进程号 | 一切的开始 |
| jstat -gc pid 间隔 | 各区容量/用量、GC 次数与耗时 | 怀疑 GC 问题 |
| jmap -histo pid | 按类统计对象数/大小 | 怀疑泄漏，先看它（轻） |
| jmap -dump:... pid | 导堆转储 .hprof | 要深挖（重，避开高峰） |
| jstack pid | 线程快照（含死锁检测） | 卡死、CPU 高、锁竞争 |
| jcmd pid help | 万能入口（dump/JFR 全能） | 记不住别的时用它 |
| JFR | 事件级飞行记录，开销 <1% | 生产常开，事后回放 |
| Arthas | dashboard/thread/heapdump，免重启 | 线上在线诊断 |

进程内对应物（示例第 1、2 段演示）：`ProcessHandle.current().pid()` ↔ jps；`Runtime`/`MemoryMXBean` 读数 ↔ jstat；`Thread.getAllStackTraces()` ↔ jstack。**进程外工具看的和你在进程内能打印的是同一批数据**——这就是为什么本篇示例"可运行可验证"。

### 2.2 堆读数三件套与 MemoryUsage 四元组

`init`（初始）/ `used`（已用）/ `committed`（已向 OS 承诺）/ `max`（上限，元空间可为 -1 表示无上限）。监控里内存曲线的三条线（used < committed ≤ max）就是这四元组。GC 优化的常见目标翻译成数字：used 在 GC 后回落、committed 不逼近 max、FGC 次数不涨。

### 2.3 内存泄漏 vs 内存溢出（必考概念题）

- **溢出 OOM**：结果——内存真的不够用（堆太小、大对象、一次性加载过多）；
- **泄漏 Leak**：原因——对象不再使用却**仍被 GC Roots 够得到**，GC 无法回收；累积到堆上限，表现成 OOM。

关系：泄漏是慢性病，溢出是终末期症状之一。泄漏的经典源头（示例第 3 段的 LEAK 就是教科书样本）：**static 集合只进不出**、无上限缓存、监听器/回调注册后不注销、ThreadLocal 在线程池中不 remove（见[GC 篇 Q2](../GC与垃圾收集器/知识详解.md)）、未关闭的资源。

### 2.4 OOM 标准排查序列

```text
① 启动预埋 -XX:+HeapDumpOnOutOfMemoryError → OOM 瞬间自动生成 java_pid<pid>.hprof
② jmap -histo pid 先看哪类对象数量/字节数异常（轻量快扫）
③ .hprof 丢进 MAT / VisualVM → 支配树（Dominator Tree）找占最大块的对象
   → GC Roots 引用链：谁牵着它不放（一眼看到那个 static Map）
④ 修代码：加上限（LRU/弱引用）、及时 remove/close、改成落盘或分页
```

支配树的思想：按"回收它就能释放多少内存"给对象排序——榜首就是"性价比最高的刀下目标"。示例第 3 段小堆变体（`-Xmx64m`）实测 16MB 即触顶抛 `OutOfMemoryError: Java heap space`，整个现场 30 秒内可复现。

### 2.5 CPU 100% 排查序列（高频场景题）

```text
① top / top -H -p <pid>          → 找到吃 CPU 的【线程号】
② printf '%x\n' <线程号>          → 转 16 进制（jstack 里 nid 是 16 进制）
③ jstack <pid> | grep -A 30 nid=0x<hex>  → 定位到正在跑的代码行
④ 常见元凶：死循环/正则回溯、频繁 Full GC（GC 线程吃 CPU，配合 jstat 确认）、
   死锁之外的锁自旋、序列化大对象
```

注意"CPU 高"的两种真相：业务线程在烧（③ 直接看到代码行）或 **GC 线程在烧**（jstack 看到的是 GC 线程，必须回去看 jstat）——先分诊再下药。

### 2.6 关键启动参数（预埋越早越好）

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| -Xms = -Xmx | 堆初始=最大 | 生产标配：避免运行期扩容缩容抖动 |
| -Xss | 线程栈大小 | 默认 1MB 别乱动 |
| -XX:MaxMetaspaceSize | 元空间上限 | 动态类多的应用兜底设一个 |
| -XX:+HeapDumpOnOutOfMemoryError | OOM 自动转储 | **每个生产进程都该带上** |
| -XX:+HeapDumpPath=... | 转储落盘位置 | 指到大磁盘目录 |
| -Xlog:gc*:file=... | GC 日志 | 常开（开销极小），排障全靠它 |

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 出事才想装工具 | jstack/jmap 依赖进程存活，OOM 崩了就晚了——HeapDumpOnOutOfMemoryError 必须预埋 |
| jmap -dump 随手就上 | 导出会长时间 STW，生产高峰等于二次事故；先 jmap -histo 轻扫 |
| 内存泄漏 = 会报错 | 泄漏本身不报错，只是 used 缓慢爬升；等 OOM 时往往已积累了数天 |
| 加大 -Xmx 治泄漏 | 只是把崩溃时间推迟；泄漏照漏，反而更难发现 |
| jstack 抓一次就下结论 | 至少抓 3 次间隔几秒对比——卡住的线程每次都在同一行才有说服力 |
| 只看 used 判断内存健康 | 要看 GC 后的 used（回落水位）与 committed 趋势；瞬时 used 波动是正常的 |
| 死锁靠肉眼查代码 | jstack 自带死锁检测，直接打印 Found one Java-level deadlock 及持有/等待关系 |
| JFR 影响性能不敢开 | 默认配置开销 <1%，专为生产常开设计 |

**排查思路（总路线）**："CPU 高" → 2.5 序列；"内存涨" → jstat 看 GC 后水位 + jmap -histo 找增长类 → dump+MAT；"卡死" → jstack 三连拍（死锁/等锁/等 IO）；"启动即崩" → 看是不是 -Xmx 超过容器 limit 被 OOM-kill（dmesg 确认，这与 JVM OOM 是两回事）。

## 五、八股追问

**Q1（必考）：线上 CPU 100% 怎么排查？**
top 定位进程 → top -H -p 定位线程 → 线程号转 16 进制 → jstack 找 nid=0x... 对应栈 → 看到具体代码行。若烧 CPU 的是 GC 线程，转查 jstat（频繁 Full GC 的根因是内存问题）。
**追问：为什么 nid 要转 16 进制？** jstack 输出里 nid（native thread id）是 16 进制格式，top 给的是 10 进制——进制对不上就永远 grep 不中，这是这题的第一个坑。

**Q2（必考）：内存泄漏和内存溢出的区别？**
溢出是"放不下"（结果），泄漏是"该回收的收不走"（原因之一）。泄漏累积终致溢出，但溢出也另有原因（堆配置小、大查询、突发流量）。**追问：举三个泄漏源头？** static 集合只进不出、无上限缓存、ThreadLocal 线程池不 remove、监听器不注销、未关闭资源——任说三个并讲清"谁牵着引用"即满分。

**Q3（高频）：OOM 的排查流程？**
预埋 HeapDumpOnOutOfMemoryError 拿到 .hprof（事后 OOM 用 jmap -dump 补）→ MAT 支配树找最大块 → GC Roots 引用链定位持有者 → 修代码（上限/清理/改结构）。轻量预检用 jmap -histo 看对象数排行。
**追问：支配树是什么？** 按"删掉它能立刻释放多少内存"排序的视图——榜首对象是回收性价比最高的目标，比单纯按对象大小排更有指向性。

**Q4：jps/jstat/jmap/jstack 分别干什么？**
jps 列进程；jstat 看 GC 与各区用量（可定时刷新）；jmap 看堆内对象统计与导出转储；jstack 线程快照与死锁检测。**追问：jcmd 是什么地位？** JDK 官方推的统一入口，其余工具的功能基本都能 jcmd 直达（如 jcmd pid GC.heap_dump / JFR.start），且对容器环境更友好。

**Q5（高频）：为什么生产上 -Xms 和 -Xmx 设成一样？**
堆不再动态扩容缩容：① 申请/归还内存引发的停顿与系统调用消失；② 内存曲线稳定，监控与容量规划简单；③ 避免扩容竞争期 GC 更频繁。代价是启动即占满配置内存——资源固定的生产环境这恰是想要的确定性。

**Q6：Full GC 频繁怎么排查？**
jstat -gc 看 FGC 涨速与老年代水位 → 涨因分诊：老年代真满（泄漏/缓存无上限 → Q3 流程）、大对象直达（jmap -histo 看大字节数类；G1 调大 Region）、晋升过快（Survivor 太小/MaxTenuringThreshold 异常）、元空间满（动态类失控，见[类加载](../类加载与双亲委派/知识详解.md)）、或 System.gc() 被人调用（-Xlog:gc 里能看到元凶栈）。
**追问：元空间 OOM 的常见根因？** 反复生成动态代理/CGLIB 子类且加载器不可回收——类进得去出不来（类卸载三条件苛刻）。

**Q7：死锁怎么排查？**
jstack 直接打印 Found one Java-level deadlock，列出互相持有与等待的锁及线程栈。预防层面回到[锁与原子类](../../并发编程/锁与原子类/知识详解.md)的死锁四条件：按固定顺序拿锁、tryLock 带超时、缩小锁范围。
**追问：jstack 里 WAITING (on object monitor) 和 BLOCKED 区别？** BLOCKED 是等进入 synchronized（锁被占）；WAITING(on monitor) 是 wait() 后等 notify——一个是抢锁失败，一个是主动让出。

**Q8（加分）：JFR 和 Arthas 各适合什么场景？**
JFR：JDK 自带、开销 <1%、事件级记录（GC/锁/分配/热点方法），适合**常开+事后回放**，"昨晚三点发生了什么"型问题。Arthas：attach 进程在线交互，dashboard 实时看、watch/trace 在不重启的情况下盯某个方法的入参与耗时，适合**在线诊断正在发生的问题**。一个事后取证、一个现场办案，生产两条腿都要有。

## 六、实际应用与取舍

- **上线检查单**：-Xms=-Xmx、HeapDumpOnOutOfMemoryError+HeapDumpPath、-Xlog:gc* 落盘、MaxMetaspaceSize 兜底——四件套齐了再谈别的调优。
- **容量规划**：容器部署时 -Xmx 必须小于容器 memory limit（留出元空间/栈/直接内存），否则被 OOM-kill 且毫无堆转储。
- **缓存类业务**：本地缓存一律设上限（[LRU](../../集合框架/LinkedHashMap与LRU/知识详解.md)）或接入淘汰策略，无限缓存等于自造泄漏。
- **取舍**：一切调优从测量开始（jstat/JFR 建立基线），只调参数不找根因是掩盖病情；真正需要"调参"解决的问题，往往代码层（一个 SQL、一个循环内 new）改一行就够。
