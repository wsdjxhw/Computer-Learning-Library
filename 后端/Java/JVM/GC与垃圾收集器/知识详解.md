# GC 与垃圾收集器

## 学习目标

- 掌握判定垃圾的标准：可达性分析（不是引用计数），说全 GC Roots。
- 分清四种引用强度（强/软/弱/虚）各自的回收语义与用途。
- 讲透三大算法（复制/标记-清除/标记-整理）与分代收集的因果关系。
- 梳理收集器演进主线：Serial → Parallel → CMS → G1 → ZGC（面试 JVM 第二题）。

**前置知识**：[内存结构](../内存结构/知识详解.md)（堆/栈里有什么——垃圾都在堆里）。
**适用范围**：GC 调优、缓存选型（引用强度）、面试 JVM 篇的核心章节。

---

## 一、本节解决什么问题

堆里的对象谁都能 new，但没人负责 delete——回收垃圾对象、把内存循环利用，就是 GC（Garbage Collection）的全部使命。它要回答三个层层递进的问题：**谁是垃圾**（判定算法）？**怎么回收**（收集算法与分代策略）？**回收时别太吵**（收集器的停顿与并发设计）。最后落到工程：为什么 JDK 8 升 21 默认收集器从 Parallel 变成 G1，大堆为什么流行 ZGC。

## 二、核心原理

### 2.1 谁是垃圾：可达性分析

从一组肯定活着的起点 **GC Roots** 出发，沿引用链走，**走得到的活着，走不到的是垃圾**。GC Roots 包括：各线程栈上的局部变量、方法区类静态字段、字符串常量池等常量引用、JNI 全局引用等。

为什么不用引用计数（数每个对象被指了几次，归零回收）：实现简单，但**循环引用无解**——两个对象互相指着，计数永不归零，却整体不可达。可达性分析从根出发，循环引用的环只要不被外部够到就整环判死（示例第 1 段：把强引用置 null，环/对象立即变垃圾）。

### 2.2 四种引用强度（同一个类 Big 的四种命运）

| 引用 | 回收时机 | 典型用途 |
| --- | --- | --- |
| 强引用 Strong | 永不回收，宁可 OOM | 日常赋值 `Big b = new Big()` |
| 软引用 SoftReference | **内存不足时**才回收 | 内存敏感的缓存 |
| 弱引用 WeakReference | **下次 GC** 就回收 | WeakHashMap、不阻碍回收的关联元数据 |
| 虚引用 PhantomReference | 形同虚设，只收回收通知 | 堆外内存清理（DirectByteBuffer → Cleaner） |

示例实测：强引用在 System.gc() 后稳如泰山；弱引用一轮 GC 后 `get()` 返回 null；软引用在内存宽裕时通常还在（**不保证**——它的语义本来就叫"看内存压力行事"）。

### 2.3 怎么回收：三大算法

| 算法 | 思路 | 优点 | 缺点 | 用在 |
| --- | --- | --- | --- | --- |
| 标记-清除 | 标出垃圾，直接清 | 简单，不动活对象 | **内存碎片**；效率不稳 | CMS 老年代 |
| 复制 | 活对象复制到另一半区，旧区整块清零 | 无碎片、高效（活对象少时） | 浪费一半空间 | **新生代** |
| 标记-整理 | 标记后把活对象**挪到一端**再清边界 | 无碎片 | 挪对象要改所有引用，慢 | 老年代 |

分代收集的因果链（面试要讲成"推导"而不是背诵）：**弱分代假说**——绝大多数对象朝生夕死 → 新生代用**复制算法**（活下来的少，复制成本低，Eden:S0:S1 = 8:1:1）→ 熬过多次回收的对象"变老"晋升老年代 → 老年代对象存活率高，用标记-清除/整理。一次回收只清理新生代的叫 **Minor GC**，收拾整个堆（含老年代）的叫 **Full GC**。

### 2.4 对象什么时候进老年代（高频）

1. **年龄达标**：每熬过一次 Minor GC 年龄 +1，默认 15 岁（`-XX:MaxTenuringThreshold`）；
2. **大对象直达**：超过阈值（G1 里超过 Region 一半即 Humongous）直接进老年代/大对象区，防止在 Survivor 间来回复制；
3. **动态年龄判定**：Survivor 中同龄对象总和超过一半，该岁数以上全体晋升。

### 2.5 收集器演进：一条"少停顿"的奋斗史

| 收集器 | 思路 | 一句话定位 |
| --- | --- | --- |
| Serial | 单线程，全程 STW | 小内存/客户端模式 |
| Parallel | 多线程并行，吞吐优先 | **JDK 8 默认**——停顿长但总吞吐高 |
| CMS | 并发标记清除，低停顿先驱 | **JDK 9 废弃、14 移除**（碎片、并发失败、浮动垃圾三宗罪） |
| G1 | 堆切成 ~2048 个 Region，按停顿目标优先回收垃圾最多的区 | **JDK 9+ 默认**，大堆可预期停顿 |
| ZGC | 着色指针 + 读屏障，几乎全程并发 | 停顿 <1ms（与堆大小无关），JDK 15 转正 |

演进的驱动力始终是**停顿时间**：STW（Stop The World）——GC 期间所有应用线程暂停；并行（parallel）缩短单次停顿的时长，并发（concurrent）让大部分回收工作与应用同时进行。示例第 3 段的 MXBean 输出直接显示 JDK 21 默认是 `G1 Young/Old Generation` 三个收集器 bean；带 `-Xlog:gc` 跑一遍，还能亲眼看到 `Pause Young (G1 Evacuation Pause) 22M->4M(252M) 4.291ms` 这样的真实日志。

### 2.6 System.gc() 的真相

它只是**建议**JVM 做 Full GC（不是命令），JVM 可用 `-XX:+DisableExplicitGC` 直接无视。但注意：开这个参数时 DirectBuffer 的清理可能被连带影响（部分版本 System.gc 参与堆外内存回收）——示例用它仅为让教学现象快速出现，业务代码不要调它。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| System.gc() 立刻触发 GC | 只是建议；JVM 可配置忽略（-XX:+DisableExplicitGC） |
| 对象不可达就【立刻】被回收 | GC 是周期性行为，判死≠已回收；Finalizer 队列还会拖一轮 |
| finalize 能救活对象 | 已废弃（JDK 9+），执行无保证还拖慢回收；用 try-with-resources / Cleaner |
| 软引用当可靠缓存 | 语义就是"随时可能没了"，命中逻辑必须容忍 miss |
| WeakHashMap 当线程安全容器 | 它只解决 key 的弱引用，不解决并发（并发用 [CHM](../../集合框架/ConcurrentHashMap与并发容器/知识详解.md)） |
| Minor GC 很快所以频繁 Full GC 也没事 | Full GC 收整堆，停顿常是 Minor 的十倍级——优化目标是减少 Full GC |
| CMS 还在用 | JDK 14 起物理移除；还在用 CMS 的答案只配出现在"历史题" |
| G1 没有分代 | G1 逻辑分代物理不分代——Region 动态扮演 Eden/Survivor/Old |

**排查思路**："频繁 Full GC" → jstat -gc 看 FGC 涨速 → jmap -histo 看谁在疯长（大对象/缓存无上限/晋升过快）；"内存宽裕但 GC 频繁" → 短命大对象（G1 Humongous）批量分配；流程见[调优排查](../调优工具与OOM排查/知识详解.md)。

## 五、八股追问

**Q1（必考）：怎么判断对象是垃圾？**
可达性分析：从 GC Roots（栈上局部变量、静态字段、常量、JNI 引用）出发走引用链，不可达即垃圾。
**追问：为什么不用引用计数？** 循环引用无解——互相引用的环计数永不归零；可达性分析从根出发，外部够不到的环整体判死。
**追问②：GC Roots 具体有哪些？** 至少说四样：虚拟机栈局部变量、方法区静态引用、常量引用、JNI 引用；有理有据即可。

**Q2（必考）：四种引用的区别与应用？**
强：永不回收（宁可 OOM）。软：内存不足才回收 → 缓存。弱：下次 GC 即回收 → WeakHashMap/ThreadLocal 的 Map（串联 ThreadLocal 内存泄漏考点——属并发深入批次，规划中）。虚：只收通知 → 堆外内存清理 Cleaner。
**追问：ThreadLocal 的内存泄漏和弱引用什么关系？** ThreadLocalMap 的 key 是弱引用（ThreadLocal 对象可被回收，key 变 null），但 value 是强引用——线程池里线程长寿，value 链不清理就漏；解法是用完 remove()。

**Q3（必考）：GC 算法有哪几种？为什么新生代用复制、老年代用标记整理？**
复制/标记-清除/标记-整理。因果链：新生代对象 98% 朝生夕死 → 复制只需搬极少数幸存者，且天然无碎片（代价的一半空间用 8:1:1 的 Eden/Survivor 压到 10%）；老年代存活率高 → 复制反而要搬大多数人，改用标记-清除/整理，避免空间减半。
**追问：标记-清除的碎片问题怎么体现？** 碎片导致后续大对象找不到连续空间，提前触发 Full GC——正是 CMS 被淘汰的原因之一。

**Q4（高频）：Minor GC / Major GC / Full GC 的区别和触发条件？**
Minor GC：只收新生代，频繁、快、必然伴随 STW；Eden 满了就触发。Full GC：收整个堆+方法区，慢；触发于老年代空间不足、元空间不足、System.gc()、CMS 晋升失败等。（Major GC 语义混乱，答"通常指老年代收集"即可。）
**追问：怎么减少 Full GC？** 治源头：防大对象直达（G1 用 -XX:G1HeapRegionSize 调大 Region）、防内存泄漏、合理新生代比例，别只调大堆掩盖问题。

**Q5（高频）：对象什么时候进老年代？**
年龄到阈值（默认 15，-XX:MaxTenuringThreshold）、大对象直达（G1 超半个 Region 即 Humongous）、动态年龄判定（同龄 Survivor 总和过半）。**追问：为什么阈值是 15？** 年龄存在对象头 4 bit 字段里，上限就是 15——数字背后有数据结构，答出来就是加分。

**Q6（必考）：CMS 和 G1 的区别？为什么 CMS 被移除？**
CMS：并发标记清除，老年代收集器，追求低停顿；三大毛病——标记-清除产生碎片、并发收集器需预留空间（浮动垃圾致并发模式失败退化 Serial Old）、与用户线程争 CPU。G1：整堆收集器，Region 化（物理不分代逻辑分代），可设停顿目标（-XX:MaxGCPauseMillis），按"回收性价比"排序优先处理垃圾最多的 Region（Garbage First 名字的由来），整体标记-整理无碎片。
**追问：G1 的 Remembered Set 是干嘛的？** Region 之间引用关系的账本——避免回收单个 Region 时扫整堆；这是 G1 空间换时间的代价（可能占堆 10%~20%）。

**Q7：ZGC 为什么能停顿 <1ms？**
着色指针（在指针位里存标记信息）+ 读屏障（访问引用时自我修复）+ 几乎全程并发（标记/转移/重定位都与应用并发跑），STW 只剩极短的根扫描。停顿时间**与堆大小无关**——TB 级堆照样亚毫秒。代价：吞吐略降、内存占用略高（染色备份）。
**追问：什么时候选 ZGC 而不是 G1？** 堆很大（>8~16G）且延迟敏感（P99 要求 ms 级）；吞吐优先的批处理任务反而 Parallel/G1 更合适。

**Q8（加分）：GC 日志怎么读？**
带 `-Xlog:gc` 运行示例可见（真实输出）：`[0.342s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 22M->4M(252M) 4.291ms`——启动后 0.342 秒，第 0 次回收，Young 暂停，回收前 22M→后 4M，堆当前承诺 252M，停顿 4.291ms。括号里的 `G1 Humongous Allocation` 说明这次是由**大对象分配**触发的——示例里 1MB 的 byte[] 在默认堆的 Region 大小下正是大对象，一条日志串起 2.4 的大对象直达。

## 六、实际应用与取舍

- **缓存引用选型**：本地缓存要么接受占内存（强引用 + 上限淘汰，如 [LRU](../../集合框架/LinkedHashMap与LRU/知识详解.md)），要么用软/弱引用让路 GC——后者命中率不可控，只适合"有最好"的数据。
- **减少 GC 压力的写法**：循环内复用对象/容器、避免无意义包装、日志拼接用惰性求值（`logger.isDebugEnabled` 或占位符 `{}`）。
- **收集器选择**：默认 G1 就好；吞吐型批处理试 Parallel；超大堆低延迟上 ZGC；容器小内存（<256M）Serial 反而稳。
- **取舍**：所有 GC 优化先**测量**（jstat/JFR，见[调优](../调优工具与OOM排查/知识详解.md)）再动手——凭感觉调参是玄学。
