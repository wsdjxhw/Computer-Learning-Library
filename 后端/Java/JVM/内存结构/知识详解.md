# JVM 内存结构（运行时数据区）

## 学习目标

- 说出 JVM 运行时数据区的五个部分，分清哪些线程共享、哪些线程私有。
- 理解虚拟机栈的栈帧机制，亲眼看到 StackOverflowError 发生在第几层。
- 掌握堆的关键读数：maxMemory / totalMemory / freeMemory 分别是什么。
- 讲清 JDK 8 的版图大迁移：永久代 → 元空间、常量池搬进堆（必考）。

**前置知识**：[字符串](../../语言基础/字符串/知识详解.md)（字符串常量池的用法层）、[ArrayList](../../集合框架/ArrayList/知识详解.md)（对象与引用的关系）。
**适用范围**：一切 JVM 参数调优、OOM/SOE 排查的地基；面试 JVM 第一题。

---

## 一、本节解决什么问题

"对象存在哪？栈溢出和内存溢出有什么区别？JDK 8 的永久代去哪了？"——这些问题的答案都在同一张地图上：JVM 把运行时管理的内存划成几个职责不同的区域，每个区域存什么、谁能访问、满了会抛什么错，就是本篇的全部内容。它是后面 [GC](../GC与垃圾收集器/知识详解.md) 与 [调优排查](../调优工具与OOM排查/知识详解.md) 的地基：不知道各区存什么，就无从谈"谁回收谁""哪里溢出"。

## 二、核心原理

### 2.1 全景图：五 + 一 个区域

| 区域 | 线程 | 存什么 | 满了会怎样 |
| --- | --- | --- | --- |
| 堆 Heap | **共享** | 对象实例、数组、Class 实例、static 变量指向的对象 | OutOfMemoryError: Java heap space |
| 方法区（元空间实现） | **共享** | 类元数据（类名/字段/方法字节码）、运行时常量池 | OutOfMemoryError: Metaspace |
| 虚拟机栈 JVM Stack | 私有 | 栈帧（局部变量表、操作数栈、返回地址） | StackOverflowError |
| 本地方法栈 | 私有 | 同上，服务 native 方法 | StackOverflowError |
| 程序计数器 PC | 私有 | 当前线程执行到的字节码行号 | **唯一不会 OOM 的区** |

外加一块不在"运行时数据区"规范里的**直接内存**（NIO 的 DirectBuffer 用），满了也抛 OOM。

### 2.2 虚拟机栈：方法调用的账本

每次方法调用压入一个**栈帧**：局部变量表（参数和局部变量）、操作数栈（计算的临时区）、返回地址。方法返回，栈帧弹出。递归不返回 → 栈帧只压不弹 → 触到 `-Xss` 上限（默认约 1MB）→ StackOverflowError。

三个推论（面试常考的因果链）：

1. 调小 `-Xss` → 可容纳栈帧变少 → 递归深度变小（示例实测：默认 21248 层 vs 256KB 栈 2378 层）；
2. 方法局部变量越多 → 每个栈帧越大 → 深度也变小；
3. 栈是**线程私有**的——一个线程爆栈不影响其他线程，这正是线程隔离的价值。

### 2.3 堆：对象的家 + 三个关键读数

`Runtime` 的三个读数（外部工具 jstat 看的就是它们）：

- `maxMemory` ≈ **-Xmx**：堆上限，默认约为物理内存 1/4；
- `totalMemory`：已向操作系统申请的量，从 **-Xms** 起步、按需增长；
- `freeMemory`：已申请中还没被占用的量；**已用 ≈ total - free**。

最经典的一组概念：**引用在栈，对象在堆**。`byte[] block = new byte[10MB]`——block 这个变量只是栈帧里 4~8 字节的引用，10MB 数据本体在堆。基本类型的**局部变量**（int x = 1）则直接存在栈帧里，不碰堆。

### 2.4 JDK 8 的版图大迁移（必考）

| | JDK 7 及以前 | JDK 8+ |
| --- | --- | --- |
| 类元数据 | 永久代（**堆的一部分**，有上限，易 OOM） | **元空间 Metaspace**（本地内存，默认只受物理内存限制） |
| 字符串常量池 | 永久代 | **堆** |
| static 变量 | 永久代 | 堆（挂在 Class 实例上） |

为什么要迁移：永久代大小由 `-XX:MaxPermSize` 定死，动态加载类多的框架（Spring CGLIB、Groovy）动不动 `OutOfMemoryError: PermGen space`；元空间用本地内存、按需扩展，把"类元数据该占多少"交给操作系统管， PermGen OOM 成为历史。

### 2.5 程序计数器：最小的区，最硬的保证

每个线程一个 PC，记录当前执行到哪条字节码指令。线程切换后回来能接着执行，靠的就是它。因为只需存一个行号，它是**唯一不会 OOM** 的区域——面试送分题，但要能说出"为什么"：它的大小与程序规模无关，恒定极小。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 对象存在栈上 | 对象永远在堆；栈上只有引用（基本类型局部变量除外） |
| 方法区 = 永久代 | JDK 8 起方法区由元空间（本地内存）实现，永久代已成历史名词 |
| 字符串常量池在方法区 | JDK 7 起就搬到了堆里 |
| static 变量在方法区 | JDK 8 起 static 随 Class 实例存在堆里 |
| StackOverflowError 会传染整个进程 | 只炸当前线程（栈私有）；进程通常继续运行 |
| 调大 -Xss 总是好事 | 每个线程的栈都变大，线程数上限（受物理内存约束）反而降低 |
| 递归深度是一个固定数 | 随栈大小、每帧大小（局部变量数）、JVM 版本变化；任何具体数字都只是参考 |
| 拿 freeMemory 当"堆剩余空间" | 剩余 = maxMemory - 已用；free 只是"已申请未占用"，GC 后 total 内会腾出 |

**排查思路**："StackOverflowError" → 看栈顶是不是自己的递归方法（日志会打几百行同类栈帧）；"OutOfMemoryError: Java heap space" → 堆不够或泄漏（见[调优排查](../调优工具与OOM排查/知识详解.md)）；"Metaspace" → 类加载失控（动态代理/CGLIB 未复用）。

## 五、八股追问

**Q1（必考第一题）：JVM 运行时数据区有哪几块？哪些共享哪些私有？**
线程共享：堆、方法区（元空间）。线程私有：虚拟机栈、本地方法栈、程序计数器。一句话记忆："**共享的存数据，私有的管执行**"。
**追问：为什么栈和 PC 必须私有？** 方法调用状态（栈帧）和执行位置（PC）都是"执行现场"——线程切换后各自恢复各自的现场；共享它们等于互相踩踏。

**Q2（高频）：堆和栈的区别？**
分工不同：栈管**运行**（方法调用的栈帧、局部变量、基本类型值），自动随方法结束弹出，无需 GC；堆管**存储**（对象实例与数组），由 GC 管理，生命周期不由方法决定。速度上栈分配只是移动指针、快得多；容量上栈默认 ~1MB、堆默认物理内存 1/4。
**追问：`int x = 1` 在哪？`Integer x = 1` 呢？** 前者基本类型局部变量，值直接在栈帧；后者是对象引用，引用在栈、Integer 实例在堆（缓存池的细节见[字符串与包装类](../../语言基础/数据类型与变量/知识详解.md)）。

**Q3（必考）：StackOverflowError 和 OutOfMemoryError 的区别？各区分别抛哪个？**
SOE = 空间"不够深"：栈帧层数超限（递归）；OOM = 空间"不够大"：堆放不下新对象、元空间放不下新类、直接内存耗尽等。栈**只会 SOE 不会 OOM**（规范未要求栈可扩展，HotSpot 不可扩展）；堆/元空间/直接内存抛 OOM；PC 都不抛。
**追问：栈能不能抛 OOM？** 理论上规范允许"可扩展栈扩展失败抛 OOM"，但 HotSpot 栈不可扩展，实践中只见过 SOE——回答时加这句区分度立现。

**Q4（必考）：JDK 8 为什么用元空间取代永久代？**
三个痛点：① 永久代有 MaxPermSize 上限，动态类加载多的框架易 PermGen OOM，调参全靠猜；② 永久代在堆内，GC 策略被堆绑死；③ 与 JRockit/HotSpot 融合的技术债。元空间用本地内存、默认按需增长（可用 -XX:MaxMetaspaceSize 兜底），把类元数据的容量问题和堆解耦。
**追问：迁移后 PermGen OOM 就绝迹了吗？** 变成了 Metaspace OOM——CGLIB 滥用、类加载器泄漏仍会撑爆元空间，只是阈值从"写死的参数"变成"物理内存"。

**Q5（高频）：字符串常量池在哪里？intern 是干什么的？**
JDK 7 起在**堆**中（原在永久代）。池中每个字符串只有一份：字面量 `"学习库"` 直接进池共享；`new String("学习库")` 强制堆里再造新对象；`intern()` 返回池中那一份（池没有就放进去）。示例实测：`s1 == s2` false、`s1 == s3` true。
**追问：为什么代码规范禁用 == 比字符串？** == 比地址，结果取决于对象是否恰好共享池，和内容无关；equals 才是内容比较。

**Q6（高频）：JVM 常用内存参数有哪些？**
-Xms/-Xmx 堆初始/最大；-Xss 每线程栈大小；-XX:MaxMetaspaceSize 元空间上限；-XX:+HeapDumpOnOutOfMemoryError（OOM 自动转储）；-Xmn 新生代大小。读数对应：maxMemory↔Xmx、totalMemory 起步于 Xms。
**追问：-Xss 调大有什么代价？** 单线程栈更大 → 同样物理内存能容纳的线程更少；默认 1MB 对 99% 程序够用，别动。

**Q7：程序计数器为什么是唯一不会 OOM 的区域？**
它只存当前字节码指令地址，大小恒定、与程序和数据的规模无关，物理上不可能"放不下"。它也是 JVM 规范中唯一没有规定任何 OutOfMemoryError 情形的区域。

**Q8（加分）：直接内存是什么？和堆什么关系？**
NIO 的 DirectBuffer 可在堆外（本地内存）分配，避免堆内↔本地的复制开销（零拷贝路径，见[NIO基础](../../IO流/NIO基础/知识详解.md)）。不受 -Xmx 限制但受物理内存限制，满了抛 OutOfMemoryError: Direct buffer memory；不用的缓冲靠 Cleaner（虚引用）回收——串联起[GC 的引用体系](../GC与垃圾收集器/知识详解.md)。

## 六、实际应用与取舍

- **读数对账**：监控里 JVM 内存曲线的三个层次（used < committed < max）正对应本篇的已用/已申请/上限——看懂地图才看得懂监控。
- **递归改迭代**：真遇到 SOE，治本是改循环/尾递归优化（Java 无自动尾递归），调 -Xss 只是买深度。
- **参数起步**：容器/物理内存已知时，-Xmx 设为可用内存的 50%~75%（给元空间、栈、直接内存留量），-Xms = -Xmx 防抖动（理由见[调优](../调优工具与OOM排查/知识详解.md)）。
- **取舍**：栈快但小、堆大但要 GC——没有"把对象放栈上"的选项（逃逸分析标量替换是 JIT 的透明优化，不必指望）。

## 八、运行示例

- 环境：JDK 11+（本库以 JDK 21 验证）。
- 命令：`java 示例代码.java`；UTF-8 终端加 `-Dstdout.encoding=UTF-8`。
- 变体（强烈推荐）：`java -Xss256k ...` 看爆栈深度骤降；输出对照着看。
- 预期输出（节选；深度与内存读数每次不同）：

```text
== 第 1 段：虚拟机栈 ==
  递归到第 21248 层爆栈：StackOverflowError（深度每次不同）
== 第 2 段：堆 ==
  堆上限 maxMemory:    4002.0 MB（≈ -Xmx，默认约为物理内存 1/4）
  已申请 totalMemory: 252.0 MB（从 -Xms 起步，按需向操作系统要）
  new 了 10MB byte[] 后，已用 ≈ 24.3 MB（GC 时机不同读数会漂）
== 第 3 段：方法区/元空间 ==
  s1 == s2: false（new 造了新对象，地址不同）
  s1 == s3: true（intern 拿回池中共享的那份，地址相同）
```

- `-Xss256k` 变体实测：`递归到第 2378 层爆栈`——同一程序，栈缩为 1/4，深度降为约 1/9。
