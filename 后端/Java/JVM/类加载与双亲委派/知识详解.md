# 类加载与双亲委派

## 学习目标

- 说清类从 .class 文件到可用的完整生命周期：加载 → 验证 → 准备 → 解析 → 初始化。
- 掌握类初始化的时机：静态代码块到底什么时候执行（实验验证）。
- 讲透双亲委派机制：是什么、为什么（三大作用）、怎么被打破。
- 认识三层类加载器（启动/平台/应用）及 JDK 9 的变化。

**前置知识**：[反射与注解](../../语言基础/反射与注解/知识详解.md)（Class 对象从哪来）、[内存结构](../内存结构/知识详解.md)（类元数据的归宿——元空间）。
**适用范围**：JDBC 驱动加载、热部署、SPI 框架设计、类冲突/ClassCastException 排查；面试 JVM 篇必考。

---

## 一、本节解决什么问题

`.java` 编译成 `.class` 只是半成品——类里的静态字段怎么赋值、静态块什么时候跑、`java.lang.String` 由谁负责加载、两个不同项目各自带的同名类会不会打架？这些答案都在**类加载机制**里。核心是一场"谁说了算"的制度设计：三层加载器各管一摊，请求**先向上委托**——这就是双亲委派（Parent Delegation）。理解了它，"为什么自己写的 String 永远替换不了 JDK 的 String"这类问题不言自明。

## 二、核心原理

### 2.1 类加载的五个阶段

```text
.class 文件
  ① 加载 Loading        按全限定名读到字节流，在方法区建类元数据，堆里造 Class 对象
  ② 验证 Verification    格式/语义/字节码安全检查（防篡改的字节码）
  ③ 准备 Preparation     static 变量分配内存并给【零值】——此时 value=0，不是 42！
  ④ 解析 Resolution      常量池符号引用 → 直接引用（可延迟到首次使用）
  ⑤ 初始化 Initialization 执行 <clinit>：static 显式赋值 + 静态块，【仅一次】
```

最易考的细节在③和⑤的分工：`static int value = 42` 在准备阶段 value = 0（零值），到初始化阶段才变 42；但 `static final int X = 42`（编译期常量）在准备阶段就是 42——ConstantValue 属性直接进 class 文件。

### 2.2 初始化时机：主动引用才触发

只有**主动引用**六种情况才触发初始化（执行静态块）：new、读写非编译期常量的静态字段、调用静态方法、反射调用（`Class.forName`）、初始化子类连带父类、启动类（含 main 的）。**被动引用不触发**（示例第 2 段逐一验证）：

- `Late.class` 类字面量——只加载不初始化；
- `loader.loadClass(name)`——只加载不初始化；
- `Class.forName(name)`（默认 initialize=true）——**触发初始化**；
- 已初始化的类不重复初始化——静态块整个生命周期只执行一次。

JDBC 用 `Class.forName("com.mysql.jdbc.Driver")` 的原理就在这：**强制初始化**驱动类，驱动在静态块里向 DriverManager 注册自己。（JDK 4 起 SPI 自动发现后不必再手写，但机制考点仍在。）

### 2.3 三层加载器与双亲委派

JDK 9+ 的标准三层：**启动类加载器**（Bootstrap，C++ 实现，加载 JAVA_HOME/lib 核心库，Java 层引用为 null）→ **平台类加载器**（Platform，加载 java.sql 等模块；JDK 9 取代扩展加载器）→ **应用类加载器**（App，加载 classpath 上你的代码和 jar）。

双亲委派流程：收到加载请求 → **一路向上委托给最顶层** → 顶层加载不了才逐层**向下退回**，最后没人能加载才抛 ClassNotFoundException。示例第 3 段的自定义 LoggingLoader 实测：请求加载 `java.lang.String`，一路委托到启动类加载器命中返回——**子加载器全程没机会插手**。

三大作用（面试标准答案骨架）：

1. **安全**：自定义加载器永远无法伪造核心类——你写的 `java.lang.String` 到不了加载那一步；
2. **唯一**：同一个类全 JVM 只被加载一次，Class 对象唯一（配合 2.4 的相等判定）；
3. **高效**：父加载器命中缓存直接返回，避免重复加载。

### 2.4 类的"相等"由加载器说了算

JVM 判定两个类"是同一个类"：**全限定名相同 + 定义类加载器相同**。同一个 class 文件被两个无关加载器各加载一次，得到两个不同的 Class——instanceof 为 false、强转抛 ClassCastException。这是热部署/容器类隔离的原理，也是一堆"明明同一个类却转型失败"灵异事件的解释。

### 2.5 打破双亲委派的三大场景

| 场景 | 打破方式 | 动机 |
| --- | --- | --- |
| SPI/JDBC | 线程上下文类加载器（Thread Context ClassLoader）——父亲【反向】委托儿子 | 核心库的 DriverManager 要加载应用层 jar 里的厂商驱动，父加载器看不见 classpath |
| Tomcat | 每个 Web 应用独立 WebappClassLoader，应用类**先自己加载** | 应用间依赖版本隔离 |
| 热部署/OSGi | 网状按需委派 | 不重启换类（代价是复杂度） |

"打破"不是乱来，全是**有明确理由的逆向委派**——面试先讲默认机制三大作用，再讲特例与动机。

示例文件：`示例代码.java`（段落与下述一一对应）

**第 1 段：加载器层级**。从本类出发 getParent 一路向上：MemoryClassLoader → App → Platform → null（启动类加载器）。顺带一个真实发现：单文件 `java 示例代码.java` 运行时编译产物在内存里，**多出一层 MemoryClassLoader**（JEP 330）；正常 javac/java 下最底层就是 AppClassLoader。String 由 null（启动）加载、DriverManager 由 Platform 加载——各回各家。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 类一被加载就执行静态块 | 加载≠初始化；类字面量/loadClass 都不触发静态块 |
| Class.forName 一定触发初始化 | 默认重载（initialize=true）才触发；forName(name, false, loader) 等价于不初始化 |
| 父加载器是"父类" | 是**组合**（字段持有 parent 引用），不是继承；父不认识儿子 |
| 启动类加载器是 Java 类 | C++ 实现，Java 层 getClassLoader() 拿到 null（示例实测） |
| 自己写个 java.lang.String 能替换 JDK 的 | 双亲委派下到不了应用加载器那步；且核心包受安全限制 |
| 两个同名类必然冲突 | 只有**同一加载器**下才冲突；不同加载器各加载一份，类不相等（见 2.4，反而可共存） |
| 双亲委派被"打破"= 设计失败 | 特例皆有动机（隔离/反向委托）；默认机制仍是压舱石 |
| 卸载类很容易 | 条件苛刻：该类所有实例已回收 + Class 对象回收 + 加载器本身回收——加载器长寿（如 App）类就几乎不卸载 |

**排查思路**："ClassCastException 但看代码同类型" → 两套加载器各加载了一份（容器/热部署/自建 URLClassLoader）；"ClassNotFoundException" → classpath 缺 jar 或名字写错；"静态块没执行" → 走的是类字面量/loadClass，不是主动引用。

## 五、八股追问

**Q1（必考）：类加载的过程有哪几步？**
加载（读字节流、建元数据、造 Class 对象）→ 验证 → 准备（static 给**零值**）→ 解析（符号引用→直接引用）→ 初始化（执行 static 赋值与静态块，仅一次）。验证到解析合称连接。
**追问：`static int a = 42` 在准备阶段值是多少？** 0——42 是初始化阶段 <clinit> 里才赋的；但编译期常量 `static final int A = 42` 准备阶段就是 42（ConstantValue）。答对这层区分即加分。

**Q2（必考）：什么是双亲委派？为什么这么设计？**
子加载器收到请求先无条件委托父亲，父亲加载不了才自己加载。作用三条：安全（核心类不可伪造）、唯一（类只加载一次，Class 对象唯一）、高效（命中缓存直接返回）。
**追问：自己写一个 java.lang.String 放 classpath 会怎样？** 委派到启动类加载器一步就命中 JDK 自带的——你的文件根本不会被加载；加上核心包访问保护，连绕过都难。

**Q3（高频）：哪些场景打破了双亲委派？**
① SPI（JDBC）：核心库要加载厂商实现，用线程上下文类加载器让父亲反向委托儿子；② Tomcat：WebappClassLoader 先自己加载应用类再委托（应用间版本隔离）；③ 热部署/OSGi：网状委派。**追问：为什么 JDK 需要线程上下文加载器？** JVM 的类加载器只认"向上"，SPI 的接口在顶层、实现在底层，只能借当前线程"捎带"一个底层的加载器下来。

**Q4（高频）：什么情况会触发类的初始化（执行静态块）？**
主动引用六种：new 实例、读/写非编译期常量静态字段、调静态方法、反射（Class.forName）、初始化子类先初始化父类、JVM 启动的 main 类。被动引用（不触发）：类字面量拿 Class、loadClass、通过子类引用父类静态字段、引用编译期常量。
**追问：`Class.forName` 和 `ClassLoader.loadClass` 的区别？** 前者加载+初始化，后者只加载；JDBC 注册驱动必须初始化，所以历史上用 forName。

**Q5：三层类加载器各自加载什么？JDK 9 变了什么？**
启动（Bootstrap，null）：JAVA_HOME/lib 核心库；平台（Platform）：java.* 模块（JDK 9 取代"扩展加载器"，配合模块化裁掉了 ext 目录）；应用（App）：classpath。**追问：为什么取消扩展加载器？** JDK 9 模块化（Jigsaw）重整了加载边界，"扩展"机制被模块路径取代，平台加载器接管其职责并改名。

**Q6（经典）：怎么判断两个类是【同一个类】？**
全限定名相同 **且定义类加载器实例相同**。同一 class 文件被两个加载器各加载一次 = 两个不同的类（instanceOf false、互转 CCE）。衍生经典题：同一个类被加载两次，static 计数器是否共享？——不共享，两套 Class 各一份。
**追问：那同一个类的两个实例的 Class 对象呢？** 同一个（该加载器下唯一）——c1.getClass() == c2.getClass()。

**Q7（加分）：类什么时候会被卸载？**
三条件同时满足：类所有实例已回收、Class 对象无引用、定义它的加载器已回收。三者里最苛刻的是加载器——App 加载器与应用同寿命，所以系统类几乎永不卸载。热部署能换类，正是靠"整个加载器扔掉重造"实现三条件一次满足。这也解释了 Metaspace 泄漏的常见根因：**不断新建加载器又不释放**（见[内存结构](../内存结构/知识详解.md)的 Metaspace OOM）。

**Q8：为什么单文件运行（java X.java）时多一层加载器？**
JEP 330 的源码启动器把编译产物放进内存，由内部的 MemoryClassLoader 加载（本示例第 1 段实测可见），其父链仍是 App → Platform → null。只是启动方式带来的实现细节，标准三层与委派机制完全不变——见到陌生加载器先 getParent 走一遍，是最快的诊断动作。

## 六、实际应用与取舍

- **SPI 框架设计**：接口放核心模块、实现放应用，靠 ServiceLoader + 上下文加载器衔接（JDBC、日志门面都这么玩）。
- **类冲突排查**：同名类两个版本共存时，打印 `clazz.getClassLoader()` 对账——不同加载器 = 两个类共存，而非"覆盖"。
- **热部署**：换加载器即换世界；但享元（Integer 缓存等）跨加载器不共享，内存成本要评估。
- **取舍**：自定义加载器是高阶武器（隔离/热替换/加密字节码），业务代码 99% 用不上——面试会讲即可，工程慎用。
