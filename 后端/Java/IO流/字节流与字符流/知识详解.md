# 字节流与字符流

## 学习目标

- 分清字节流（InputStream/OutputStream）与字符流（Reader/Writer）的适用场景。
- 理解 `read()` 返回 int 的原因、编码不一致导致乱码的机制。
- 理解缓冲流的装饰器结构与性能意义。
- 掌握经典文件复制套路与 `Files` 工具的现代替代。

**前置知识**：[异常处理](../../语言基础/异常处理/知识详解.md)（try-with-resources 是本篇的默认姿势）、[字符串](../../语言基础/字符串/知识详解.md)（编码）。
**适用范围**：Java IO 体系；文件读写、网络数据传输、一切数据搬运的地基。

---

## 一、本节解决什么问题

程序要与外部交换数据（文件、网络、内存），Java 用"流"统一抽象这件事：**数据像水流过管道，程序从一端读、向另一端写**。但数据分两种——照片/zip 这类**原始字节**，和文本这种"字节 + 编码"的**字符**。IO 体系按此分成两大门派，选错门派轻则效率低，重则乱码。

## 二、核心原理

### 2.1 四大抽象基类

| | 字节流（万能） | 字符流（文本专属） |
| --- | --- | --- |
| 输入 | `InputStream` | `Reader` |
| 输出 | `OutputStream` | `Writer` |

选择标准一句话：**内容是文本 → 字符流；不确定/二进制 → 字节流**。字节流读文本要自己处理编码（配合 InputStreamReader）。

### 2.2 read() 为什么返回 int

两个原因：① 要用 **-1 表示"读完了"**，byte 是有符号的（-128~127），-1 与合法字节值冲突，装不下哨兵；② int 低 8 位是**无符号字节**（0~255），避免 byte 的负数值（如 0xFF = -1）被误判为流结束。

### 2.3 字符流的本质：字节流 + 编解码器

字符从来不是直接存进文件的——写文件时字符按编码（UTF-8/GBK…）转成字节，读文件时再解码回来。`OutputStreamWriter`/`InputStreamReader` 是两大门派之间的**桥梁**：

```java
new OutputStreamWriter(new FileOutputStream(f), StandardCharsets.UTF_8)  // 字符 → 按 UTF-8 编码 → 字节
new BufferedReader(new InputStreamReader(new FileInputStream(f), UTF_8)) // 字节 → 按 UTF-8 解码 → 字符
```

乱码的根源永远是一个：**编码与解码用了不同方案**（示例第 2 段用 GBK 硬解 UTF-8 字节，输出"宸ヤ祫锛"即证据）。写读两端显式指定同一编码是铁律——不写就是赌 JVM 默认值，换个平台就翻车。

### 2.4 缓冲流：装饰器模式

`BufferedXxx` 不替换流，而是**包一层 8KB 内存缓冲**：无缓冲时每 write/read 一次就触发一次系统调用；有缓冲则攒一批再搬运，快几个数量级。`new BufferedWriter(new OutputStreamWriter(new FileOutputStream(...)))` 这种"俄罗斯套娃"就是**装饰器模式**——每层只加一个能力（文件落地 / 编码转换 / 缓冲），自由组合。

### 2.5 文件复制标准套路

```java
try (InputStream in = ...; OutputStream out = ...) {
    byte[] buf = new byte[8192];
    int len;
    while ((len = in.read(buf)) != -1) {   // read 返回实际读到的字节数
        out.write(buf, 0, len);            // 只写 len 个——最后一段往往不满一桶
    }
}
```

`write(buf, 0, len)` 的 len 是高频出错点：最后一段不足 8192 字节，写整段会把上一次的残留数据带出去。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| 不关流 | try-with-resources 兜底；不关会泄漏文件句柄，Windows 上还锁文件 |
| 编码靠默认值 | 显式指定 UTF-8；`FileReader`/`FileWriter` 用平台默认编码，慎用 |
| write(buf) 写整段 | 必须 `write(buf, 0, len)`，最后一段有残留风险 |
| 用字节流 readLine | 字节流没有行的概念；文本按行处理用 BufferedReader |
| 忽略 flush | 缓冲流/管道数据要 flush/close 才落盘/送达；close 前先 flush |
| 中文乱码乱试编码 | 先确认文件真实编码，再显式按它读；两端一致是唯一解 |
| 大文件 readAllBytes | 一次性全读进内存会 OOM；流式处理或 Files.lines 逐行 |

**排查思路**：乱码 → 先查文件真实编码 vs 读取编码；"文件被占用"（Windows 删不掉）→ 有流没关；数据尾部有脏字节 → 查 write 是否带了 len。

## 五、八股追问

IO 流的八股偏"体系认知题"，考的是对整个家族树的把握。

**Q1（必考）：字节流和字符流的区别？怎么选？**
字节流按 8 位字节搬运（InputStream/OutputStream），处理一切数据；字符流按字符搬运（Reader/Writer），内部自动编解码，只处理文本。选型：文本用字符流（省去手工编解码），二进制/不确定用字节流。
**追问：字符流的本质？** 字节流 + 编解码器的组合——Reader/Writer 底层还是包装着字节流。

**Q2：InputStreamReader 在体系里扮演什么角色？**
"字节流 → 字符流"的**桥梁（适配器）**：接收一个字节流和一个字符集，把字节解码成字符。`FileReader` 就是 `InputStreamReader(FileInputStream)` 的便捷子类（默认编码），需要显式编码时必须自己组装这对桥梁。

**Q3（高频）：read() 为什么返回 int 而不是 byte？**
-1 要当"流结束"哨兵，而 byte 的 -1 与合法数据 0xFF 冲突；返回 int 既放下哨兵，又让低 8 位按 0~255 无符号解释，两个问题一起解决。

**Q4：缓冲流的原理是什么？为什么快？**
在用户态加一块 8KB 数组做蓄水池：写时攒满一桶才触发一次系统调用（内核拷贝），读时一桶一桶搬。系统调用和内核交互是 IO 的大头开销，次数降两个数量级，速度就上两个数量级。缓冲流**不改变数据**，只改变搬运节奏——这正是装饰器模式的语义。

**Q5：什么是装饰器模式？IO 体系怎么体现的？**
"不修改原类、通过包装增强能力"的结构模式：BufferedInputStream 包装 FileInputStream 得到缓冲能力，再包 DataInputStream 得到读 Java 基本类型的能力……每层只加一个功能、可自由组合，比继承爆炸（BufferedFileInputStream、DataBufferedFileInputStream…）优雅得多。

**Q6：flush 和 close 的区别？**
flush 把缓冲数据立刻推送出去但流还能继续用；close 先 flush 再释放句柄，之后流作废。不 flush 就依赖 close 兜底——但如果程序中途崩溃，没 flush 的数据就丢了；对实时性有要求（日志、socket）要主动 flush。

**Q7：序列化用哪个流？**
对象流 `ObjectOutputStream`/`ObjectInputStream`（writeObject/readObject），类要实现 `Serializable`。
**追问：serialVersionUID 干什么用？** 版本指纹——反序列化时两边不一致抛 InvalidClassException，防止类结构变化后被错误还原。

## 六、实际应用与取舍

- **配置/小文本**：`Files.readString/writeString` 一步到位（见[文件与Path](../文件与Path/知识详解.md)）。
- **日志文件逐行分析**：`Files.lines` + Stream（见[Lambda与Stream](../../语言基础/Lambda与Stream/知识详解.md)）。
- **网络传输**：Socket 拿到的就是字节流，协议是文本则套 InputStreamReader。
- **取舍**：新代码优先 NIO 工具（Files），经典流用于理解原理、处理流式/增量数据；必须流式处理（文件大于内存）时，字节流 + 缓冲仍是唯一正解。
