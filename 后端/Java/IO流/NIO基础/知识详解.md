# NIO 基础（Buffer / Channel / Selector）

## 学习目标

- 掌握 NIO 三大件的分工：Buffer（容器）、Channel（通道）、Selector（多路复用器）。
- 熟练 Buffer 三指针（position/limit/capacity）与 flip/clear 的切换逻辑。
- 会用 FileChannel 读写文件、transferTo 复制文件，理解零拷贝思想。
- 理解 Selector 事件循环的工作模型，说清 BIO/NIO/AIO 的区别。
- 建立"NIO 不一定更快"的正确认知。

**前置知识**：[字节流与字符流](../字节流与字符流/知识详解.md)（BIO 的流式 API——本篇处处与之对照）、[多线程基础](../../并发编程/多线程基础/知识详解.md)（BIO 一连接一线程的代价）。
**适用范围**：高并发网络服务（Netty 底层）、大文件高效传输；是理解各类通信框架的地基。

## 一、本节解决什么问题

经典 IO（BIO）有两个结构性短板：

1. **流是单向的、阻塞的**——读就会卡到有数据，一线程伺候一连接，一万连接一万线程，内存和调度直接崩（[TCP通信第 3 段](../../网络编程/TCP通信/知识详解.md)的天花板）；
2. **数据在内核态与用户态来回倒**——read 把数据从内核缓冲拷进 JVM 堆，write 又拷回去，大文件传输白白多搬几趟。

NIO（JDK 1.4 引入"New IO"，后称 Non-blocking IO）的解法：**Channel 双向 + Buffer 承载 + 非阻塞 + Selector 多路复用**——一个线程用一次 select() 盯住成百上千条连接上"谁就绪了"的事件，谁就绪处理谁；数据搬运上提供 transferTo 等内核态直搬能力（零拷贝）。

## 二、核心原理

### 2.1 三大件的分工

```text
                ┌─────────────┐
   数据 ────────▶│   Buffer    │ ◀──────── 数据
   （容器：装字节的杯子，管指针）│
                └──────┬──────┘
                       │ 只认 Buffer，不认数组
                ┌──────┴──────┐        ┌──────────┐
                │   Channel   │◀──────▶│ Selector │
                │（通道：双向门）│        │（盯事件的看门人）│
                └─────────────┘        └──────────┘
```

- **Buffer**：数据的容器，内部一数组 + 三个指针。
- **Channel**：数据进出的通道，**双向**（同一通道可读可写），可非阻塞。
- **Selector**：注册一批 Channel 的"兴趣事件"，一次 select() 返回所有就绪的——多路复用的核心。

### 2.2 Buffer：三个指针与两次翻转（本篇必须肌肉记忆的部分）

```text
capacity：总容量，分配后不变
position：下一个读/写位置（指针）
limit    ：读/写不得超过的界限

写模式：  [已写 5 格][position=5 → 还能写][limit=8 ───────── capacity=8]
flip 后：  [可读 5 格 0→limit=5][position 归 0]
```

三个关键方法：

| 方法 | 干什么 | 一句话 |
| --- | --- | --- |
| flip() | limit=position; position=0 | **写→读**切换；忘了它读出的是空 |
| clear() | position=0; limit=capacity | 读→写复位；数据没擦，只是可覆盖 |
| rewind() | position=0 | 重读一遍（limit 不动） |

### 2.3 FileChannel：文件版通道

只能通过 FileChannel.open(path, 选项) 或 RandomAccessFile.getChannel() 获得；读写都拿 Buffer 中转。StandardOpenOption 常用项：CREATE、READ、WRITE、TRUNCATE_EXISTING。

### 2.4 零拷贝与 transferTo

传统复制（read+write）：磁盘→内核缓冲→用户态(JVM堆)→内核 socket/文件缓冲→目标，**4 次拷贝 4 次上下文切换**。transferTo 底层走 sendfile 系统调用：内核里直接从源文件页缓存送进目标，**JVM 堆不沾手**。Kafka 的消息批量落盘/网络发送快，核心之一就是这类内核态直搬。同族还有 MappedByteBuffer（mmap 把文件映射进内存）。

### 2.5 Selector 事件循环（NIO 网络的心脏）

```java
channel.configureBlocking(false);              // 非阻塞是注册 Selector 的前提
channel.register(selector, SelectionKey.OP_READ);  // 声明关心的事件
while (true) {
    selector.select();                         // 阻塞到至少一个事件就绪（可带超时）
    Iterator<SelectionKey> it = selector.selectedKeys().iterator();
    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();                           // ★ 必须手动移除，否则下轮重复处理
        if (key.isAcceptable()) { /* 接入新连接 */ }
        else if (key.isReadable()) { /* 某连接数据就绪：read 进 Buffer */ }
    }
}
```

四类兴趣事件：OP_ACCEPT（有人来连）、OP_CONNECT（连接建立）、OP_READ（有数据可读）、OP_WRITE（可以写出——通常默认就绪，缓冲区满才需要关注）。read 返回 -1 = 对端关闭，此时应关闭通道注销事件。

### 2.6 BIO vs NIO vs AIO（一句话版）

| 模型 | 一句话 | 内核支持 |
| --- | --- | --- |
| BIO | 阻塞流；一连接一线程 | — |
| NIO | 非阻塞通道 + Selector 就绪通知（Reactor） | Linux epoll |
| AIO | 内核完成 IO 再回调你（Proactor） | Windows IOCP 成熟；Linux 原生 Aio 不成熟，Netty 曾实现后移除 |

Linux 生产主流是"NIO + epoll"，AIO 在 Java 圈基本没成为现实——面试答"NIO 为主"即可。

示例文件：`示例代码.java`（段落与下述一一对应；第 4 段是 localhost 自回环的完整客户端/服务端演示）

**第 1 段：三指针现场**。allocate(8) → put "Hello" → flip → 逐字节读 → clear，每一步打印 position/limit/capacity——三指针怎么走一目了然（输出见第八节）。

## 四、常见误区与边界条件

| 误区 | 纠正 |
| --- | --- |
| put 完直接 get | 中间必须 flip；否则 position 在队尾，读出 0 字节 |
| clear 以为会清空数据 | 只是复位指针，旧数据仍在（直到被覆盖） |
| 忘了 selectedKeys 的 it.remove() | 下一轮 select 重复处理同一事件（经典 NIO bug） |
| 阻塞模式下直接 register | 抛 IllegalBlockingModeException——先 configureBlocking(false) |
| 一个 Buffer 读写两用不切指针 | flip/clear 错位是 NIO 代码乱码与空读的第一大来源 |
| read 返回 -1 不处理 | -1=对端关闭；不 close 不 cancel 会反复触发读事件（busy loop） |
| 以为 NIO 一定比 BIO 快 | 连接少且个个忙碌时线程池 BIO 更简单高效；NIO 强在**海量空闲连接** |
| Selector 一个线程打天下 | 单线程 Selector 是教学模型；生产用主从 Reactor（accept 与 IO 分线程）——见 Netty |
| 非阻塞 read 读到 0 字节当异常 | 正常现象（暂时没数据）；按 -1 才是关闭、>0 有数据、0 没数据处理 |

**排查思路**："读到空/乱码" → 检查 flip 时序与 Buffer 复用；"CPU 100% 空转" → 大概率某通道 read 到 -1 未关闭，触发就绪死循环；"连接数上不去" → 查文件描述符上限（ulimit -n）。

## 五、八股追问

NIO 是 Java IO 面试的**分水岭题**：初级答得出区别，中高级要答得出 Selector 细节与零拷贝。

**Q1（必考）：BIO、NIO、AIO 的区别？**
BIO：同步阻塞，流式单向，一连接一线程。NIO：同步非阻塞，Channel+Buffer 双向，Selector 多路复用——一个线程管多连接，谁就绪处理谁（Reactor 模式）。AIO：异步，发起读后内核全程代办、完成后回调（Proactor 模式）；Windows IOCP 可用，Linux 支持不成熟，Java 圈实际以 NIO 为主。
**追问：为什么 NIO 叫"同步非阻塞"？** read/write 本身还是你自己调、自己等结果（同步），但就绪前不挂起线程——通过 Selector 先问"谁好了"再读写（事件就绪模型）。

**Q2（必考）：Buffer 的 flip() 做了什么？**
写转读：limit=position、position=0（capacity 不变）。配套：clear() 读转写复位（position=0、limit=capacity，数据不擦）；rewind() position=0 重读。
**追问：不 flip 会怎样？** position 停在写入队尾，hasRemaining 立即为假，读出 0 字节——NIO 空/乱码 bug 的头号来源。

**Q3（高频）：Selector 的工作流程？**
① 各 Channel 设非阻塞并 register(selector, 兴趣事件)；② select() 阻塞到有事件就绪（可带超时）；③ 遍历 selectedKeys，逐个 it.remove() 后按 isAcceptable/isReadable 分发处理；④ 新连接 accept 后注册自己的读事件；read==-1 时关闭并注销。
**追问：为什么必须 remove？** selectedKeys 是就绪集合的副本，select 只往里加不自动删——不移除下轮还会处理同一事件。

**Q4（高频）：什么是零拷贝？有哪几种实现？**
传统 read+write 数据要 kernel→user→kernel 搬 4 次、上下文切换 4 次。零拷贝让数据不进用户态：① **mmap+write**（MappedByteBuffer：文件映射到用户地址空间，省一次拷贝）；② **sendfile**（transferTo：内核中直接文件→socket/文件，JDK 封装为 FileChannel.transferTo）；③ sendfile+DMA gather（进一步省 CPU 拷贝）。Kafka 大吞吐的关键之一。
**追问：零拷贝是"一次拷贝都没有"吗？** 不是，指不经过**用户态**缓冲；内核/DMA 层的搬运仍在。

**Q5：NIO 一定比 BIO 快吗？**
不一定。NIO 赢在"连接数巨大但活跃比例低"（长连接网关、IM）——省的是线程内存与切换；连接少且都忙碌时，线程池 BIO 的吞吐完全不输，还免掉事件循环复杂度。NIO 的代价：编程模型复杂（事件状态机、半包拆包、Buffer 指针管理），所以生产几乎都用 Netty 这类封装。
**追问：什么场景必须 NIO？** 十万级长连接、推送、游戏服务器——线程数成为资源瓶颈的地方。

**Q6：堆内 Buffer 和直接 Buffer（allocateDirect）的区别？**
allocate：JVM 堆内，受 GC 管理，分配便宜；但 IO 时内核不能直接写堆内存（GC 可能移动对象），要多一次"堆→本地"拷贝。allocateDirect：堆外本地内存，内核可直写，省一次拷贝、适合大流量反复 IO；代价是分配贵、不受堆 GC 管理（靠 Cleaner 释放），泄漏难查。网络/文件通道的大缓冲推荐 direct。

**Q7（操作系统层连线）：select、poll、epoll 的区别？**
select：fd 集合有上限（1024）、每次调用全量线性扫描、每次要重新传集合；poll：链表无上限，仍线性扫描；epoll（Linux）：红黑树注册一次 + 就绪链表回调，只返回就绪的 fd——百万连接下依然高效。Java Selector 在 Linux 上底层就是 epoll（Windows 上是选择器原生实现）。

**Q8：Netty 和 NIO 是什么关系？**
Netty 是 NIO 的工程化封装：EventLoopGroup（主从 Reactor 线程模型）、ByteBuf（可扩展的 Buffer 指针管理，解决 flip 心智负担与半包）、开箱即用的编解码器与粘包拆包处理器、空轮询 bug 规避。回答时点一句"生产不裸写 NIO"即是加分项。

## 六、实际应用与取舍

- **高并发长连接服务**：网关、IM、推送、游戏——Selector/Netty 的主场。
- **大文件传输**：transferTo/mmap（日志搬运、静态资源分发、消息队列落盘）。
- **文件定期读取**：FileChannel + 固定 Buffer 比小 byte[] 的流式读少拷贝（见[文件与Path](../文件与Path/知识详解.md)的 Files 系列对比）。
- **取舍**：业务后端内部服务连接数有限，[BIO+线程池](../../网络编程/TCP通信/知识详解.md)依然合理；别为了"NIO 高级"引入事件循环复杂度——用 Netty 的前提也是"确实到了它的场景"。

## 七、可继续学习的方向

- **Netty**：EventLoop、Pipeline、ByteBuf、粘包拆包——NIO 的工业级封装。
- **Reactor 与 Proactor 模式**：事件驱动 IO 的两种经典设计。
- **epoll 原理**：操作系统层（红黑树+就绪链表），树结构见[数据结构与算法/二叉搜索树](../../../../数据结构与算法/数据结构/二叉搜索树/知识详解.md)。
